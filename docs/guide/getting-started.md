# Getting started with the board

For people who have installed the board and want to see what it does.

[Back to the documentation index](../README.md)

In this page, "the box" means the machine that runs the board.

## Using it

- **New project** (the **+** menu, the sidebar's **+ project**, Home's empty state, or `c` then `p`) → the four-step wizard ([below](new-project-and-clone.md#the-new-project-wizard)): name, repo (blank, clone or import), agent defaults, first prompt. *Import from GitHub* and *Batch prompt* are also in the **+** menu (`c` then `r` imports). Clones run in a visible session (`<project>--<repo>--clone`) and the sheet shows the clone queue; if a clone fails the repo shows *clone failed* and *Attach* shows the error. Home has no per-project *Add repo*, *Delete* or *Remove* buttons any more: they live on the project page (see [The project page](home-and-projects.md#the-project-page); the API is `POST /api/projects/<project>/repos` and `DELETE /api/projects/<project>[/repos/<repo>]`).
- **New session** on a repo → the launcher sheet (the **+** menu, a project block on Home, a project page, the **+** on a project's row in the sidebar, an empty quad slot, the terminal dock, the Move sheet's *Options…*): pick the agent (Claude, Codex or a plain shell), the launch (new, resume, continue, from a pull request, fork) and the fields of that agent; *Start & open* opens the terminal. Everything about it is under [The launcher](launcher.md#the-launcher). Bypass is offered only inside the devcontainer; scheduled, batch and task runs cannot use it.
- **New session** on the *project folder* row (projects that hold several repos) → Claude starts in the project folder itself, so every repo below is in scope without `--add-dir`. Such sessions use the reserved repo name `root` (`<project>--root--<session>` in tmux), so a repo cannot be called `root`.
- **Tasks** (**+ task** on a project page or on `#/tasks`, the **+** menu, or `c` then `t`). On a project page the form opens at once, for the repo in the address, else the one the Files tab shows, else the one a task was last started in, else the first repo (the **in** select at the top of the form switches repo and keeps what you typed), so **+ task**, type, **Start task** is three taps and the prompt box already has the focus. From Home the + menu asks for the repo first. The form is a prompt (Enter adds a line, ⌘/Ctrl+Enter submits; the title is optional and defaults to the first line of the prompt), a **Run** control and *Options*:
  - **Now** starts Claude on a new branch in its own worktree (`claude --worktree`, session `<project>--<repo>--t-<slug>`), toasts *started <slug>* and opens that session's peek (the terminal is one tap from there).
  - **Later** adds a card to the **Backlog** column and nothing starts.
  - **Schedule** swaps the lower half of the form to the schedule fields (name from the title, cron presets *nightly 02:30* / *weekdays 09:00* / *hourly* / *one-off*, which runs once now, permission mode (`auto` unless you pick another), max turns and budget) and creates the job; the prompt is carried over. The agent picker stays: with Codex the form shows its model and reasoning and drops the turn and budget limits (Codex has none).
  - The submit button follows the choice (*Start task* / *Add to backlog* / *Schedule*) and ignores a second tap while the first is in flight. Model, effort and permission mode are under *Options*; they, the Run choice and the cron are remembered per repo on this device (`ccboard:task:<project>/<repo>`), so the next task is a prompt and a key press. Errors show inside the form and nothing you typed is lost. Bypass permissions is never offered for a task, and the server refuses it.
  - The **project folder** is a target too when it is itself a git repo (listed as *<project> · project folder*, repo name `root`): the task runs on a branch of that repo. A project folder that is not a git repo is offered for sessions only; the picker says *tasks need git*.
- **The Backlog.** A backlog card shows the title, the first two lines of the prompt, the repo and when it was added, and has four actions:
  - **Start** (one tap) runs it in a new worktree session, opens its peek, and the card is in *In progress* before the next poll.
  - **Send to session** lists the project's Claude sessions, ready ones first (idle, done, or waiting for an answer) with their last prompt; busy ones (working, or waiting on a permission decision) are listed greyed with the reason. Picking one pastes the prompt into it as a single multi-line paste: no worktree is made, and the card moves to *In progress* with an *in <session>* chip that opens that session. A session of another repo asks *work there anyway?* and then puts `Work in <repo path>.` in front of the prompt. When exactly one session in the task's own repo is ready, the card also has a **→ <session>** button that does it in one tap.
  - **Edit** changes the title and the prompt (the full prompt is loaded first when the poll only carried its head); **Delete** takes two taps.
  - A card waiting behind another step (phase *queued*) can be edited or deleted but not started. Only Backlog and queued tasks can be edited or deleted; a started task is archived.
  - Cards, Start, Send, Edit and Delete update the board at once (the poll only confirms), and an optimistic change that the server refuses puts the card back with the reason as a toast.

  The API: `POST /api/tasks {project, repo, title, prompt, when: now|later, auto_close?, model?, effort?, permission_mode?, args?, add_dirs?}` (`agent` is `claude` until Codex arrives; `repo` may be `root` when the project folder is a git repo), `GET /api/tasks?project=&repo=&phase=` and `GET /api/tasks/<id>` (with the full prompt and the launch choices), `PATCH`/`DELETE /api/tasks/<id>`, and `POST /api/tasks/<id>/dispatch` with `{mode: "lane"}` (a new worktree session) or `{session: "<tmux name>", force?}` (hand it to a running one; 409 with the reason when the session is busy, has a pending permission or belongs to another repo). The per-repo `POST /api/projects/<p>/repos/<r>/tasks` and the MCP `create_task` still work (`create_task` takes `dispatch: false` to add to the Backlog instead of starting). In demo mode (`?demo=1`) the demo state has two Backlog cards (one repo with a single ready session, which gets the one-tap button, and one whose sessions are all busy) and a task handed to a running session, and the buttons act on the page only. Drag and drop, auto-close and chains come later (v0.5.14b and v0.5.15).

  **Queued prompts (issue #64) and closing (issue #88).** A task handed to a working Claude session (`queue: true`: the Move sheet, a drag) is pasted into Claude's queue and runs as a second turn with a Stop of its own. Observed on the box (Claude Code 2.1.294): the UserPromptSubmit of the queued text fires when it is queued, about as long before its turn as the first turn takes, and the first Stop carries the queued prompt's `prompt_id`, so neither the prompt hook nor `prompt_id` says which Stop belongs to the task. The board counts Stops instead: the dispatch stores `turns_ahead` (1 for the turn in flight, one more for every task already queued on that session), every Stop of the session skips one, and the task is credited only with the Stop after the counter reached zero. Until then its card says *queued*, it has no result, and no auto-close countdown starts; its own Stop gives it its own message and the countdown. The dispatch answer and `state.tasks[]` carry `turns_ahead`. Claude runs the prompts it holds in its queue together as ONE turn with one Stop (two tasks queued a second apart came back merged on the box), so the board keeps at most one of its prompts in Claude's queue per session: a task queued behind another queued task stays in the board (answer `held: true`, `pasted: false`, card *queued*) and is typed about 3 s after the Stop that starts the prompt ahead of it, so every queued task gets a turn, a Stop, a result and, for the last, the close of its own. Text queued by hand in the terminal or by `POST /api/sessions/<name>/prompt` is not counted (a task dispatched behind it is credited one Stop early); a queue emptied from the terminal leaves the task waiting for a Stop that does not come. A session the board has queued prompts for wears a **+N queued** chip (Home row, Quad tile, terminal header; `queued_prompts` in the state) counting only those board-queued tasks, never text typed in the terminal; its title reads "prompts the board will send when the session is free" and zero shows nothing.

  A close (auto-close or *Close session*) types the agent's exit command and kills the session 8 s later. Claude's `/exit` in a worktree with changes opens a dialog (*You have N uncommitted files ... 1. Keep worktree / 2. Remove worktree*); while the agent quits the board looks at the pane every 2 s and presses Enter on the preselected *Keep worktree* (never Remove), records an `AutoCloseDialog` event, and gives the agent another 8 s to end, so a SessionEnd is recorded and claude-mem summarises the session. Claude's idle-prompt Notification a minute after the Stop no longer cancels a close that is waiting for a client at the terminal or for claude-mem; a countdown that is dropped for any other reason leaves an `AutoCloseSkipped` event. Reopen starts the task again with the model, effort and permission mode it was created with, also when it was created with `when: now`. It resumes the lane's earlier conversation (`resumed: true`): a `--worktree` session starts in the repo root, so Claude keeps its transcript under the root's project folder, which is where the board looks (after the path the session's own hooks reported), and it puts a copy under the worktree's folder for the resume. While claude-mem is busy the card keeps the countdown and says *waiting for claude-mem*.
- **State badges** come from Claude Code hooks: *working* after you send a prompt, *needs you* when Claude asks for permission or input, *done* when a turn ends (with the last line it printed), *error* on API failures. *Ack* clears a done/error highlight. The hooks are the scripts in `bin/`; they POST to the board over loopback with the token in `~/.local/share/ccboard/hook-token` and never block the TUI (they are registered `async`). `scripts/claude_settings.py show|remove` inspects or removes them. If you already had a `statusLine`, ccboard keeps yours and the per-session model/context numbers stay empty.
- **On a phone** the board is a PWA (add it to the Home Screen): a bottom bar jumps to Needs you / Tasks / Schedules / Projects, action rows scroll sideways, forms open as sheets, and the board re-polls the moment it comes back to the foreground (there is also a ↻ button, since an installed PWA has no browser reload). The UI is built on Blueprint's dark theme.
- The **first interactive launch** of `claude` in a new folder shows Claude Code's workspace-trust prompt and possibly its onboarding screens. Answer them yourself in the terminal; the board never answers them. A task uses `--worktree`, so Claude may refuse to start until trust is accepted. If a running task has reported no state and returns to the login shell with a line starting with that trust error, polling within the first minute (after a 20-second launch grace) marks the session errored and the task failed, with one event and a needs-you notice, locally and through the hub. Sending prompts and echoed commands quoting the error do not trigger this check. Open a session in that repository once, accept the trust dialog, then run the task again. The project page and task launcher warn until the board has opened an interactive Claude session there, a Claude session has reported a state other than this trust failure, or a Claude task has completed. Dispatch to an existing session hides the warning. That history check is advice, not proof that trust was accepted.
- tmux names are `<project>--<repo>--<session>`. From a shell on the box: `TMUX_TMPDIR=/tmp tmux -L ccboard ls`.
- Session sizes follow the most recently active client (tmux `window-size latest`), so attaching from a phone reflows the TUI for a desktop tab that is also attached.

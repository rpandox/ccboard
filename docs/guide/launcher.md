# The launcher

For people starting sessions, tasks and runs.

[Back to the documentation index](../README.md)

### The launcher (v0.5.13)

One sheet starts every kind of run, from every page: the **+** in the top bar, a project block on Home, a project page (*+ session*, *+ task*), the **+** on a project's row in the sidebar, an empty slot of the quad view, the terminal dock and the *Options…* of the Move sheet. It is a right-hand panel from 840 px and a bottom sheet below that; the footer is sticky (*Cancel* and the one filled button, *Start & open*), inputs are 16 px on touch so a phone does not zoom, and a new session from anywhere is two taps once the defaults are remembered (the **+**, then *Start & open*).

- **The agent picker** is a segmented control, *Claude · Codex · Shell*. An agent that is not installed on the box is disabled and says why; the one you used last in this repo is chosen when the sheet opens. Changing the agent swaps the fields.
- **The fields come from `GET /api/agents`** (read once per page load, never on the 3 s poll). The launcher embeds a static copy of the same schema and uses it until the answer arrives or when the request fails, so the sheet always opens at once. Each field is `{key, label, kind, choices, default, help, group: basic|advanced, danger, when}`: `basic` ones are on the sheet, `advanced` ones sit under *More options*, `when` shows a field only while another is set (`{"launcher": ["resume", "continue"]}` = whichever of those is chosen; `{"worktree": true}`; `{"repo.devcontainer": true}`), and the one `danger` field is the bypass switch.
- **Claude** (the defaults are `opus`, effort `high` and permission mode `auto`: Claude's own mode that runs with its safety checks, issue #83): *Start* (new, `--resume` with an optional id, `--continue`, `--from-pr` with a number or URL), name, model (`opus`, `fable`, `sonnet`, `haiku` first; then `opusplan`, Opus while planning and Sonnet for execution, and `best`, labelled *strongest available (may be Fable)* because it can bill as Fable; any full id after them. There is no `[1m]` entry any more: the Claude Code docs (read 2026-10-07) say the suffix has no effect on Opus 5.5 and Sonnet 5.5, which have the 1M window natively. A typed or remembered `opus[1m]` still works as a custom id, and the custom-id help says the suffix only matters for models without a 1M window by default, such as Opus 4.6 and Sonnet 4.6), effort, fast, permission mode (*auto (default)*, *ask*, *accept edits*, *plan*, *don't ask* and, in a session only, bypass), first prompt. Under *More options*: allowed and disallowed tools, `--tools`, text appended to the system prompt, `--agent`, `--fallback-model` (up to three), the *Subagent model* and its *Force* switch (see *Subagent model* below), `--autocompact` (`auto` or a number), a new worktree (with a name), *fork instead of continuing* (`--fork-session`, only for resume and continue), `--add-dir` (the repo's siblings are pre-checked, other projects' repos can be added), the devcontainer (only when the repo has one), an MCP config file and extra arguments. Claude does not restore `--mcp-config`, `--fallback-model`, `--add-dir` and the others on a resume, so the board stores them with the session and passes them again on recovery.
- **Codex**: *Start* (new, resume by id **or name**, continue = `resume --last`, and *fork* where this Codex has `codex fork`), name (the board's own label: Codex has no `--name`), model (the catalogue of `codex debug models`, cached for an hour; the box's visible slugs until it has been read), reasoning (the levels each model accepts, the others are disabled), and **one mode picker**, a segmented control that opens on *auto* (the automatic approval review where this Codex has `--approve-for-me`; a Codex without it runs `auto` exactly as *default*: `-s workspace-write -a on-request`, never wider): *default* (`-s workspace-write -a on-request`), *auto*, *read-only*, *bypass* and *custom* (which shows a sandbox and an approval select). Under *More options*: web search, `--add-dir`, a managed worktree, `-c key=value` lines, a profile, the scrollback switch and extra arguments. **Config lines** must match `^[A-Za-z0-9_.]+=.+$`, at most 20 lines of 400 characters, and the server refuses the keys the launcher owns or that would loosen the sandbox (`model`, `model_reasoning_effort`, `sandbox*`, `approval*`, `profile(s)`, `hooks`, `features.hooks…`, `notify`, `mcp_servers`, `model_providers`, base URLs and logins, `projects`, any bypass or yolo spelling); everything else goes to Codex as `-c`.
- **`--fallback-model` and `codex fork` in an interactive session (issue #92; box check 2026-10-09, Claude Code 2.1.294, codex-cli 0.161.0).** Both work in an interactive session. Claude accepts `--fallback-model` and the TUI starts, up to 3 fallback models (a fourth gets a 400 from the server, and the sheet says "Up to 3 fallback models."); whether it really switches on an overload could not be provoked, so that part is not verified. `codex fork <thread id>` prints "Thread forked from ..." and keeps the old transcript, but the model and the reasoning level are not carried over (choose them again), and the board binds the new thread id only after the first prompt (before that, the prompt route answers `not_ready`). The command preview equals the server's `cmd` token by token for Claude (new, resume, fork, continue, from a PR) and for Codex (new, fork, resume, continue); a `--from-pr` launch with a real PR was not tried. These are results for those two versions only.
- **Shell**: a name, and the devcontainer when the repo has one.
- **The default permission mode is `auto`** (the owner's call in issue #83). A session, task, dispatch, schedule or batch the form is not told otherwise about starts with Claude's `auto` (Codex: `auto`, see above), shown as *auto (default): Claude's safety checks*. *Ask* is one tap away and sends no flag, as before. A choice you made (a saved per-repo or project default, a preset, a card's own mode, an issue's model line) wins; only the fallback changed. A Claude Code too old to start in `auto` (below 2.1.283) opens on *ask* instead of failing. Schedules and batches that exist keep the mode they were stored with; the API default for `permission_mode` on `POST /jobs` and `POST /api/batch` is `auto`, while `POST /api/tasks` and the sessions route still pass no flag when the caller names none (Claude's own settings decide). Bypass is never a default anywhere, and a request from another node still never carries `auto`, bypass or `dontAsk`.
- **Presets** are chips above the fields: *opus high worktree* and *ultracode* for Claude, plus the ones you save per repo.
- **Defaults are remembered per repo and agent** on the device (`ccboard:launch:<project>/<repo>:<agent>`; the old `ccboard:launch:<project>/<repo>` is read once as Claude's; `ccboard:agent:<project>/<repo>` is the agent used last, `ccboard:defaults:<project>` a project-wide default, `ccboard:task:<project>/<repo>:<agent>` the task form's).
- **The danger gate.** Bypass is allowed **only inside the repo's devcontainer** (owner decision on #104). The *bypass* choice of Claude's permission select is enabled while *Run in the devcontainer* is on (under Advanced, in a repo that has one); while it is off the option is disabled and reads "bypass: only inside the devcontainer", and unticking the devcontainer under a chosen bypass switches the mode to *auto* with a note. A saved default, a preset or a remembered form that holds a bypass without the devcontainer also falls back to *auto*, with the same note. Codex has no bypass choice at all: no *bypass* mode and no `danger-full-access` sandbox. Choosing *bypass* shows the red warning and turns *Start & open* off until you tick *I understand*. The tick is asked **once per repo** (`ccboard:bypass-ack:<project>/<repo>`), not on every launch, and the sheet then sends `mode: "bypass"` with `bypass: true` and `devcontainer: true`. The gate is never offered for a task, a dispatch or a schedule, and the server refuses it there too: tasks, dispatch and headless runs take no `mode` at all and reject every spelling of bypass (`bypassPermissions`, `danger-full-access`, any `bypass`/`yolo` option or extra argument).
- **The command preview** is a read-only monospace line under the fields with a *Copy* button. It is approximate (it is built in the browser from the same flags); the `cmd` the server answers with after *Start & open* is the truth and replaces it. It is held to the route by one list of cases read by both suites (`tests/fixtures/launcher_cases.json`), including Codex launches on a Codex whose `--help` has `--no-daemon`: every Codex line (new, resume, continue, fork) starts `codex [resume|fork] --no-daemon --no-alt-screen …` there, in the preview as well as in `cmd` (the preview lacked `--no-daemon` until box check #92).
- **The account** a new session will run on is shown in the footer (Claude: the current account; Codex: the current Codex account) with the window left. When it is at 85 % or more and another saved account has more room, a quiet *Switch first* button switches (the same switch as Settings) and repaints.
- **Task mode** adds a title, the prompt, *from a GitHub issue*, *Run now · Later · Schedule* and *Close when finished*; it never offers bypass.

**`POST /api/projects/<project>/repos/<repo>/sessions`** takes the sheet's words and builds the flags itself; the UI never sends raw flags. `launcher` is `new` (or `claude`), `resume`, `continue`, `from_pr`, `fork` (Codex), `shell`, or the older `codex`, `codex-resume`, `codex-continue`, `codex-fork`; `agent` (`claude`, `codex`, `shell`) turns a plain launcher into that agent's. The body:

| Field | Meaning |
|---|---|
| `name`, `resume_id` | the session name (blank: the next free `s1`, `s2`…); a UUID for Claude, a UUID **or a session name** for Codex |
| `mode` | `default`, `auto`, `read-only`, `bypass`, `custom` (Codex's picker); Claude reads it as its permission mode (`default` = `manual`, `read-only` = `plan`, `bypass` = `bypassPermissions`, or a Claude mode by its own name) |
| `permission_mode`, `model`, `effort`, `allowed_tools`, `disallowed_tools`, `append_system_prompt`, `args`, `add_dirs`, `devcontainer`, `bypass`, `opts` | the flat fields the API always took, unchanged |
| `reasoning` | Codex's reasoning effort (Claude reads it as `effort` when none is sent) |
| `prompt` | the first message of a new session (8000 characters at most; longer ones are a task) |
| `worktree`, `worktree_name` | `true` (or the name itself) starts in a new worktree: Claude with `--worktree <name>`, Codex with a worktree the board creates (`git worktree add -b worktree-<slug> .ccboard/worktrees/<slug>`, `.worktreeinclude` copied in, taken away again if the launch fails). The name defaults to the session name |
| `from_pr`, `fork_session` | Claude `--from-pr <n or URL>` (also what `launcher: from_pr` means); `--fork-session` on a resume or continue (Codex: a resume by id becomes `codex fork`) |
| `fallback_model`, `autocompact`, `tools`, `agent_name`, `mcp_config` | Claude `--fallback-model`, `--autocompact`, `--tools`, `--agent`, `--mcp-config` (a file under the projects folder or the Claude config folder) |
| `config`, `sandbox`, `approval`, `search` | Codex `-c key=value` lines (a list or one text), `-s`, `-a`, `--search` |
| `fast` | Claude fast mode: there is no CLI flag, so the route only records it with the session's options; the launcher sheet sends `/fast on` through `POST /api/sessions/<tmux>/command` once the session is at its prompt, after `/effort ultracode on` when both are ticked (the Fast switch of Tune sends `/fast on` or `/fast off` later). The board never sends a bare `/fast`: on Claude Code 2.1.290 it opens a dialog that swallows keys, and `/fast on` is refused on an account without usage credits |
| `cwd_rel` | start in that folder of the repo (relative, no `..`, an existing directory; not with a worktree or the devcontainer) |

The answer is `{tmux, attach_url, agent, agent_session_id, claude_session_id, cmd}`. A Claude-only field sent to Codex is refused by name (`tools: not supported by codex`), and the other way round. **Bypass:** only for Claude with `devcontainer: true` in a repo that has `.devcontainer/devcontainer.json`. There `mode: "bypass"` needs `bypass: true` beside it (the acknowledgement of the gate above), and the spellings that existed before (`permission_mode: "bypassPermissions"`, `mode: "bypassPermissions"`, `--dangerously-skip-permissions` or `--permission-mode bypassPermissions` in `args`, a resume or continue with a bypass mode) build the same line, never stored for resume, and need the same `bypass: true`: without it the answer is a **400** `bypass skips every approval: send bypass: true with the acknowledgement`. Every other request is a **400** with `bypass is allowed only inside the repo's devcontainer (owner decision, #104); choose auto or turn on Run in the devcontainer` for host Claude, and `Codex sessions never run with bypass or danger-full-access (owner decision, #104); choose auto` for any Codex session (`mode: "bypass"`, `bypass: true`, `sandbox: "danger-full-access"`, `--dangerously-bypass-approvals-and-sandbox`, `--yolo`, `-s danger-full-access`), in any launch kind (new, resume, continue, from a pull request, fork). Sessions already running on the host in bypass are not touched; only new launches are refused. Tasks, dispatch and headless runs refuse bypass as before.

**Ultracode.** `--effort ultracode` is accepted only where the box's `claude` takes it: its `--help` names it on the `--effort` option (read once per binary), or `CCBOARD_CLAUDE_ULTRACODE_FLAG=1` records that `claude --effort ultracode -p 'say ok'` worked on the box (`0` records that it did not). Then `ultracode` is one of the efforts of `GET /api/agents` and of the launch request; until then it is not, and the *ultracode* preset starts the session and sends `/effort ultracode on` through `POST /api/sessions/<tmux>/command` once the session is at its prompt. `GET /api/agents` shows which one this box is on as `claude.capabilities.ultracode_flag`.

Ultracode is a setting, not an effort level (v0.5.21, #78): it plans a workflow for each substantive task at any effort. There are three routes: `claude --effort ultracode` at launch (it sets `xhigh` and turns ultracode on; the box check V19 saw it work on 2.1.290 although `--help` lists only low..max, and the launcher preview says so), `/effort ultracode on` and `/effort ultracode off` typed into a running session (session only; the level stays; Claude Code 2.1.284 or newer), and the word `ultracode` typed into one prompt, which starts a workflow for that prompt only (the palette's Modes row inserts it). Tune's Ultracode switch sends the on and off commands through `POST /api/sessions/<name>/tune` and reads the pane's "Ultracode on" or "Ultracode off" line back; no statusline field carries the state, so the switch says "unknown" until the board has read it once. Ultracode has no effect under `-p`, so a scheduled or headless run refuses it.

**Subagent model (issue #106).** *More options > Subagent model* sets `CLAUDE_CODE_SUBAGENT_MODEL` for the subagents (and teammates and workflow agents) the session starts after launch: `inherit` (the main model, the default), `haiku`, `sonnet`, `opus` or a full model id. The board puts it in front of the launch line, `env CLAUDE_CODE_SUBAGENT_MODEL=haiku claude ...`, only when the choice is not `inherit`, and the preview shows the same line. A subagent that names its own model, or a definition with a `model`, still gets that one. The board-wide default is `CCBOARD_SUBAGENT_MODEL` (shown in Settings > Box > Claude defaults, empty = `inherit`); it applies to sessions, tasks and scheduled or batch `claude -p` runs, and the launcher's field overrides it per launch (an explicit `inherit` too). The choice is stored with the session and typed again by recovery after a reboot, because Claude does not restore the variable on `--resume`; a session launched without it is not given a default that was set later. It is remembered per repo like the model. *Force the subagent model* additionally sets `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (Claude Code 2.1.257 or newer): every subagent then uses that one model and **overrides definitions that ask for a stronger one**. It is a separate tick, off by default, never remembered and never implied by a model choice or the board default. The board does not write `~/.claude/settings.json`; the manual alternative is an `env` entry there. Unverified here: that a subagent really ran on the chosen model (that needs a real session; read it from the transcript or the statusline), and the board shows no readout of it.

**Unattended Claude runs (issues #107 and #108).** A schedule or batch job runs `claude -p` with nobody to answer a prompt.

- **Permission prompts.** Where this box's `claude --help` lists `--permission-prompts` with a `none` choice (2.1.259 and newer; the box's 2.1.293 does, its text reads "nobody: anything that would prompt is denied automatically"), every headless argv carries `--permission-prompts none`, so a tool that is not pre-approved is denied at once instead of waiting. The help is read once per binary (`claude.capabilities.permission_prompts_none` in `GET /api/agents`). Where it is not listed, the argv is unchanged and Settings > Doctor > *Unattended Claude runs* warns that a run may stall on a prompt. The permission mode still decides everything else (a job given none runs with `auto`; `dontAsk` plus *Allowed tools* is the safest unattended pair). `--permission-prompt-tool`, `--settings` and anything with `bypass` stay refused in the extra arguments, and no headless path has a bypass. Measured on the box (Claude Code 2.1.294, Haiku 5.5, a scratch repo, 2026-10-09): a run never stalls on a tool it may not use; the tool is denied and the model carries on (4 turns and 14 s plain, 2 turns and 9 s with `--permission-prompts none`), and the run exits 0 with `is_error: false` and `subtype: success`, the denials only in the JSON `permission_denials`. A refused tool does not by itself fail a run, because a model often probes a tool it does not need (a memory plugin's MCP tool) and then answers: a run that produced a usable result stays **ok** and its run line carries the warning (`denied 1 tool call: mcp__...`). It is recorded with the status **denied** when it did not: an empty result, or denials together with an answer that says it could not go on. A denied run's line says `denied 3 tool calls: Bash, Write`, the job's *last* status reads *denied* and the task card's title carries the same note: nothing may have been done, so it must not read as success. A pre-approved rule matches the exact command: the model's compound `a && b` is not matched by `Bash(a *)`, so rules are matched per command and the model may combine commands.
- **Allowed tools.** The schedule and batch forms (Claude only) take *Allowed tools*: rules as the CLI reads them (`Bash(git diff *)`, `Read`), comma separated, at most 20, no shell metacharacters; they are passed as `--allowedTools`.
- **`--bare` is refused.** The box's help says it skips hooks (the board's state source), plugin sync, auto-memory (so claude-mem's observer), keychain reads and CLAUDE.md discovery, and that Anthropic auth is then strictly `ANTHROPIC_API_KEY` or an `apiKeyHelper`, never the subscription login the board runs on; on a claude.ai-signed-in box the run exits 1 in a second with "Not logged in". A schedule or batch with `--bare` in its arguments is a 400 that says so, unless the board's own environment has `ANTHROPIC_API_KEY` (an `apiKeyHelper` in the Claude settings is opaque to the board and does not count). A job stored earlier with `--bare` runs without it.
- **A job with no schedule.** A job with no cron and `run_now: false` is parked (`next_run_at` empty, shown *parked: Run now*) and runs only when *Run now* asks; the forms send `run_now: true` for the one-off preset, as before. The batch route still runs its jobs at once.
- **Fable.** The docs say `claude -p` never asks before billing Fable usage credits, so a schedule or batch job whose model text resolves to Fable (`--model fable`, `best`, any id containing `fable`, a `--fallback-model` that does, or the id `ANTHROPIC_DEFAULT_FABLE_MODEL` remaps it to) is refused with a 422 unless the request carries `acknowledge_fable: true` **and** a `max_budget_usd` of at most `CCBOARD_HEADLESS_FABLE_CAP` (default 25). The forms show the unticked checkbox *This run bills Fable usage credits without asking* directly above the button, and Max $ becomes required, as soon as the model text resolves to Fable. The acknowledgement is per job: it is stored on the job with its time, cap and models, never remembered with the form, and goes stale when the model text or the cap changes. A Fable job already stored without it is **held**, not run under a cap of ours (a cap is not consent): the schedule row says so, Settings > Doctor > *Fable jobs waiting* lists it, and the row's *Acknowledge Fable* button (`POST /api/jobs/<id>/acknowledge-fable`) records the acknowledgement and Max $. Max $ is Claude Code's own client-side estimate: it counts subagent spend, and it is not a billing ceiling set by the provider. Interactive sessions, tasks and chain steps are unaffected (Claude can ask there); a model that is the box's settings default, not named in the arguments, is not detected.

## What v0.1 does

- **Sessions.** Unlimited, all concurrent, one tmux session each, always started *inside a repo*. Launchers: `claude` (new session with a board-minted `--session-id`), `claude --resume`, `claude --continue`, and a plain `shell`. Extra CLI args are passed through. **One session can edit several repos:** the launch form pre-checks the sibling repos of the same project and passes them as `--add-dir`.
- **Attach** from the browser through ttyd, **kill** from the board.

## What v0.4 adds: autonomy & fleet

- **Devcontainer**: repos with `.devcontainer/devcontainer.json` can run sessions inside the container. Bypass permissions is allowed **only inside the repo's devcontainer** (owner decision on #104, v0.5.62): an interactive Claude session started with *Run in the devcontainer* may choose it, with the acknowledgement; on the host, for Codex, and for tasks, scheduled and batch runs it is refused; and settings overrides in extra args (`--settings`, `--setting-sources`, `--permission-prompt`) are rejected everywhere.

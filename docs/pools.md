# Runtime profiles (P1)

For the owner enabling isolated Claude and Codex accounts on one node. In this page, "the box" means the machine that runs the board.

[Back to the documentation index](README.md)

`CCBOARD_POOLS` is off by default. Set it to `1`, `true` or `on` and restart the board to enable account isolation on the box. With it off, launches and Settings behave as before; the additive database migrations create empty pool metadata tables and default legacy columns; they never migrate credentials at startup.

Migration runs only when the owner chooses **Migrate saved logins** in Settings > Accounts (`POST /api/pools/migrate`). Startup never migrates. The live legacy login is skipped: switch the legacy login to another account first. Each other saved slot hands over its credential files as opaque bytes into `<data dir>/profiles/<provider>/<account_id>`. Each file is written atomically and fsynced before the slot file is removed. The slot retains only a marker naming its pool account. A rerun repairs interrupted moves and missing database rows; conflicting or missing credentials are reported per slot without guessing.

A handed-over slot cannot be switched to, overwritten, forgotten, merged, restored or logged into again through the legacy switcher, even with pools off. Its row says which pool account owns it. Migration returns per-slot `moved`, `skipped` or `error` results; slot conflicts are JSON 400/409 responses; database failures return JSON 500 and can be retried.

To roll back: **turn pools on, release each account, then turn pools off**. The two-step **Release** button calls `POST /api/pools/accounts/{id}/release`. Release and launch reserve the account under the same lock. Release is refused with 409 while that account has an open attempt; the response names its tmux sessions. If tmux liveness cannot be checked, Release and legacy switching return JSON 503 and leave the attempts open. It moves the profile's current credential files back to the original slot, removes the marker and account row, and leaves the profile directory without credentials.

`GET /api/pools/accounts` lists id, provider, label, state and a credential fingerprint. Settings shows the same accounts above “Legacy: subscription accounts”. Supply an `account_id` from that list to a task, session or scheduled job request to bind its process. An unbound launch is unchanged. There is no account picker in the launcher yet. When the switch is off, these routes return 404 and account bindings are refused with 400.

Each profile has private settings and credentials, with mode 0700 on its directories. Claude profiles reuse ccboard's hook template. Their `projects` links point through `_shared/claude/projects` to the configured global Claude projects folder. Codex profiles install the same ccboard hooks as the global home and pin the file credential store; their `sessions` links point through `_shared/codex/sessions` to the configured Codex sessions folder. Codex shares `CODEX_SQLITE_HOME` and resumes only by thread UUID. Transcript readers keep using the same directories. The global transcript root must already exist; a launch refuses a missing root instead of creating global directories. Validation alone creates nothing.

Codex hook trust is **per profile**. Under the default `CCBOARD_CODEX_HOOK_TRUST=review`, ccboard installs hooks but does not grant trust automatically, just as for the global `CODEX_HOME` (`scripts/codex_hooks.py trust-help`). A global trust record does not authorize a different profile's hooks file. After migration, for **each Codex pool account**:

1. On the box, run `CODEX_HOME='<data dir>/profiles/codex/<account_id>' codex`, replacing the placeholders with that profile's absolute path from the data directory and its pool account id.
2. Accept Codex's hook review prompt, or type `/hooks`. Review and trust every ccboard entry (commands containing `ccboard-hook`, `ccboard-hook-fast` or `ccboard-permission`).
3. Codex writes the trust records into that profile's `config.toml`, under `[hooks.state."<absolute profile path>/hooks.json:<event>:<group>:<index>"]` with `trusted_hash`. Do not copy the global records: the key includes the hooks file path and position and the hash covers its definition.
4. Start a bound session from the board and send a prompt; check that its state follows the turn. Review again if Codex reports modified hooks after a checkout move or hook definition change.

An owner who already chose `CCBOARD_CODEX_HOOK_TRUST=bypass` keeps that existing launch behavior for profiles too; it also bypasses review of repository hooks. Creating or preparing a profile preserves its existing `config.toml` and any owner-reviewed trust records.

The agent command scrubs inherited authentication and profile variables after the login shell's startup files have run. Headless launches receive an explicit child environment. Each bound process gets a runtime attempt, which records its provider conversation id and closes when the process ends. On exit, the board updates a SHA-256 credential fingerprint (16 hexadecimal characters), without returning credential contents. If hooks have not supplied a conversation id, discovery checks only this working directory’s Claude project folder or today’s Codex sessions folder, once a second for at most ten seconds. Before launch, it snapshots transcript names, inodes and sizes. Existing files stay excluded even if they are edited; new files must have an mtime at or after the attempt began. This works without filesystem birth times. Multiple matching files leave the id unset. An existing session id is never overwritten by this fallback. The legacy switch endpoints return 409 while an attempt is open. SessionEnd during `/clear` or `/resume` does not close an attempt: the session row must end or the pane monitor must observe the agent exit to its shell (recorded as `agent_exited`). Startup and switch guards reconcile attempts whose session ended or whose tmux session or run disappeared. Bound sessions keep their pool account attribution and are skipped by “continue after switch”.

On macOS, Claude file-login profiles are refused with “the Mac Keychain adapter comes in P5”. A separately provisioned setup-token profile may keep its opaque token in `.setup-token` as a regular file owned by the user with mode 0600 and nonempty UTF-8 content; the process wrapper reads it into its own environment without putting it in a command or API response. All Claude profile paths are canonical absolute paths. Codex file profiles work independently of the Mac Keychain.

This phase covers local processes only. Profile launches in a devcontainer are refused because the host's private paths are not mounted there. Ranking, rotation, drain, grants, vaults, account selection UI and multi-node bindings come later. The owner's two-login spike is still needed to verify provider behavior with real accounts.


## Usage (P2)

With `CCBOARD_POOLS=1`, accounts on one subscription share one quota group. Claude uses the organization and account identity pair; Codex uses only `tokens.account_id` from `auth.json`; no JWT is decoded. P0 names no non-JWT user-id field, so two logins of one team workspace may share a group even when they belong to different seats. Settings labels a Codex group containing two or more pool accounts “shared workspace?”; a permitted seat identity would be needed to distinguish them. Only a SHA-256 prefix is stored. Missing identity stays isolated to the profile. An unreadable or unsafe identity file marks the group unknown with a reason and logs at most once per account per hour; other accounts continue collecting. No raw subscription identity is returned. The two-login spike is still needed to verify workspace behavior.

The collector reads every available free local source and chooses the highest effective confidence after age decay, breaking ties by source preference. Every source uses the same freshness multiplier: 1.0 for the first 30 seconds, falling linearly to 0.5 at ten minutes (and toward zero thereafter). The table lists base confidence; saved confidence includes this multiplier. Active sources run only if no member of the group has a free reading; estimates run only if the group has no real reading.

| Provider | Source | Confidence |
|---|---|---|
| Claude | The profile's own `.claude.json` usage cache, using the existing parser | 1.0 |
| Claude | Statusline rate limits from a session bound to that attempt | 0.95 at the session’s last activity time; 0.8 if activity time is unavailable |
| Claude | `/usage` in an idle, unattached bound pane, followed by a newly refreshed cache | 0.9 |
| Claude | Transcript token deltas and a coarse plan budget | 0.4 |
| Codex | Recent rollout rate limits, attributed to the launch attempt, never the rollout creator | 0.8 |
| Codex | CLI app-server `account/rateLimits/read` inside the scrubbed profile environment, only for a ready account with no open attempt, at least one previous attempt, and no free group reading | 0.85 |
| Codex | Transcript token deltas and a coarse plan budget | 0.4 |

There is no direct authenticated endpoint call in P2. Claude's endpoint needs a live access token and its refresh chain belongs to the CLI; a competing refresh can invalidate that chain (P0 findings 2 and 3). `/usage` and the Codex app-server leave authentication to the CLI. The collector never reads or refreshes an access or refresh token. Estimates need a known plan and measured deltas within the attempt; missing evidence produces no invented percentage. Claude plan metadata comes from the migrated account record, not extra profile identity fields.

Free local reads run every 60 seconds for a group with an open attempt, every five minutes otherwise, and are marked due immediately when an attempt starts. Launch only marks the schedule and wakes the worker; it does no usage I/O. Active requests are at most once per five minutes per profile. Failures back off by two, four and eight minutes, capped at ten, and lower the kept reading's confidence by 0.1 per miss. The five-minute request floor still applies to the two- and four-minute backoff stages. History is retained for 14 days, pruned at most hourly. Orphan groups are removed; closed attempts lose their statusline cache and released accounts lose refresh metadata. Attempts are limited to open attempts plus those ended within the seven-day estimate window, capped at 128 per account (open attempts first). Each estimate also excludes attempts outside its own window. Rollout paths use a shared directory index (at most 8,192 entries per scan, once per five minutes), then a bounded per-attempt cache; only tails are read. Claude transcripts use cached byte offsets and bounded incremental reads, retaining incomplete final lines for the next poll. Legacy Codex exclusion uses session-id set lookups and only open attempts or attempts ended within seven days. Re-reading an unchanged cache or rollout preserves its original timestamp. Statusline redraws retain the session’s last activity time when available. A window whose reset time has passed is discarded. Without a reset timestamp, a window expires five hours or seven days after its sample, according to its own length. Only ready profiles are collected. Sampling marks a cancellable flag under the per-account lock, then releases that lock before subprocesses or file parsing. A launch waits at most one second for sampling, then cancels it and proceeds; app-server kills its entire process group on cancellation, completion or timeout and always reaps the child. Busy accounts are skipped for the current tick. A failed group is marked unknown with a reason while the others continue; a failed identity pass backs off instead of spinning. Automatic `/usage` skips drafts, rechecks viewers and command guards before typing, and sends Escape only to its own recognised Usage panel with no viewer attached. It confirms the empty prompt has returned; failure records a one-hour pause on further automatic typing into that profile. Other dialogs are left alone and recorded as failures; the composer is never cleared.

**Unknown** means there is no reading within five minutes, or confidence is below 0.5. Missing windows stay null; no scheduler, strip or peer read substitutes zero or fifty. The strip uses the worse of the five-hour and weekly windows; a weekly-only figure is usable. Pills name the accounts, show which window is limiting when weekly is worse, and retain keyboard focus across polls. Unknown groups are hatched with the sample age. A failed lazy load retries after one, five, then fifteen minutes and toasts once. Tap a group for its two windows, source and confidence. Settings > Pool accounts shows the group's figures. Estimates remain unknown even when recent. The coarse plan table uses a five-hour token budget and seven such blocks for the weekly estimate; these are approximations, not provider limits.

`GET /api/pools/usage` returns groups with account ids, both windows and resets, age, source, confidence and nodes. `/api/state` always includes `pools`: null when off, otherwise `{enabled: true, groups: [...]}`. There is no pool account grant model in P2, so pool groups and their hashes/headroom are neither sent to nor accepted from peers. The hub shows only the node's own groups until P5. Nothing sums across groups or providers.

With pools off, no collector starts, no usage rows are written and no active request runs. With pools on but no accounts, no collector starts either. Pool migration starts collection when it creates the first account.

## Assignment (P3)

The v0.5.116 backend adds local account assignment. Launcher controls arrive in the same version's second half. All of this remains behind `CCBOARD_POOLS`; `state.pools` stays null when off, and gains only a compact `pools: [{id, provider, name}]` list when on.

Task, session and scheduled-job requests accept `account_mode`: `legacy` (the default, today's behavior), `pinned` with `pinned_account_id`, or `pool` with `pool_id`. P1's explicit `account_id` still works. Pool launches pick an account once and reserve its runtime attempt before starting a process. The assignment explanation is stored on that attempt. A failed preparation or launch closes the reservation. Selection and reservation share P1's account serialization with Release; the assignment lock covers only database selection and insertion, never process, tmux, or usage-probe I/O.

Eligibility is checked in this order:

1. The account and pool must match the requested provider.
2. The account must be `ready`; `needs_login`, releasing and missing accounts cannot run.
3. The target must be this node (`node: "local"`, or omitted). Other targets are refused with “pool accounts run on this node until account grants (P5)”. Profiles are local private directories; being paired with a node does not grant it an account. Peer launch bodies still refuse every account field.
4. Both known usage windows must be below their soft thresholds. P2's `account_headroom` supplies the readings; stale or incomplete readings count as unknown, never as zero. Known percentages above soft still refuse even in a partially unknown reading.
5. Open attempts on this account must be below its concurrency cap. Accounts sharing a quota group share usage, but have separate concurrency caps.
6. A requested model must satisfy any explicit account `allowed_models` metadata. The repo has global model catalogs but no authoritative per-plan entitlements: absent account metadata, the reason says “model availability unknown (known restrictions only)”. No model is substituted.
7. A subscription launch must use a subscription account. The additive `pool_account.billing_class` defaults to `subscription`; any other class is excluded. Neither this field nor `allowed_models` contains credential material or appears on the new public surfaces. They are internal metadata seams for future provisioners, not credentials inferred from profile files.

Among known eligible accounts, ranking is lowest `max(5 h percentage, weekly percentage)`, then earliest next reset, then least recently assigned (`runtime_attempt.started_at`), then account id. Unknown accounts are considered only when no known account passes all eligibility checks; they rank by least recently assigned and id, and say “usage unknown”. Refusals name every candidate, both percentages, its exclusion reason, and reset times, with the earliest reset first. Times in explanations are UTC.

Defaults live together in `app/config.py`: soft **70% / 80%**, hard **85% / 92%** (5 hours / weekly), and **2 open attempts per account**. Pools override all thresholds and concurrency; members override soft thresholds and concurrency. Soft cannot exceed hard. `on_limit_policy` is `auto` in pool mode and `wait` in pinned mode, with an explicit request overriding the pool policy. Both policies are recorded now; automatic continuation, rotation and hard-limit handling wait for P4. Exceeding soft refuses a new launch in this phase, even when every candidate is above soft. Pool resumes also wait for P4. No new environment variables or Settings registry entries are needed.

Person-only CRUD (CSRF on writes): `GET /api/pools`, `POST /api/pools`, `PATCH /api/pools/{id}`, `DELETE /api/pools/{id}`, and `PUT` / `DELETE /api/pools/{id}/members/{account_id}`. A pool is created with `id`, `provider`, and an optional `name`; thresholds are optional. The member PUT body contains optional soft thresholds and concurrency. Membership is a `pool_member` join row, never a JSON array. IDs use P1's validator. Cross-provider membership is refused with both providers named. Deleting a pool returns 409 while an open attempt, or its task, references it. These routes return 404 with pools off.

`POST /api/launch/dry-run` accepts the task or session create body, with `project` and `repo` in the body (session bodies include `launcher`). It returns `will_start_as` (provider, account id and label, node and reason), `refused_reason`, and sanitized `candidates` (account id, label, both percentages, resets, state, eligibility and exclusion reason). It performs no write, executable/version probe, credential read, profile preparation or tmux call. It checks assignment and local request constraints, not live CLI availability. A launch rechecks and reserves against current state, so intervening launches may change the answer. With pools off it always returns 200 and `{will_start_as: null, refused_reason: null, candidates: []}`. Pool selection and dry-run never enable bypass, change repository access, model, sandbox, permission mode or billing class.

# Runtime profiles (P1)

For the owner enabling isolated Claude and Codex accounts on one node. In this page, "the box" means the machine that runs the board.

[Back to the documentation index](README.md)

`CCBOARD_POOLS` is off by default. Set it to `1`, `true` or `on` and restart the board to enable account isolation on the box. With it off, launches and Settings behave as before; the database migration only creates two empty tables, `pool_account` and `runtime_attempt`.

Migration runs only when the owner chooses **Migrate saved logins** in Settings > Accounts (`POST /api/pools/migrate`). Startup never migrates. The live legacy login is skipped: switch the legacy login to another account first. Each other saved slot hands over its credential files as opaque bytes into `<data dir>/profiles/<provider>/<account_id>`. Each file is written atomically and fsynced before the slot file is removed. The slot retains only a marker naming its pool account. A rerun repairs interrupted moves and missing database rows; conflicting or missing credentials are reported per slot without guessing.

A handed-over slot cannot be switched to, overwritten, forgotten, merged, restored or logged into again through the legacy switcher, even with pools off. Its row says which pool account owns it. Migration returns per-slot `moved`, `skipped` or `error` results; slot conflicts are JSON 400/409 responses; database failures return JSON 500 and can be retried.

To roll back: **turn pools on, release each account, then turn pools off**. The two-step **Release** button calls `POST /api/pools/accounts/{id}/release`. Release and launch reserve the account under the same lock. Release is refused with 409 while that account has an open attempt; the response names its tmux sessions. If tmux liveness cannot be checked, Release and legacy switching return JSON 503 and leave the attempts open. It moves the profile's current credential files back to the original slot, removes the marker and account row, and leaves the profile directory without credentials.

`GET /api/pools/accounts` lists id, provider, label, state and a credential fingerprint. Settings shows the same accounts above “Legacy: subscription accounts”. Supply an `account_id` from that list to a task, session or scheduled job request to bind its process. An unbound launch is unchanged. There is no account picker in the launcher yet. When the switch is off, these routes return 404 and account bindings are refused with 400.

Each profile has private settings and credentials, with mode 0700 on its directories. Claude profiles reuse ccboard's hook template. Their `projects` links point through `_shared/claude/projects` to the configured global Claude projects folder. Codex profiles install the same ccboard hooks as the global home and pin the file credential store; their `sessions` links point through `_shared/codex/sessions` to the configured Codex sessions folder. Codex shares `CODEX_SQLITE_HOME` and resumes only by thread UUID. Transcript readers keep using the same directories. The global transcript root must already exist; a launch refuses a missing root instead of creating global directories. Validation alone creates nothing.

Codex hook trust is **per profile**. Under the default `CCBOARD_CODEX_HOOK_TRUST=review`, ccboard installs hooks but does not grant trust automatically, just as for the global `CODEX_HOME` (`scripts/codex_hooks.py trust-help`). A global trust record does not authorize a different profile's hooks file. After migration, for **each Codex pool account**:

1. On the box, run `CODEX_HOME='<data dir>/profiles/codex/<account_id>' codex`, replacing the placeholders with that profile's absolute path from the data directory and its pool account id.
2. Accept Codex's hook review prompt, or type `/hooks`. Review and trust every ccboard entry (commands containing `ccboard-hook`, `ccboard-hook-fast` or `ccboard-permission`).
3. Codex writes the trust records into that profile's `config.toml`, under `[hooks.state."<absolute profile path>/hooks.json:<event>:<group>:<index>"]` with `trusted_hash`. Do not copy the global records: the key includes the hooks file path and position and the hash covers its definition.
4. Start a bound session from the board and send a prompt; check that its state follows the turn. Review again if Codex reports modified hooks after a checkout move or hook definition change.

An owner who already chose `CCBOARD_CODEX_HOOK_TRUST=bypass` keeps that existing launch behavior for profiles too; it also bypasses review of repository hooks. Creating or preparing a profile preserves its existing `config.toml` and any owner-reviewed trust records.

The agent command scrubs inherited authentication and profile variables after the login shell's startup files have run. Headless launches receive an explicit child environment. Each bound process gets a runtime attempt, which records its provider conversation id and closes when the process ends. On exit, the board updates a SHA-256 credential fingerprint (16 hexadecimal characters), without returning credential contents. If hooks have not supplied a conversation id, discovery checks only this working directory’s Claude project folder or today’s Codex sessions folder, once a second for at most ten seconds. Before launch, it snapshots transcript names, inodes and sizes. Existing files stay excluded even if they are edited; new files must have an mtime at or after the attempt began. This works without filesystem birth times. Multiple matching files leave the id unset. An existing session id is never overwritten by this fallback. The legacy switch endpoints return 409 while an attempt is open. SessionEnd during `/clear` or `/resume` does not close an attempt: the session row must end or the pane monitor must observe the agent exit to its shell (recorded as `agent_exited`). Startup and switch guards reconcile attempts whose session ended or whose tmux session or run disappeared. Bound sessions keep their pool account attribution and are skipped by “continue after switch”.

On macOS, Claude file-login profiles are refused with “the Mac Keychain adapter comes in P5”. A separately provisioned setup-token profile may keep its opaque token in `.setup-token` as a regular file owned by the user with mode 0600 and nonempty UTF-8 content; the process wrapper reads it into its own environment without putting it in a command or API response. All Claude profile paths are canonical absolute paths. Codex file profiles work independently of the Mac Keychain.

This phase covers local processes only. Profile launches in a devcontainer are refused because the host's private paths are not mounted there. Usage, pools, ranking, rotation, drain, grants, vaults, account selection UI and multi-node bindings come later. The owner's two-login spike is still needed to verify provider behavior with real accounts.

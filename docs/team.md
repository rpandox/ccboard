# Team

For people who share a repository with teammates.

[Back to the documentation index](README.md)

In this page, "the box" means the machine that runs the board.

## Teammates in a shared repository

These four parts show what teammates do in a shared repository, read from GitHub. They are not part of the [nodes feature](nodes/overview.md#several-devices-nodes): a teammate never gets a node, a scope or a token.

### Team: who is working on what

For each repository you switch on, the board shows who else is working in it, using only what GitHub already shows: issues assigned to a person, branches linked to those issues or pushed in the last 14 days, and open or draft pull requests (a teammate's pull request from their own fork is listed under the shared repository). A teammate does not need ccboard. **Reading is read only, and opt-in per repository.** This is the decision of #196 (2026-10-10): still one board per person and no shared control, with presence of teammates as the one addition. Writing your own status is a separate switch, off by default: see [Publish my status](#team-publish-my-status).

- **What is read.** Through the box's own `gh`, as the login `gh` is signed in as, and only for a repository that is both one of this board's own projects (its `origin` or `upstream` remote) and switched on: open issues that have an assignee, one page (100) of the open issues that have none (for the free list below), open pull requests with their author, draft flag, head branch and head repository, the `ccboard:in-progress` claim comments of #148 (read side only, absent is fine), and, in one GraphQL query per repository, the branches linked to issues, the issues a pull request closes and the recent branch tips with their author. No `git fetch`: your checkout is never touched. A peer, a GitHub answer or a request can never choose which repository is read.
- **What reading never writes.** Nothing. Reading creates or changes no comment, label, assignee, branch or issue, and nothing about your own sessions leaves the box unless you also switch on **Publish my status** (below): no prompt, reply, path, host name or terminal text. The one thing on the wire that is not a plain GET is the GraphQL query, which `gh` sends as a POST and which only reads (`app/github.py` builds it from one fixed query, with the owner and name checked first); `tests/test_security_surface.py` keeps every other `gh` command a GET.
- **Opt-in, off by default.** Each repository has a switch, **Shared with my team**, on the project page (the **Team** tab) and in **Settings > Team**. With nothing switched on the board starts no thread, makes no `gh` call, writes no row and adds no key to `/api/state`. Switching a repository off removes its read, its schedule and its stored record.
- **Who is who.** A person is the GitHub user id GitHub reports, shown as the login. The board's own login is read from `gh api user` (cached 10 minutes), is on the node card as `owner_login` and `owner_id`, and is marked **you** in the block. `null` means "not known yet", never "nobody". Settings > Doctor has two rows: **GitHub login of this board** and **Team GitHub access**. Logins, repository names and branch names go through GitHub's own name rules before they name anything; titles, branch names and logins are text written by other people and are cut, stripped of control and bidi characters and drawn as text only.
- **The words.** *Assigned*, *Linked branch*, *Pushed branch*, *Draft PR* and *Open PR* are different words with different glyphs, not only different colours. A repository is always in one state: not shared, reading for the first time, read, **authorise this token for the organization** (GitHub's single sign-on said no), **no access**, not found, waiting for GitHub (rate limit), few requests left, `gh` not logged in, `gh` missing or could not be read. An access problem, a rate limit or an old read is shown as its own state and never as "no teammates"; data from an earlier read stays on screen, marked with its age. The block has no button: its only actions are **Open on GitHub** links, built from a validated owner, repository and number.
- **What a token needs.** A classic token needs the `repo` scope. A fine-grained token needs read access to Issues, Pull requests and Contents on the repository, with the organization opted in. An organization with SAML single sign-on also needs the token authorised for it; the Doctor tells that apart from "no access".
- **Cost.** The 5,000 requests an hour belong to the login and are shared with everything else it does. The team poll is last in line: one thread, one call at a time at least 1.5 seconds apart, at most **600 points an hour for all shared repositories together**, every interval 2 times longer under 3,000 requests left and 4 times longer under 1,500, nothing at all under 300 until the limit resets, and it waits while the epic reader is backing off. A repository GitHub refuses (single sign-on, no access, not found) is tried again every 10 minutes. Issues and pull requests are read as conditional requests (an ETag; `gh` exits 1 and prints `gh: HTTP 304`, which is read as "not modified" and any other failure stays an error) every 120 seconds, the GraphQL query every 600 seconds, earlier (but not closer than 150 seconds to the last one) when the issue or pull request list changed.

  Measured with the test fake over one hour of virtual time, two people and three branches per repository, counting every 304 as a full point:

  | Shared repositories | Points an hour | Of which GraphQL | Issues and pull requests read every |
  | --- | --- | --- | --- |
  | 1 | 67 | 6 | 120 s |
  | 5 | 335 | 30 | 120 s |
  | 20 | 600 (the cap) | 60 | about 277 s |

  If a 304 costs nothing the same hour would spend 9, 45 and 120 points. **UNVERIFIED:** whether a 304 is free (one sample, and `gh api rate_limit` lagged), and the real `gh` 2.87 output of a 304. They stay unverified until the two-login check on a real private organization repository.
- **Routes.** `GET /api/team/state` (a weak ETag), `PUT /api/team/repos/<owner>/<repo>` `{shared}` and `POST /api/team/refresh`, on the board's own origin and for a signed-in person only: the hook token, an MCP token and a node or device token are refused, and none of them is in `NODE_ROUTES`. Another board never sees your team view.
- **`repo_slug`.** Every session and task row of `GET /api/node/state` carries `repo_slug`, the lower-cased `github.com/<owner>/<name>`, taken from the `upstream` remote when there is one (a fork reports its parent) and otherwise `origin`; a renamed repository or a fork without an `upstream` remote is resolved once the repository is shared and GitHub has said so. A non-GitHub remote, the project folder and a session outside a repository have `null`. No key was removed and the 100 KB cap holds.
- **The demo.** `?demo=1` shows `example/website` shared with `alice` (you) and `bob`, and two repositories that are off: open `#/p/phasezero?tab=team` and `#/settings?sec=team`. `&team=loading|empty|alone|sso|forbidden|notfound|rate|low|stale|nologin|nogh|error|pending|cut|off|hostile` shows each state without a server; the switches work for the life of the page.
- **Not done.** The two-login check on a real private organization repository (a real 304, single sign-on, forks) has not been run; the GraphQL query (`linkedBranches`, `closingIssuesReferences`, `refs`) has only run against the test fake; the hub view of a paired node does not carry its `owner_login` or `repo_slug` yet; and presence on GitHub alone is inferred, not announced: a teammate who works without an assigned issue, a pushed branch or a pull request is visible only if their board publishes a status (next section). Warnings in the launcher, a sidebar group and notifications are later phases of #196.

### Team: publish my status

A board can tell the teammates of a shared repository what its owner works on right now: which issue, which pushed branch, which agent, in what state and since when. It is **opt-in per repository, off by default, and separate from the read switch** of Team P1. A teammate whose board reads this repository sees it as a **live line** under your name in the Team block of the project page. A teammate without ccboard can read the comment on GitHub itself. Nothing is exchanged board to board.

- **Where.** One issue per repository, titled `ccboard team presence`, with the label `ccboard:presence`. It is made on the first opt-in if it is not there, and found by its label afterwards. Each person has **one comment** on it, edited in place, and **one line in it per board** of that person (the node alias and the first 8 characters of the node hash), so two boards of one login keep two lines and neither removes the other's. The first line of the comment is `<!-- ccboard:presence v1 -->`. The issue is filtered out of the launcher's issue picker.
- **What is published.** A fixed list of keys, pinned by a test (a key added without changing the list fails it): `node`, `nid`, `repo`, `seq` (a sequence number), `at` (the board's time), `lease` (30 minutes), `state` (`running`, `needs_you`, `idle` or `ended`), `agent`, `since` (to the minute), `last` (last activity, rounded down to 15 minutes), and, for a session that belongs to a task, `issue`, `phase` and `branch`. A session you started by hand has no title and no issue link, so it publishes an agent, a state and a time only. One line holds one work item: the session that needs you, else a running one, else an idle one, else an ended one.
- **What is never published.** A title, prompt, reply, result, transcript, terminal text, environment value, token, account label, e-mail address, usage, cost, host name, tailnet name, path or folder name, and anything outside the shared repository. Every value must match its own pattern, so free text cannot get in.
- **Branches.** A branch name is published only in a repository GitHub says is **private**, and only when GitHub already has the branch (it has a pull request, the team read saw it, or GitHub says it exists). A branch that exists only on your box never appears. A **public** repository publishes no branch at all.
- **When it writes.** When the line changes (a state change), and a heartbeat every 10 to 15 minutes (jittered per repository) so that teammates can tell you are still there; a line is stale after 30 minutes. Nothing is written when nothing changed and no heartbeat is due. A state change is written at most once in 90 seconds per repository (a flapping state is written once, as it is by then), and not at all once a quarter of the hourly budget is left: that part is for heartbeats, and the change goes out with the next one. The body changes only when the state changes (and the heartbeat, which changes only `seq` and `at`), because GitHub keeps the edit history of a comment.
- **Edit history.** GitHub keeps every earlier body of a comment and anyone who can read the repository can open it **while the comment exists**. That is why the list above holds from the first write. The opt-in text in Settings says so. **UNVERIFIED:** what is left after the comment is deleted, and whether an organization's own settings keep a copy; this has not been checked on a scratch repository (it needs the real GitHub). Some organizations forbid tools writing to their issues; the opt-in text says that too.
- **Who it is.** The person is the owner of the comment on GitHub (its numeric user id and login, a user and not an app), not a name in the text. A line is shown only if the comment starts with the marker, was written by an owner, member or collaborator, and was **last edited by its owner** (checked with GraphQL `editor`; if GitHub will not say, the edited lines are left out and the block says so). The reader caps pages, comments and the size of a body before any pattern runs, strips control and bidi characters, and shows the text as plain text only. It never reaches a prompt, a shell or an address.
- **Live, idle, stale, gone.** Measured on GitHub's clock (the `Date` header of the answer, also on a 304), never this machine's. **Live** means the sequence number moved between two reads and the line is younger than its 30 minute lease; **idle** is the same with no session running or waiting for a person (a heartbeat with no activity); **not confirmed yet** is a first sighting (the number has not been seen to move, so it is not live); **stale** is older than the lease and says "last seen 2 h ago"; **gone** is older than 24 hours and is hidden, not removed; **unknown** is no clock from GitHub (not live). A comment that was touched without a new sequence number does not make a line live. The page also makes a line stale by itself once it has outlived the lease since the last read, and never the other way round. Every word has a glyph (`●` `◐` `◌` `!` `?`), and the board's own session words (`✽ Running`, `✻ Needs you`, `∙ Idle`, `○ Ended`) are kept.
- **The controls (Settings > Team > Publish my status).** A **Publish my status** switch for each repository of your projects that has a GitHub remote; **Private** for each repository where publishing is on (take my line down and stop writing there, keep the switch); one **Pause team presence** for the whole board; **What I published**, the literal last body per repository, as text; the opt-in text; the writes spent this hour; and the last few publishing events. Pause and Private stop the heartbeat and delete this board's own line within one turn of the publisher (about a minute); switching a repository off does the same. When the board starts it takes down its own lines in repositories that are now off or gone. The comment is deleted when its last line is taken out.
- **Public repositories.** A repository GitHub says is private publishes after one switch. A **public** repository, or one GitHub has not said is private yet (it has to be read first, or the publisher's own check has to have run), needs a **second confirm**, a box that lists exactly what becomes public (your GitHub login, the issue number, the state and agent of your session, when it started and when you were last active to 15 minutes) and shows the line as it would be written, with no branch. The confirm is remembered in the row and asked again after the switch has been off. The Doctor row **Team presence published** warns, naming each public repository that publishes.
- **Why a status can be blocked, in words.** Each has its own state in Settings and a next step: **Issues are off**, **Archived**, **Issue locked**, **Issue closed** (the board stops and says so), **Issue deleted**, **Cannot open issues** (no right to create the status issue), **Cannot add the label** (that needs triage rights), **GitHub refused**, **Interaction limits**, **Waiting for GitHub** (a rate limit), **Hourly budget spent**, **Could not write**. Paused, Private, Needs your confirm, Waiting for gh, Taking my line down, Publishing and Not published are the other states.
- **Writes and budget.** Every write goes through the one serial write queue of #148 (1.1 seconds apart, 30 a minute, back off on 403 and 429), with its allow list extended by exactly these shapes: create the status issue (the fixed title, body and label only), create the one label, and create, edit and delete the board's own comment (the body must be a canonical presence body). An epic request can never create an issue, and a presence request can never carry a claim body. The epic switch `CCBOARD_EPIC_WRITES` does **not** govern presence, and presence does not need it: with the publish switch off, the pause on or Private, no command is built at all. Only the board's own comment is ever edited or deleted: before each edit the thread is read again and the comment must be there, written by this board's own login, start with the marker and (to delete) hold this board's own line; a comment id from the database or from GitHub alone is never enough. A write whose outcome is unknown is never sent again: the next turn reads the thread first, and a record saved before the first comment lets Off and Pause find a line whose answer was lost. A thread of more than 300 comments is not read in part: the board writes nothing there, cannot take its line down either, and says `too_long`. A refusal by GitHub (403, 422, interaction limits) is looked at again after 15 minutes, a 5xx or a timeout after 2. A budget of **240 presence writes an hour per GitHub login** covers all repositories and all of the person's boards (a board learns how many boards share a login from the person's own comment in that repository; two boards that publish to different repositories each assume the full 240, at worst 480, still under GitHub's 500 an hour for content, but with no room left for epic writes). Heartbeats may use 75 % of a board's share and stretch to at most 25 minutes under pressure.

  Measured with the test fake over hours 2 and 3 of a virtual run, two boards of one login, private repositories, steady state:

  | Repositories that publish | Presence writes an hour | Presence reads an hour |
  | --- | --- | --- |
  | 1 | 9 | 54 |
  | 5 | 51 | 306 |
  | 20 | 177 | 1062 |

  The reads are, before each write, the repository (asked again so a repository that turned public is noticed), the list of status issues (so two boards that made one each meet on the lowest) and the thread twice (the second just before the write, so a line a sibling board added meanwhile is kept); all are conditional, and a `304` costs no request budget. When a sibling board changed the comment there is also a GraphQL editor check (spent from the separate GraphQL limit; one more call by node id for a comment older than the last 50). With 20 repositories a heartbeat stretches to about 13.3 minutes. The team read of Team P1 grows with the presence comments: 97, 485 and 600 points an hour for 1, 5 and 20 shared repositories (before: 67, 335 and 600; the cap of 600 still holds).
- **Setting up.** Nothing to install. The status issue needs the right to open issues in the repository, and the label needs triage rights. A fine-grained token should need read and write access to Issues; a classic token needs the `repo` scope (UNVERIFIED against real GitHub). If the login lacks either right, the state says which.
- **Routes.** `GET /api/team/presence`, `PUT /api/team/presence` `{paused}` and `PUT /api/team/presence/<owner>/<repo>` `{publish, private, confirm_public}` (409 with `needs_confirm`, the list and the line when a confirm is due), on the board's own origin, for a signed-in person only and with CSRF: the hook token, an MCP token and a node or device token are refused, none is in `NODE_ROUTES`, and a repository that is not one of this board's projects is a 404. The routes write nothing to GitHub themselves; the publisher does, on its next turn. Choices are recorded in the board's audit log (`presence_on`, `presence_off`, `presence_pause`, `presence_resume`, `presence_private`, `presence_unprivate`, `presence_issue`, `presence_label`, `presence_publish`, `presence_delete`, `presence_blocked`) with no login, body or comment text.
- **Off means off.** With no repository switched on and no earlier line to take down, the board starts no thread, makes no request, writes no row and adds no key to `/api/state`. The settings are stored as `team:publish:<key>` (exists only while on), `team:presence-pause` and `team:presrec:<key>` (the last body and its ids) in the `kv` table; there is no migration.
- **The demo.** `?demo=1` shows `example/website` publishing as `alice` with `bob` live on two boards: open `#/p/phasezero?tab=team` and `#/settings?sec=team`. `&team=lineneeds|lineended|lineunconfirmed|linestale|lineunknown|linegone|linenone|lineclosed|lineerror|linecut` shows each live word and what the board found of the status issue; `&presence=off|paused|private|confirm|waiting|removing|issuesoff|archived|locked|closed|deleted|nocreate|nolabel|forbidden|limited|ratelimit|toolong|budget|error` shows each publishing state. In the demo `example/ccboard` is public and `example/api` is not known to be private, so switching either on opens the second confirm; the switches work for the life of the page.
- **Not done.** The two-login check on a real private organization repository (a real comment, a real GraphQL `editor`, an organization that limits interactions), what survives a comment delete, whether a comment edit counts as a content-creating request for GitHub's secondary limit, and the screenshots at 1280, 1024 and 390 pixels are not done (the test fake stands in for GitHub). A sidebar group and notifications are later phases of #196 (the warnings in the launcher are in [Conflict warnings](#team-conflict-warnings)). Presence is advice: it never blocks a dispatch and never claims an issue.

### Team: conflict warnings

Before you start work a teammate already holds, the board says so. It is a warning with the person's name and, where GitHub or a live status line gives one, since when. It is **advice only**: a warning never disables a button, never blocks a start and never claims anything, and **nothing is written to GitHub** for it (no assignee, no label, no comment). Start is the same button, with or without a warning.

- **What warns.** *The same issue*: a teammate has it assigned, has a live status line naming it, has a branch linked to it, holds a live claim on it (#148), or has an open or draft pull request that closes it. Two signs from one person are one warning; two people are two. *The same branch*: the branch your task would get (`worktree-` and the slug of its title) is already on GitHub under a teammate, pushed, linked to an issue or the head of their pull request (a fork's branch, the default branch and the `ccboard-backup/` branches are not counted; one older than 14 days says so). *The same files*: an open or draft pull request of a teammate changes files that one of your own open tasks also changes.
- **Where.** In the launcher's issue picker a row carries a chip in glyph and words: `! taken by @bob`, `◌ @bob, seen 7 min ago` or `◌ @bob, last seen 3 h ago`. Above Start, in the task form, one line per person: `! #212 is being worked on by @bob since 14:10`, with what lies behind it (assigned, live status, branch, pull request) in small type, and `! Branch worktree-fix-login is already on GitHub under @bob`. When you start a task that exists already, the same block names its files: `! PR #158 by @bob (draft) also changes 3 of these files` with the first six names and a count. The project page's Team block marks a teammate's row that collides with one of your open tasks: `! Collides: same issue as your task “…”`.
- **Words, not colour.** Taken, seen lately and stale are different words and glyphs in the warn colour, never the red of an error. `since` appears only when a live status line gave it (GitHub gives no time for an assignment); a stale line says how long ago it was last seen on GitHub's clock; a gone line claims nothing, and a line whose age GitHub did not give says it was not seen lately. A login GitHub text could not vouch for is shown as "a teammate", never `@null`. The id is what identifies a person, so two boards of your own login never warn each other.
- **Quiet notes, never a gate.** When "no warning" could mean "not known", one dim line says so: GitHub is being read for the first time, the last read failed (the warnings are from the read before, and how old it is), the read is old, the board does not know who you are on GitHub, or (when you start a task) some pull requests have no file list yet, so file overlap is not fully checked. The form is whole in every state and Start is never disabled by a warning.
- **Where it comes from.** `GET /api/team/state` carries `warnings` on each shared repository's block (null when it is not shared or not read yet): by issue number, by branch name and by your local task id. The launcher reads that cached view with one `GET` to the board when the sheet opens and asks GitHub for nothing; the words are in the lazy `team` bundle (first paint is unchanged, 537,564 bytes of script). `GET /api/state` carries `team: {shared: true}` while a repository is shared, so a board that shares nothing makes **no team call at all** and the sheet is what it was. No route was added and none is in `NODE_ROUTES`.
- **The changed files of pull requests.** The one new read is `GET /repos/<owner>/<repo>/pulls/<n>/files`, through the same read-only reader, its allow list (this one shape, nothing near it), its conditional requests and the shared back-off. It reads only a teammate's open or draft pull requests whose author can write to the repository (owner, member or collaborator, and not a bot: anybody can open a pull request on a public repository), the 12 most recently updated, at most 3 pages a cycle and 2 pages (200 names) for one, again when the pull request was updated or after 30 minutes. A pull request with 3,000 files is cut and said so. These reads have their own cap of 100 points an hour inside the 600 of the team poll, and they stop when fewer than 100 of the 600 would be left for the other reads. A page is kept as file names only (the patch text is dropped before it is cached), and one pull request whose files fail to read is marked unknown for 30 minutes while the next ones are read. Measured with the test fake (7 open pull requests per repository, 6 with files): 111, 555 and 601 points an hour for 1, 5 and 20 shared repositories, against 99, 495 and 599 before; at 20 repositories the file reads take the capped 100 and the other reads stretch a little. The free-issue read of Team P4 (one conditional request per repository every 10 minutes, so 6 an hour at most) moves the same fake to 117, 580 and 599 points an hour. A 304 is counted as a point here, as everywhere in the poll.
- **Your files stay yours.** The files of a task come from the diff of its worktree on this box (cached a minute) and are compared with a pull request's list only on the board, for a repository where a teammate's file lists were read. They are shown to the signed-in person who owns the board and are never published; file lists are not part of presence.
- **Untrusted text.** Logins, titles, branch names and file paths are cut before any pattern runs, stripped of control and bidi characters and set as text, never as markup, never into a shell, a prompt or an agent; a link exists only for a validated `https://github.com/<owner>/<repo>/(issues|pull)/<n>` or `/tree/<branch>` address.
- **Off means off.** With no repository shared nothing new runs: no read, no thread, no key in `/api/state`, no team call from the launcher.
- **The demo.** `?demo=1`: open the launcher (`+`, then task) on `phasezero/website` and open the issue list: #152 and #154 are taken by `@bob` (every kind of sign), #156 was seen lately, #160 is stale (`last seen 3 h ago`), #162 is held by "a teammate" and #164 by two people; pick #154 for the branch line, and start the backlog task "Add alt text to the product gallery images" from Tasks for the files lines. `#/p/phasezero?tab=team` shows the three kinds of mark on `bob`'s rows. `&team=warnnone|warnnoid|warnempty|warnfiles|loading|rate|stale|sso|off` change what is known (nothing worked out, who you are not known, no warnings, a cut file list, and the quiet notes of the other states).
- **Not done.** The two-login check on a real private organization repository, a real changed-files list with its `Link` pagination, and whether GitHub counts a 304 are UNVERIFIED (the in-process fake stands in). A path git quotes (non-ASCII) will not match GitHub's name. The task-create form has no task yet, so its file warning is by task: starting an existing task shows it, creating one shows the issue and the branch. Screenshots at 1280, 1024 and 390 pixels are not taken. A sidebar group and notifications are later phases of #196.

### Working with a team

One place to see the whole team across every repository you share, and the check that the feature works between two real people. Everything here is **read only**: a teammate never gets a control, a scope or a token, and nothing on these screens changes anyone's work. With no repository shared, none of it exists: no sidebar group, no Home line, no palette row, no request, no key in `/api/state` beyond `team: {shared: true}` while a repository is shared.

- **Where.** `#/team` (the page), a collapsed **Team** group in the sidebar below **Other nodes** with the number of teammates who are live (open it for who and where; it sits behind a label of its own, so it is never read as a project or a node), one quiet line on Home (`● 3 teammates active in 2 repos`, or `! Team: 1 repo could not be read. See why`, or `∙ Team: reading GitHub for the first time`; nothing when it has nothing to say) and, in the command palette, **Team** and **Team: owner/repo** for each shared repository (that opens its Team block on the project page).
- **The page.** Rows grouped by **person** or by **repo** (a segmented control), each row with its state in a glyph and words (`✽ Working`, `✻ Waiting`, `∙ Idle`, `◌ Not confirmed yet`, `! Stale`, `○ Ended`, `? Unknown`, `◦ On GitHub`), what it is (issue, pull request or branch, as links to GitHub), the repo or the person, the branch, the agent, since, last seen or last change, and how old the read is. Filters for person, repo and state; the address carries them (`#/team?by=repo&person=…&state=working`). A repository that cannot be read shows its words and its one next step above the rows, and its rows are stale: an old or failed read is never "no teammates". Your own rows come first.
- **Free issues.** For each shared repository: the open issues nobody holds (no assignee, no live status, no linked branch, no claim, no pull request that closes it). **Free is never guessed.** The board reads one page (100) of the open issues that have no assignee, `GET /repos/<owner>/<repo>/issues?state=open&assignee=none&per_page=100&page=1` (one more allowed shape of the read-only reader, nothing near it), as a conditional request at most every 10 minutes per repository, after the repository's own read worked, inside the 600 points an hour and only while at least 100 of them are left for the other reads. Only the number, title, label names and date are kept (never the body), and pull requests are left out. When that page is full the list says it may be longer. Until the first read, after a failed read, or when the list is more than an hour old, the board says `unread` or `unknown`, names the numbers that are held and does not list anything as free; the same goes for an old, failed or cut repository read, a cut presence thread, a link read that did not cover every assigned issue or open pull request (30 of each), or a holder check that is not known (`unknown`, in words). A presence line with no clock from GitHub holds its issue. **Limit:** an unassigned issue with a linked branch and no status line can show as free, because linked branches are read only for assigned issues. A list shows on a live board and in the demo (`?demo=1&team=freeok`).
- **What is read.** Nothing new in this phase. The page is built from the cached team view (`GET /api/team/state`, which gains `overview` and, on each shared repository's block, `free`); it asks GitHub for nothing. What the board reads for the team is what [Team P1](#team-who-is-working-on-what) and [P3](#team-conflict-warnings) already read, in the repositories you switched on.
- **What is published.** Nothing, unless you switched on **Publish my status** for a repository ([Team P2](#team-publish-my-status)): one line of your own in one comment, with the issue, the pushed branch (private repositories only), the agent, the state, since when and the last activity to 15 minutes. This phase publishes nothing more.
- **How to switch it off.** For one repository: turn **Shared with my team** off in **Settings > Team** or on the project page (the board stops reading it and its rows leave every screen). To stop publishing: **Publish my status** off, **Private** for one repository, or **Pause team presence** for all. With nothing shared the board starts no thread, makes no request and writes no row.
- **What stays private.** Prompts, replies, transcripts, terminal text, environment values, account labels, host names, paths, the file lists of your tasks (compared on the board, never published) and branches you never pushed. Nothing of that is ever read from a teammate or shown from one either.
- **Notifications: off until you switch them on.** **Settings > Notifications** gets a sixth switch, **A teammate started on an issue I hold**, listed only while a repository is shared. It is off by default and pull stays the rule: nothing is sent unless you turn it on, and then only through the channels you already set up (ntfy and Web Push). It fires only on a change between two reads (a teammate starts on an issue you hold: assigned to you, a live claim of yours, a branch of yours linked to it, a pull request of yours that closes it, your own status line or one of your open tasks), once per person and issue, never for your own logins or boards, never for a pull request of somebody who may not write to the repository, never on the first read after a start, a gap of an hour or a switch off and on, and at most five a read; a read that lost part of the picture (presence comments that could not be read or were cut, editors not checked, a cut list) moves nothing, so the next good read is not taken for new starts. An app assigned to an issue is not a teammate. Only a signed-in person can switch it on: the hook token and a node or device token get 403 for that change. The text holds the person's login, the issue number and your repository's name, and no title or text from GitHub. A tap opens `#/team`.
- **Limits.** Presence is advice: someone with write access can edit another person's line, and GitHub's comment object does not say who edited it. A public repository's presence is readable by everyone. The 5,000 points an hour of the GitHub login are shared with everything else it does (the team reads are capped at 600 an hour, publishing at 240). The page shows at most 600 rows; free issues are not listed until the first page of open issues is read, and an issue closed in the last 10 minutes can still show as free. A teammate who has nothing on GitHub (no assigned issue, no branch, no pull request, no live status) is not visible. Nothing here is board-to-board, and that stays a separate decision.
- **The two-login check (an owner action; it has not been run).** Every claim about a second person's permissions comes from GitHub's documentation until this is done, and one login cannot test it. Use a **private repository in an organization** with two real GitHub logins that can write to it (A is you, B is a second person or a second account), each with a board whose `gh` is logged in as that login and that has the repository as a project. If the organization uses single sign-on or restricts third-party apps, authorise each token for it first and note what GitHub asks for. Then, writing down what you see and how long it took:
  1. **Read.** Both boards switch **Shared with my team** on. A assigns an issue to B; B pushes a branch linked to it and opens a draft pull request that closes it. Does A's board show B's issue, branch and pull request, and B's show A's? Note the state words and how long until each appears.
  2. **Presence both ways.** Both boards switch **Publish my status** on (the second confirm must not appear for a private repository). Does each see the other's live line within one poll? Stop B's board: when does the line turn stale (30 minutes) and gone (24 hours)? Then **Pause** and **Private** on one board: the line must go from the other board; open the comment on GitHub and note what is left of the earlier text (edit history).
  3. **Warnings.** On A, open the launcher's issue picker: the issue B holds must show `! taken by @B`, and a task that touches the files of B's pull request must show the files line. Check that the owner's own second board never warns.
  4. **A fork contributor.** A third login that can read but not write opens a pull request from a fork: it must show under the shared repository, and it must not make an issue `taken`.
  5. **Single sign-on and app approval.** If the organization has either: before authorising, the repository must show `Authorise the token` or `No access`; after, it must read. Note the exact wording GitHub gives.
  6. **A read-only collaborator.** Add a login with read access only and note what its board can read (the presence issue) and cannot write.

  9. **The notification.** On A, switch **A teammate started on an issue I hold** on; B starts on an issue A holds: exactly one notice must arrive through ntfy and Web Push, a second start on the same issue none, and with the switch off none.

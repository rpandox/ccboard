# Several devices: overview

For people who run more than one board and want them to work together.

[Back to the documentation index](../README.md)

## Several devices (nodes)

A **node** is a board with its own sessions, tasks, agents and data. Any board becomes a **hub** for the nodes paired with it: it reads their trimmed state and relays the actions their scopes allow. Each keeps working when the hub is gone.

Start in **Settings > Nodes**: Refresh finds candidates; create a code on the other board, choose its scopes, then **Add node** here. **Both ways** also lets the other board call this one with `read` and `tasks`. The panel holds discovery, incoming and outgoing pairs, token and signing-key rotation, Device check, Worker and Activity. Discovery grants no access. See [pairing](pairing.md#pairing-two-boards-issue-135-phase-p3) and the [scopes table](../security.md#node-scopes-and-routes).

Pick a node in the launcher to [start work there](hub-and-relay.md#starting-work-on-another-node-issue-141-phase-p8). A remote session's peek has [Reply, keys and permission answers](hub-and-relay.md#steering-a-session-on-another-node-issue-142-phase-p9). **Open terminal** opens that node's own page; quad and dock tiles are [read-only tails with a separate prompt box](hub-and-relay.md#remote-terminals-and-tiles-issue-144-phase-p10). Devices without ccboard have a separate [SSH start, read and stop flow](device-check.md#devices-without-a-board).

**Tasks > Epics** has [labels and pins](epics.md#epics-issue-147-phase-p12), [Run and Pause](epics.md#routing-an-epic-to-a-node-issues-150-and-152-phase-p15), and [report, auto_pr and close settings](epics.md#working-an-epic-issue-issue-149-phase-p14). Read the [unattended worker warning](epics.md#the-epic-worker-issue-157-phase-p17) before enabling it. Each node [pushes its own notifications](../guide/notifications.md#notifications-across-nodes-issue-151); the hub merges the inbox, while the app badge counts only the board that last drew it. [MCP across nodes](agents-and-mcp.md#using-nodes-from-an-agent-issue-152-phase-p10) is off by default. Use the [platform table](platforms.md#several-devices-issue-154-phase-p6), [failure table](epics.md#when-something-goes-wrong-issue-153-phase-p16) and [settings table](../configuration.md#settings) for setup and fixes.

Sources and limits: the [epic's evidence table](https://github.com/rpandox/ccboard/issues/131) records the design sources; the [two-node check](https://github.com/rpandox/ccboard/issues/155) records partial device results, including remote tasks, permission answers and a three-issue epic. Phone terminals, sleep and wake, notification delivery, idle cost and remote MCP remain **to verify** there. The details below describe shipped code, not a claim that every device check passed.

### Nodes: identity, the node card and names (issues #131, #133, #137; phase P1)

A board is one **node** on the tailnet. Its stable identity survives restarts. Pairing enables the hub poller; the separate epic worker can run without a hub when explicitly enabled.

- **Node id.** `<data dir>/node-id` (0600, written once, atomically). The first read saves `ts:<StableNodeID>` when `tailscale status --json` answers (`Self.ID`), otherwise `n_` and 16 random hex characters. It is never taken from the host name and the board never changes it. If the file says `ts:X` and Tailscale later reports a different `Self.ID` (the device was registered again) the file wins and Settings > Doctor warns: reset the node id (remove the `node-id` file and restart the board); every pair must be made again afterwards. A board that starts before Tailscale is up keeps a random `n_` id.
- **Node key.** `<data dir>/node-key` (0600) holds the private Ed25519 seed. It is excluded from backup, like `node-id`; a restore without it needs every pair made again. `node-key-rotation.json` holds only public rotation proofs. See [Node signing keys](pairing.md#node-signing-keys).
- **Name.** `CCBOARD_NODE_NAME`, else the short MagicDNS name, else `hostname -s`, cut to letters, digits, `-` and `_` (41 characters at most). The name can change; the id cannot.
- **`GET /api/node/hello`** needs no login and answers exactly `{"app":"ccboard","api":1,"node_id":"…"}`: no version, no name. It is limited to 30 a minute per source address (`429` with `Retry-After`). Behind `tailscale serve` the connection comes from loopback and the caller's tailnet address is in `X-Forwarded-For`; the header is believed only on a loopback connection. Other routes have distinct credentials: see the [closed node route table](../security.md#node-scopes-and-routes). The legacy `GET /api/node/summary` also takes `CCBOARD_HUB_TOKEN`, and nothing else does.
- **`GET /api/node`** (a person's login or a pair with `read`) is the node card: `app`, `api`, `node_id`, `name`, `url` (`CCBOARD_PUBLIC_URL`, else built from the MagicDNS name, else null), `version`, `os`, `runtime`, `now` (this node's UTC time, for clock skew), `agents` (installed, version, logged in, hooks, a login problem flag), `accounts` (`supported`, and per account its label, whether it is current, `subscription_key`, its 5-hour window and whether it is limited), `lanes` (`cap`, `running`, `free`), `load`, `sessions` (`live`, `working`, `needs_you`), `capabilities` and `tailscale` (`dns_name`, `tags`, `user_owned`). A part that cannot be read is `null`, never `0` and never an error: a Mac has no `/proc`, so its load fields are null, and `accounts.supported` is false where saved logins do not work. The card holds no secret, prompt, e-mail address or path, and the credentials files are never opened (account windows come from the board's own records). `state.node` is the same card without `agents` and `accounts`, plus `handle: "local"`; `state.node_name` and `GET /api/node/summary` are unchanged.
- **`subscription_key`** is the first 12 hex characters of a SHA-256 over the provider's account id (Claude: the account uuid; Codex: the account id), null when the board holds none. Two nodes logged in to one subscription show the same key, so a rate-limit window can be counted once. Which stored field is the same on two devices is to verify in the two-node check (#155).
- **Lanes.** A lane is a running task that owns a session of its own (a worktree or in-place task; a prompt handed to a running session is not one). `free` is `CCBOARD_NODE_LANES` minus the running lanes, never below 0, null when the limit is 0. A hand start over the limit still starts; the answer of `POST /api/tasks/{id}/dispatch` then carries `lane_warning: {cap, running}`.
- **Names of things on a node (issue #137).** A *handle* is `^[a-z0-9][a-z0-9-]{0,30}$` (`local` is the board in front of you and is never written into a URL or a ref). A session ref is `<handle>/<tmux name>` (`box/shop--api--t-fix`), a task ref `<handle>:<id>` (`box:42`); the hash forms are `#/n/<handle>`, `#/n/<handle>/s/<tmux>` and `#/n/<handle>/t/<id>`. Local items keep `#/s/<tmux>`, `#/t/<id>`, the notification link and the old `#s=<tmux>` link unchanged, and tmux, ttyd and hook names never change: the handle is added around them. `app/nodes.py` `parse_ref` refuses `..`, a slash inside the tmux part, an uppercase or over-long handle, `local/…`, a task id that is not 1 to 12 digits and a tmux part that is not a ccboard session name; `tests/fixtures/node_refs.json` is the table the JavaScript helper `Ref.parse` (`app/static/nodes.js`) is held to as well. Addresses use the handle, not the name, so a peer renaming itself breaks no bookmark; the node id is the true key in the registry.
- **`tasks.origin`** (`TEXT`, null) is added by a forward-only migration: the board that asked for the task, as JSON `{node, user}`, null for work asked for here. It never holds a token or a prompt and is not part of `state.tasks`.
- `?demo=1` reads `app/static/demo/node.json` for the card and `state.json` carries `node`.

#### Finding other nodes (issue #134; phase P2)

`GET /api/nodes/discover` lists the devices on your tailnet that could be nodes and asks each one whether ccboard answers. It gives a device no access: pairing does. Nothing runs on a timer: no request leaves the board until a person opens the Nodes panel or presses Refresh, and a board with no Tailscale (or none that is signed in) answers `{"tailscale": {"ok": false, "reason": "…"}, "rows": []}` with status 200 and sends nothing.

- **Which devices.** The same Tailscale user's devices, plus any device whose tags include one of `CCBOARD_NODE_TAGS` (default `tag:ccboard`). Never this device, never a device without a MagicDNS name, never a device shared in from another user (a name outside your tailnet's MagicDNS suffix, or one Tailscale marks as shared, is dropped even when it carries the tag: any tailnet may use `tag:ccboard`). A tagged device has no user, so on a tagged board only the tag rule applies. Rows are keyed by the Tailscale id, because two devices can share a host name.
- **What a probe is.** `GET /api/node/hello` over https, on each of `CCBOARD_NODE_PORTS` in turn, 2 seconds each, at most 4 probes at a time, with no header of our own (no login, no token). The name must be under your tailnet's MagicDNS suffix (or an address in `100.64.0.0/10` or `fd7a:115c:a1e0::/48`), with no user info, query or fragment, and it must resolve only to such addresses. It is resolved once and the connection goes to that address while the certificate is checked for the name, so a second DNS answer cannot redirect it. Redirects are refused. An offline device is never probed. Only the hello's three keys (`app`, `api`, `node_id`) are read. An address typed as an IP fails the certificate check (the certificate is for the MagicDNS name), which shows as `no_tls`.
- **The answer.** Per device: `name`, `dns_name`, `os`, `online`, `last_seen`, `owner` (`user` or `tag`), `tags`, and the probe result `state` with `url`, `node_id`, `at`, `age` and `stale`. `state` is `found` (ccboard answered), `refuses` (401 or 403: something answers and does not let us in), `no_ccboard` (connection refused, or an answer that is not a ccboard hello), `no_tls` (the handshake failed: HTTPS is not enabled for the tailnet, or the port is not HTTPS), `unreachable` (a timeout, a redirect, a name that does not resolve), `offline` (Tailscale says the device is not connected; `last_seen` is shown), `invalid` (the name fails the address rule) or `unchecked` (nobody has asked yet). "Online" means the device is on the tailnet, not that ccboard answers. The answer holds no address.
- **Cache.** Results are kept in the `node_discovery` kv record with their time. A result older than 30 seconds is marked `stale` (with its age in seconds) and probed again by the next refresh; it is never deleted for age. A result younger than 5 seconds is not probed again, and one refresh runs at a time.
- **`?refresh=1`** is what sends the probes, so it needs the `X-CCBoard: 1` header like a change does; a plain read needs only the login and never sends one.
- **Doctor rows (group Box, read only).** `tailscale-status` (signed in, a MagicDNS suffix, HTTPS certificates, and how many devices could be a node), `nodes-port` (this board is served on a port in `CCBOARD_NODE_PORTS`) and `nodes-tagged-self` ("this device is tagged: browsers on it carry no identity": fine for a server nobody browses from; also names a malformed `CCBOARD_NODE_TAGS`). Never tag a device you browse from.
- `?demo=1` reads `app/static/demo/nodes-discover.json` (a found, a refusing, an offline and a no-ccboard device). To verify in the two-node check (#155): a real second board and a Mac with only the Tailscale app.

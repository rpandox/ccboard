# Epics

For people who run an epic across nodes.

[Back to the documentation index](../README.md)

#### Epics

An **epic** is a parent issue labelled `ccboard:epic` with sub-issues, as chosen in [#146](https://github.com/rpandox/ccboard/issues/146). The page shows each child's claim, task, pull request and progress. **Run** routes ready work; **Pause** stops new assignments on this hub, not work already started. Claims and work require `CCBOARD_EPIC_WRITES=1`. The [sub-issues API](https://docs.github.com/en/rest/issues/sub-issues) is the source for the parent-child links; the board also supports the label fallback below.

- **What counts as an epic.** An open issue labelled `ccboard:epic` in a repository this board has a project for (the GitHub `origin` remote of its own projects' repos, read with git on this board; nothing a paired node reports adds a repository), a pull request never. Its children are its sub-issues, in the order GitHub keeps them (the queue order), up to 100, read with `gh api` (`GET /repos/<owner>/<repo>/issues/<n>/sub_issues`). A repository that has no such endpoint is read through the **label list** instead: the children are the issues labelled `epic:<n>` (the parent's number) in the same repository, by issue number, and the page says so in one quiet line.
- **Which repositories it asks GitHub about.** Exactly the GitHub remotes of **this board's own projects**, and an epic addressed by `#/epic/<owner>/<repo>/<n>` only when its repository is one of them (otherwise `404 this board has no project for <owner>/<repo>`, with no request made). Nothing else chooses a request: not a paired node's task (`issue_ref`, a repository slug, project or repository names in its state), not a `repository_url` in a GitHub answer, not a `depends on owner/name#N` line, not a sub-issue that lives elsewhere. A child in a repository this board has no project for is shown from what the sub-issues answer already held, with "Claim not known: in another repository", and gets no follow-up request. A node's task is only **joined** to a child already read, by the exact issue number and a repository slug that is one of this board's own, and it cannot make a child appear, change its state or give it a link. A pin names only an issue of the epic's own repository that this board has read as one of its children (open the epic first). The Epics list reads the first 25 repositories and says "This board has more repositories than it looks in" when there are more; it says "There are more epics than shown" past 50, and "more issues than shown" for an epic with 100 or more children (a full page of children may have a next one, and the page never presents itself as complete).
- **The labels.**

  | Label | Meaning | Who sets it |
  | --- | --- | --- |
  | `ccboard:epic` | this issue is an epic | you, on GitHub |
  | `epic:<n>` | this issue is a child of epic `<n>` (only when the repository has no sub-issues endpoint) | you, on GitHub |
  | `ccboard:ready` | a child is ready to be taken | you; required by the unattended worker |
  | `ccboard:in-progress` | some node holds this child | a node, when it claims the issue (see [Claiming an epic issue](#claiming-an-epic-issue); off unless `CCBOARD_EPIC_WRITES=1`) |
  | `ccboard:node:<alias>` | a **label pin**: this child is meant for the node called `<alias>` | you, on GitHub |

  A child's body may say `depends on #12` (or `depends on owner/repo#12`) on a line of its own; the page then shows "waits for #12" while #12 is open in the epic, and flags a cycle. Nothing is resolved or reordered.
- **Where it is.** **Tasks > Epics** (the switch above the task board; it shows when the board has a task from a GitHub issue, a paired node, or an earlier epic visit, and always for `#/tasks?tab=epics`), the **Epics** link in a project's header, the palette (type `epic`, or `epic owner/repo#147`, or `open epic <GitHub issue link>`), and the page itself at `#/epic/<owner>/<repo>/<n>`.
- **The page.** A header (title, a link to the issue, "5 open, 1 closed", the GitHub requests left, **Pause** or **Resume**, **Pin epic** and **Run** (with a reason when unavailable)). **Progress by node**: one row per node with a bar of segments for done, running, queued and failed and the numbers in words with a glyph each (`✓ 1 done, ✽ 1 running, ∙ 1 queued, ✕ 1 failed`), so no state is shown by colour alone; the rows add up to the epic, and a closed issue counts as done for the node that held it. Then the issues, in queue order, in three groups: **On nodes**, **Unclaimed** and **Claim not known**. A row shows the state glyph and word, `#n` and the title, the node chip, the claim ("Running by node-a, renewed 3 min ago", or "Claimed by node-a, not live: last renewed 4 h ago"), the task phase on that node (an offline node shows its last phase and how long ago), the pull request, what it waits for, how long ago GitHub saw it change, and a **Pin** menu with "No pin" and every paired node (44 px rows on touch, arrow keys on a keyboard). A poll never moves the row you are on and never rebuilds a row that looks the same.
- **Times are GitHub's.** "updated 4 min ago" and "renewed 3 min ago" are measured against GitHub's own clock (the `Date` header of the answer), never against your browser's or any node's.
- **Pins and pause** are kept on this board only (`epic:<owner>/<repo>#<n>` in its key-value store) and change nothing on GitHub. A pin is this board's routing choice; **Pause** says "this board stops routing the epic". A handle must be `local` or a paired node; a pin to a node that was unpaired afterwards is shown as "no longer paired: ignored". A **label pin** is read too; when both exist the page pin wins, and a stale page pin falls back to a good label pin. Only a signed-in person can set them (`PUT /api/epics/<owner>/<repo>/<n>/settings`, the `X-CCBoard` header, a 403 for the hook token and for a node), and a refusal puts the old value back with the board's words in a toast.
- **The claim comment, and who may write one that counts.** A node that takes an issue (see [Claiming an epic issue](#claiming-an-epic-issue)) posts a comment whose first line is `<!-- ccboard:claim v1 -->` and whose second is `ccboard claim: alias=<alias> nid=<8 hex> lease=30m seq=<n> status=<claimed|running|done|failed|released|cancelled> attempt=<n>`, with `task=<ref> branch=<name>` when set. The page reads claims; the node makes them through the claim route below. A comment counts only when **all** of these hold: its author is a **user** (a user object with a login, type `User`, never a bot, an organisation or a deleted account), the login is in **`CCBOARD_EPIC_AUTHORS`** or, when that is empty, is **the login `gh` is authenticated as on this board** (compared without regard to case), and GitHub's own **`author_association`** on the comment is `OWNER`, `MEMBER` or `COLLABORATOR`, someone who can write to the repository. **Owning the repository earns no trust**: in a clone of someone else's repository their claim-shaped comments are not claims here. A matching login whose association is `CONTRIBUTOR`, `NONE`, `FIRST_TIMER` and so on (a new owner of a name someone else left, or any stranger) is "not from an allowed author", even when the name is in `CCBOARD_EPIC_AUTHORS`. When neither the setting nor the `gh` login is known, **no claim counts** and the page says "cannot tell who may claim: gh login unknown": no issue is shown as free then (every one is "Claim not known"). A comment with the marker from anyone else is not a claim: the row says "not from an allowed author" and nothing more, and its alias appears nowhere. The parser ignores a comment without the marker or with another version, tolerates extra fields, and evaluates nothing. A claim is **live** when its status is `claimed` or `running` and GitHub's clock is less than its lease (10 to 120 minutes) after the comment's last edit; the first live claim by `(created_at, id)` is the claim shown, and a claim that is not live is shown as "not live" and counts for nobody. **Known limit:** an allowed writer who copies a node's marker line can write a claim; the list and the association are the protection, not the marker.
- **What "Unclaimed" means: only when every comment was read, in this refresh.** Each issue's claim is one of three things. **Claimed**: an allowed claim was found. **None** (shown as Unclaimed, the only state that means free): every comment of the issue was read in this refresh and none is an allowed claim. `none` is a statement about a moment, so each open row says "claims read 12 s ago" by GitHub's clock (and `claims_read_at` in the answer is that time), and it is only reported when every page of the thread was fetched, or revalidated with GitHub (a `304` on `If-None-Match`), in the refresh that built the answer: a page kept in the cache (a closed issue's comments are kept ten minutes), a stale entry returned while GitHub asked us to wait, and the last good answer shown while GitHub cannot be reached are never `none`; they are **Claim not known: not read recently**, and a claim found in them is shown with its age and is judged live against GitHub's clock now, so a cached live claim older than its lease reads as not live. A reopened issue is open again and is read afresh, never from the days it was closed. **Unknown** (shown under **Claim not known**, with the reason, and counted apart from Unclaimed in the progress bars): anything else. The reasons are "too many comments to read", "GitHub asked us to wait", "not read yet in this refresh" (the budget of 40 comment requests or 30 seconds ran out), "the comments could not be read" (an error), "in another repository" and "cannot tell who may claim: gh login unknown". A thread of up to 200 comments is read whole; a longer one is read from both ends (the first 100 and the last 100, the last page worked out from GitHub's comments count and the page size, never from a link in the answer) and is **Claim not known** unless a **live** allowed claim was found in it, because a live claim could sit in the unread middle and anyone can post comments. A child whose comments count is 0 is taken as having no comment only when the issue list is fresh, not one kept while GitHub asked us to wait. A thread is read as one reading: the issue's comments count and `updated_at` are taken from the list (revalidated in this refresh) before the pages and the issue is read again, revalidated, after them; it counts only if the count is the same before and after, equals the number of comments the pages show, the comment ids strictly increase and no page read has a next link beyond the last one. Otherwise (a comment added or deleted between two page reads moves the page boundaries) the whole thread is read once more, and if it moved again the issue is **Claim not known: changed while it was read**. This costs one extra `gh` call per child with comments (the second issue read; a `304` costs no request budget) and none for a child with no comments, inside the same budget of 40 calls and 30 seconds a refresh already had. **A claim cannot trust a cached page.** The claim path calls `nodes_epics.fresh_claim_state(owner, repo, number, repos)` right before claiming: it bypasses every cache and TTL (the issue and every page revalidated in that call, the issue read again after them, at most pages + 2 calls) and answers `claimed`, `none` or `unknown` with the reason; only that `none` may be acted on.
- **Reading GitHub is cheap and polite.** Only `GET` requests, through `gh api` with an argv list (never a shell), after the owner, repository and number are checked against GitHub's own naming rules; an answer is capped (100 children, the first and last 100 comments of an issue, 2 MB); the list of children and an open issue's comments are revalidated in every refresh and a closed issue's comments are kept ten minutes, and later reads send `If-None-Match` (a `304` costs no request budget), and the page asks again every 30 seconds only while it is visible. The `gh` token is never read, printed, logged or returned. When GitHub says wait (`Retry-After`, or `x-ratelimit-remaining: 0`, or a secondary limit) the board stops asking, keeps the wait in memory, and the page says "GitHub asked us to wait 40 s" with the last read kept; it asks again once the time is up and never loops.
- **Errors and empties.** Every GitHub problem is a plain sentence with the next step, over the last read when there is one ("Showing the last read, from 2 min ago"): no `gh` ("Install the GitHub CLI (gh) on this board, then run gh auth login."), no login ("Run gh auth login on this board, then reload this page."), no access to the repository, no such issue, a wait, a slow or broken GitHub, an answer too large to read. An epic with no sub-issues says "This epic has no issues yet. Add sub-issues on GitHub." The Epics list says "No GitHub remote here" when no project has one and "No epics yet" when none carries the label. There is no error screen: a failed read keeps the page.
- **Doctor.** `Epics from GitHub` (id `epic-gh`, group Box): `gh` has a login with the `repo` scope, can read the first repositories that carry an epic (a tiny label query each), how many requests are left, and a note on the `gh` version (whether `gh issue create --parent` is available there, to verify; reading epics does not need it). Read only; it runs when the Doctor is opened.
- **Demo.** `?demo=1#/epic/example/website/147` shows a seven-child epic across two nodes (done, running, queued, failed, unclaimed with a pin, an issue whose claim was not renewed, one with a claim comment from someone not allowed, and one under **Claim not known**); `?demo=1#/tasks?tab=epics` shows the list. `&epic=nologin|noaccess|notfound|wait|stale|labels|empty|norepo|none|down` lays one degraded state over it; pins and Pause are played in the page.

Not in this phase, and to verify in the two-node check (#155): how real `gh` reports a missing login (the exit code), the `--include` head on a `304`, real rate use, and the page with live claims. A remote node's task carries no pull request in the hub's reading, so a pull request shows only for a task on this board. One refresh of the Epics list makes at most **40** `gh api` calls across all repositories and epics (`LIST_CALLS`; a `304` counts, a cached answer does not): the epics page of each repository, then one count call per epic when GitHub's own summary is missing. When they are used up the rest is **not read this time** and says so, never shown as empty or free: a repository not looked in is named under the list, an epic whose issues were not counted reads "issues not read this time" (`children: null`, `children_state: "budget"` in the answer, `partial`, `deferred_repos`, `deferred_counts` and `budget` on the list), and the next refresh, about 11 seconds later (the board reuses a cut list for 10 seconds), carries on with what was left first so no repository starves. A claim is matched to its author by login and association, not by account id, so a user who renames and a stranger who takes the old name are told apart only by the association. **Run**, the report back to the issue and routing by free lanes are the next phases.

#### Claiming an epic issue

When several nodes work one epic, each open issue must be taken by exactly one of them, a node that dies must give its issue back, and a node that was slow must not write after it lost. The only arbiter is GitHub: a **claim** is a comment on the issue, the order of claims is the order GitHub stamped them, and a claim stays alive only while its holder keeps renewing it by GitHub's own clock. No hub is the lock, so this is safe with no hub, with two hubs, and with nodes whose clocks disagree.

- **Off by default.** A board writes to GitHub only with `CCBOARD_EPIC_WRITES=1` in its environment (set it in `/etc/ccboard/env` and rerun `./install.sh`; any other value, and unset, is off). With it off the claim writer refuses before it builds a command, `claim_issue` answers `writes_off`, and the claim writer never builds or runs a `gh` command with a method other than `GET` (the claim does not even ask `gh` who it is). The switch governs the epic claim writes only: the pull request actions a person starts on a task (Create PR, Merge, comment) are separate, are not governed by `CCBOARD_EPIC_WRITES`, and are not behind the fence. Settings > Agents shows the switch and the alias read only, with a sentence each; the Epic page says "GitHub writes are off on this board (CCBOARD_EPIC_WRITES)" where a claim would otherwise be offered.
- **Exactly which GitHub writes the epic claim can make**, and nothing else (no issue edit, no close, no pull request, no repository setting, no other label, no comment that is not its own claim):

  | Write | Used for |
  | --- | --- |
  | `POST /repos/<o>/<r>/issues/<n>/comments` | the claim comment (and, after three failed attempts, one fixed comment asking for a person) |
  | `PATCH /repos/<o>/<r>/issues/comments/<id>` | edit the board's **own** claim comment: renew, start, release |
  | `DELETE /repos/<o>/<r>/issues/comments/<id>` | delete the board's **own** claim comment (a loser, an unconfirmed claim) |
  | `POST` and `DELETE /repos/<o>/<r>/issues/<n>/assignees` | add or remove **this board's own gh login**, the removal only if the board added it |
  | `POST /repos/<o>/<r>/issues/<n>/labels` and `DELETE .../labels/ccboard:in-progress` | the one label `ccboard:in-progress`, the removal only if the board added it |
  | `POST /repos/<o>/<r>/labels` | create that one label when the repository has none |

  Every path is built from a validated owner, repository, issue number, comment id and login; the body goes to `gh` on stdin as JSON (`--input -`) with an argv list, never a shell, a 20 s timeout and a capped answer; a `gh` failure is reduced to a fixed reason, and `gh`'s own text is never passed on. Writes go only to repositories that are this board's own projects' remotes and to issues that are children of an epic this board has read; another node, a request or a GitHub payload can never choose the target. The board edits or deletes only a comment whose id **it created and recorded**, and re-reads it first to check that its author is the board's own `gh` login and that the marker and node hash still match.
- **The protocol.** Node X claims issue I of repository R:

  | Step | What happens |
  | --- | --- |
  | 0 guards | writes on; R is one of this board's own repositories; I is a child of an epic this board has read as a `ccboard:epic` within the last 15 minutes; a `gh` login whose claims count |
  | 1 check | the issue and **every page** of its comments are read now (revalidated, never a cached "none"). A closed issue is never claimed. **Claim not known is never claimable.** A live claim of anyone: stop with `taken` and the holder's alias. A newest claim that is `done`: `done`. A thread counts as read only if GitHub confirmed every page in that read (a page from the cache means `claim not known`). Before the first post the board reads the repository and needs `permissions.push` to be true: a login that cannot push would post a comment that never counts, so it answers `no_access`, and a repository whose permissions cannot be read answers `error`, with nothing written. The attempt is the highest attempt seen plus one |
  | 2 post | the claim comment (status `claimed`); GitHub returns its id, and `owner/repo#n:comment id` is the **claim_ref**, the fencing token. A post whose outcome is unknown (a timeout, a 5xx) is **never repeated**: the thread is read back first and the board's own comment is adopted, or found absent |
  | 3 decide | wait 1.5 s, read without cache, wait 1.5 s, read again. The node wins **only if its claim is the first live one in both readings**, ordered by GitHub's `created_at` and then the lower comment id. Otherwise it deletes its own comment, does nothing else and answers `lost` with the winner's alias |
  | 4 mark | only the winner: add itself as assignee (kept only if GitHub echoes it back; no push access is a note) and the label (created if missing; a refusal is a note). These are visible state, never the lock |
  | 5 hold | the winner sets `running` when the task starts and **renews every 5 minutes** by editing its own comment with `seq` raised, so GitHub moves `updated_at`. A claim is live while GitHub's own `Date` is less than the lease (`CCBOARD_EPIC_LEASE_MIN`, 30 by default, 10 to 120) after `updated_at` |
  | 6 release | `done`, `failed`, `cancelled` or `released` edit the status, then remove the label and the assignee, but only what this board added |
  | reclaim | a claim that is not live is ignored by the ordering, so another node may claim at once; its comment says `reclaims=<comment id>` and its `attempt` is one higher. After attempt 3 the nodes stop and one fixed comment asks for a person |

  One difference from the issue's wording: the assignee and the label are added **after** the decision, not before it. With marks first, a loser has to undo what it added, and two nodes claiming at once could both believe they added the label, so it would never be removed or the winner's would be taken away. Marking only after the win leaves a loser with nothing to undo.
- **The fence.** Every later GitHub write by the holder (a progress comment, a label change, a pull request, the release) must pass `fence_ok(claim_ref)` first. It reads the thread afresh and requires the claim comment to exist, to be the board's own (author, marker and node hash), to be live by GitHub's clock and to be first. If the comment was deleted, edited into something that does not parse, renamed to another node, expired or overtaken by an earlier live claim, the claim is **lost**: the record is kept as `lost`, one audit row `epic-claim-lost` (repository and issue number, a reason word) is written, no further write happens for it, and the Epic page says so once with a toast. Parking the task `lost-claim` and keeping its worktree is done by the run phase (#149): this phase provides the hook (`LOST_HOOKS`) and the link (`attach_task`), but nothing starts a task from a claim yet, so no real task is parked by this version. **The fence fails closed**: a read that fails, is rate limited, is not confirmed by GitHub in that call or cannot settle (a thread over 200 comments), and a `gh` login this board does not know at that moment, all answer "not ok" without declaring a loss, and nothing is written.
- **What the comment says, and what it never says.** The comment holds the alias, an 8-hex hash of the node id, the lease, a sequence number, the status, the attempt, `reclaims` when set, and `task=<ref> branch=<name>` when set, in a fixed template; a fixed sentence follows for people. It is **never free text**: nothing a peer, an agent, an issue or a caller sends ever enters it, and the writer refuses any other body. Comments on a public repository are public, so it carries no path, no host name, no address, no token and no login beyond GitHub's own author field. The alias is `CCBOARD_EPIC_ALIAS` or, by default, a short neutral word and two hex characters derived from the node id (for example `willow-3f`); an alias with a dot, or equal to the machine's short host name, is not used and the Doctor says so.
- **Known limits.** The tie-break (earliest `created_at`, then the lower comment id) is **this board's own rule and is unverified on real GitHub**: GitHub does not document the order of comments created in the same second. The two-node box check (#155) measures it with 20 simultaneous claims, and so measures a killed node's reclaim and what the 5-minute heartbeat costs in rate limit. **Anyone with write access to the repository can forge a claim** (a comment that copies a node's marker line counts, as it must for the page to read it); the allowed-author rule of the epic view limits whose claims count. Reads can be briefly out of date after a write, which is why a node reads twice before it believes it won. A thread over 200 comments is not claimable ("claim not known: too long") and a holder on one cannot renew. A claim has at most 288 renewals (24 hours); then it is left to lapse. The pull-request writes that `prpoll` and `gitops` already make are not behind the fence yet (they are not part of a claim until the run phase starts a task from one).
- **Claim recovery.** Busy-claim `wait_s` is an upper bound, not a measured queue time. The relay gained one read-only GET row, `epic_claim_status` (scope `tasks`), on purpose so the page can recover an unknown answer without sending another claim. It reads local results only and never calls GitHub. Attempt tokens keep results separate; pending results expire after 120 s, and recovery rows age out after a day during claim or status requests. The page paints before these checks finish and trusts the fresh GitHub read when an issue is closed or held by another node.
- **The write queue.** One GitHub write at a time per board, at least 1.1 s apart, at most 30 a minute, a back-off on `403` and `429` (`Retry-After`, or 60 s for the secondary-limit message; a wait over two minutes is reported as "GitHub asked us to wait" instead of slept), and no automatic retry of a write whose outcome is unknown. A write that cannot get its turn in the queue within 45 s is refused as `busy` with nothing sent, and a node takes at most four claims asked of it at once (the fifth is answered `busy` before it starts, with `claims_ahead` and `wait_s`; Run respects that delay). The renew timer exists only while a board holds a claim, is bounded, stops on shutdown and never touches the database after it stops; a board that never claimed runs nothing new in the background. After a restart the board takes back an unconfirmed claim of its own and starts the timer again for a held one.
- **Edit history and cost.** Run, the hub loop, `epic_run`, the peer work route and the worker share this rule. Verdicts are cached for ten minutes (256 entries), keyed by the repository, issue, update time, text digest and allowed logins with their pinned ids. The post-claim read checks again if text or update time changed. The epic page reads stored check results only, hides old results after an update, marks blocked or unknown rows with words and a glyph, and disables Work. Almost every issue needs one history page; a ten-issue epic normally needs eleven initial checks. Fresh checks record actual `rateLimit.cost` in the audit, separate from the REST budget. A cache hit writes no audit row or stored result when the verdict, editor and update time still match; a missing or changed stored result is recorded again. Below 25 remaining GraphQL points the check refuses and the worker rests until reset. Comments do not enter prompts; any future comment-to-prompt path must check that comment's history first.
- **Settings.** `CCBOARD_EPIC_WRITES` (default off), `CCBOARD_EPIC_ALIAS` and `CCBOARD_EPIC_LEASE_MIN` (see the table under [Settings](../configuration.md#settings)). Settings > Agents shows the first two read only, beside `CCBOARD_MCP_NODES`.
- **The route and the page.** `POST /api/nodes/<handle>/epics/claim {repo, issue, epic}` on the hub asks a paired node to claim; the node's side is `POST /api/node/epics/claim`. It is a relay row: scope `tasks`, write class, a signed-in person only (the hook token, an MCP device token and a node token are refused: **the agent path for epics is a later phase and stays closed**), the person is named, the body is strict (`repo` is `owner/name`, `issue` a whole number, `epic` the epic's number or `owner/name#n`; the hub adds a random `claim_id` correlation token), and both boards write an audit row `claim_issue` with the repository and the issue number only. The node answers 200 with `{claimed, reason, repo, issue, winner, attempt, claim_id}` or 409 `claim_refused` with a `why` from a closed list; the hub rebuilds the answer from a whitelist and uses its own words. The claim takes more than the usual 10 s (two waits of 1.5 s and writes 1.1 s apart), so this row waits up to 90 s (over twice the 39 s observed under load); a timeout is "unconfirmed" and is **never retried**. On each subsequent epic-page poll, the hub reads `GET /api/nodes/<handle>/epics/claim/status?repo=<owner/name>&issue=<number>` (the node has the same path under `/api/node/`). This tasks-scope, person-only read uses the node’s stored claim outcome, makes no GitHub request and replaces the unknown result as soon as the node settles it. Claim and Work stay blocked while a recovery check is pending; an unknown or expired result clears the check and asks the person to look at the issue on GitHub before trying again. The node logs durations for reads, writes (including queue time), read-back, withdrawal and the whole claim. On the Epic page a row shows **Claim on `<node>`** only when this board's writes are on, the issue is open and its claim is none (every comment read), it is pinned to a paired node (the issue's pin, else the epic's) that is online and holds the `tasks` scope with this board. It paints "Claiming on `<node>`…" at once and shows the answer in plain words: taken (with the winner's alias), lost, claim not known, writes off (on the node), closed, already done, attempts used up, offline, scope, unconfirmed. This board's own claims show on their rows as held and renewing, or lost with the reason, and a lost claim says so once with a toast (and, once the run phase links a task to a claim, that the task is marked `lost-claim`). A pin to this board itself gets no Claim action here (a claim is asked of a paired node). **Run** stays disabled.
- **Doctor.** `Claiming epic issues` (id `epic-claim`, group Box). With writes off it says so in plain words and asks GitHub nothing (and still reports the alias and lease settings). With writes on (read only, on a probe thread): the `gh` login and its `repo` scope, push access to the first repositories (without it the board will not claim there, because a claim comment from a login that cannot push would not count, and the assignee and the label are refused too), the alias setting with the host-name warning on a public repository, the lease setting, and what the board may write.
- **Demo.** `?demo=1#/epic/example/website/147` shows a held claim of this board on #202 ("This board is running this issue and renews its claim"), a lost one on #203 (with its toast, once, and a task linked to it, which only the demo has) and **Claim on node-b** on #205, which is pinned to an online node; the Claim plays a made claim, and `&claim=taken|lost|unknown|writesoff|closed|done|attempts|offline|scope|unconfirmed` plays each refusal. `&epic=writesoff` shows the writes-off note, `&epic=offline` and `&epic=notasks` a node that cannot take a claim.

#### Working an epic issue

A claim is only a reservation. **Work** turns it into a task: the node that wins the issue starts it as a task on itself (a worktree, a branch and a session), with the issue's own model line, and keeps the issue informed with a few short comments. Everything here sits behind `CCBOARD_EPIC_WRITES` (off unless it is exactly `1`): with it off the work route refuses before any claim, task or `gh` command, the epic page draws no settings and a disabled **Work** that says why, and a board with no paired node behaves as before (no new key in `/api/state`, no poller, no table row).

- **The route.** `POST /api/nodes/<handle>/epics/work {repo, issue, epic?, force?}` on the hub asks a paired node; the node's side is `POST /api/node/epics/work`. It is a relay row like the claim: scope `tasks`, write class, a signed-in person only (the hook token, an MCP device token and a node token are refused; there is no MCP tool), and the body is strict (`repo` is `owner/name`, `issue` a whole number, `epic` the epic's number or `owner/name#n`, `force` a boolean). The settings of the epic (`report`, `auto_pr`, `close`) are **not** in the page's request: the hub fills them in from the settings it keeps for that epic, so a caller cannot choose them. The answer is `{claimed, reason, id, task_ref, branch, tmux, repo, issue}` or a refusal (below). The node takes at most as many of these at once as it takes claims.
- **What the node checks, in this order, and what each refusal says.** (1) Writes are on. (2) The repository is one of this board's own projects (an `origin` in SSH or HTTPS spelling both match) and a clone is here: otherwise `404 repo_not_here`, "That repository is not cloned on this node, so nothing was claimed", and no claim exists. (3) **The author check, the first guard:** the issue and the epic it belongs to must each be written by a *user* (never a bot or an organisation) whose login is in `CCBOARD_EPIC_AUTHORS`, or, with that empty, is the login `gh` is authenticated as on this node; the repository owner is not trusted by being the owner. Anyone who can write to a repository can edit an issue body, and the body becomes the prompt of an agent that edits files, so an issue by anyone else is refused with "authored by <login>, not on the allowed list" **before any claim comment exists**. Anything that cannot be read is refused too (`unreadable`). (4) **The edit-history check:** every body revision and title rename of the issue and its epic must be by an allowed User with a numeric id, matching any `login:id` pin (else this board's own gh id). An outsider edit, even followed by an allowed edit, refuses before any claim: `edit_not_allowed` or `epic_edit_not_allowed`, naming the editor. Add that login to `CCBOARD_EPIC_AUTHORS`, or have an allowed author copy the text into a new issue. Hidden, incomplete or unreadable history, more than 300 edits, more than 50 title renames, errors or low GraphQL budget refuse as `edit_unknown` or `epic_edit_unknown`. The newest visible body edit or title rename must reach `lastEditedAt` within one second; otherwise GitHub did not show the newest edit and work is refused. There is no off switch. (5) The advisory lane cap (`CCBOARD_NODE_LANES`): "This node already runs as many tasks as its lane cap advises" (`lanes_full`); the page offers **Start anyway**, which sends `force`. (6) The claim itself, with the claim's own refusals (`taken`, `lost`, `claim_unknown`, `closed`, `done`, `attempts_exhausted`, ...). (7) The issue is read again and its **Who should do it** block is parsed by the same parser the From GitHub issue launcher uses (`app/issues.py`). A model line that names `--dangerously-skip-permissions`, `bypassPermissions`, `danger-full-access`, `--dangerously-bypass-approvals-and-sandbox` or `--yolo`, in any spelling (dashes, case and invisible characters are folded), or a permission setting this node does not use for work from an issue, is refused with **one** fenced comment (`refused: the issue asks for bypass`), and the claim is released as failed; the refusal counts as an attempt. An issue with no model line uses the node's defaults and never bypass. (8) The task is made by the board's own task create, with `issue_number` and `issue_url`, and started in a lane; the claim becomes `running` with the task and the branch.
- **The issue text is data.** Its title and body go into the task prompt between marker lines, with hidden HTML comments, control, format and separator characters removed and the body cut at 12,000 characters. They never reach a shell, an argv or a launch line; the launch (agent, model, effort and permission mode) is built only from the validated values of the model line through the same safe launch path a remote task uses, and it states its permission mode explicitly. The footer of the prompt says to work only in this worktree and not to push unless asked.
- **Comment formats.** The claim comment is the "started" comment; nothing else is posted for it. Every other comment is a fixed template, written only by `app/github_write.py` from validated fields (the alias, one sentence of a closed list, the branch name, and a pull request link built from a validated owner, repository and number), and the writer refuses any other body:

  ```text
  <!-- ccboard:progress v1 -->
  ccboard <alias>: <phase sentence> [<pull request link>]
  Branch: <branch>
  ```

  | Phase | The sentence |
  | --- | --- |
  | waiting | `waiting for a person` (a permission or input request has been open for 10 minutes) |
  | pr | `pull request opened <link>` (only with the epic's pull request setting on) |
  | done | `done` (with the link when a pull request was opened) |
  | failed | `failed` |
  | cancelled | `cancelled` |
  | refused | `refused: the issue asks for bypass`, or `refused: the issue asks for a permission setting this node does not use` |

  At most **one comment per issue every 5 minutes**, only on a change of phase; a comment held back by that wait goes out on the next beat of the claim's 5-minute renew timer, so "waiting for a person" appears between 10 and 15 minutes after the request opened. `done` is posted only after the task's own confirmed result. With the report setting `none` the waiting, done and failed comments are not posted; a refusal and the help-needed comment still are, because they ask a person to look. After the third failed attempt the node posts the claim's fixed help comment instead of a third `failed`.
- **What the epic's settings do (phase reports by default; auto_pr and close off).** They are kept on the board, per epic (`PUT /api/epics/<owner>/<repo>/<n>/settings {report, auto_pr, close}`), and the epic page shows them as labelled controls with one paragraph that says in words what will be posted and pushed. A change applies to work started after it: a task that is already running keeps the settings it started with.

  | Setting | Values | Effect |
  | --- | --- | --- |
  | `report` | `phase` (default), `summary`, `none` | `phase`: phase comments only, no result text leaves the node. `summary`: also the first 1500 characters of the task's result after the redaction pass below. `none`: no phase comment and no result. An older board's `true` is read as `summary` and `false` as `phase`. |
  | `auto_pr` | off | Off: nothing is pushed. On: when a task is done its worktree is committed and **only the task's own branch** is pushed (the argv is checked: the branch is the task's own `worktree-...` branch and never the base, `main` or `master`) and a pull request is opened through the same code the **ship it** chip uses; the link goes in the comment and on the task card. Nobody has read the diff when this runs, so the commit and the push run **no repository hook** (`core.hooksPath` is switched off and both get `--no-verify`; an agent could have edited a hook script), the worktree's real branch is read first and must be the task's own (otherwise nothing is committed or pushed, and `done` is posted without a link), and the pull request is made for the issue's own `owner/name` (`--repo`), never for another remote of the clone. The **ship it** chip a person taps keeps its hooks. It is the one GitHub write that does not go through `app/github_write.py`, and it is fenced like the others. |
  | `close` | off | On, and only with `auto_pr` on: the pull request says `Closes #N`. Nothing else ever says it. |

- **The redaction pass.** A result is posted only when `report` is `summary`, after **one** pass: the text is cut to 4,000 characters first (at white space), then credentials in a link (`//user:pass@`) and email addresses become `[removed]`; this machine's home folder and the macOS, Linux, Windows (`C:\Users\name`) and `/root` home folder prefixes (the folder and the user name after it, a name with spaces too) become `~`; the temporary folders `/var/folders` and `/private/var` become `[tmp]`; the value of a `password=`, `token=`, `secret=` or `api_key=` assignment and a host name that ends in `.ts.net`, `.local`, `.internal` or `.lan` become `[removed]`; anything shaped like a GitHub token (`gh*_...`, `github_pat_...`), `sk-...`, `AKIA...`, `xox...-...` or `Bearer ...`, any run of 32 or more hexadecimal characters, and any run of 32 or more base64 characters that holds both a digit and a letter, becomes `[removed]`; control characters are dropped and backticks become apostrophes; the result is cut to 1500 characters. The comment adds the line `Some text was removed before posting.` when anything was removed, and the writer refuses a text that the pass would still change. The rule is blunt on purpose: a long branch name with digits in it is removed too. Comments never carry a path, a host name or a token.
- **Failure, retry and a lost claim.** A task that ends `failed` or `cancelled` posts its comment, sets the claim `failed` or `cancelled`, removes the label (and the assignee, if this node added it), and leaves the issue open for another attempt; three attempts at most (see the claim table above). A task that ends and whose claim cannot be checked is retried for 12 beats of the renew timer, then the work is marked abandoned and the claim is left to lapse; nothing is posted and no loss is marked. A **lost claim** (another node was first, the comment was deleted or edited, the lease ran out) posts nothing: the task is parked (its worktree is kept, its session is not ended, the card says **lost claim**) and the epic page says why.
- **The task still stops at permission requests.** A task an epic started is a normal task: it waits for a person at a permission request or a question, the owner answers on the board (or from another board that has this one paired), nothing auto-answers, and the issue is not released while it waits.
- **The page.** On the epic page, an open issue that a paired node can work (unclaimed, pinned or epic-pinned to an online node that holds the `tasks` scope, or claimed by such a node without a task yet, or whose last attempt ended) shows **Work on <node>**, the one tinted action of the row (**Claim on <node>** next to it is then a bordered button; the page keeps a single filled primary, which is **Run**, enabled when routing can proceed). The tap paints at once ("Starting on <node>...", the row held by that node and queued) and the node's answer replaces it; a refusal puts the row back and says why in plain words, one sentence for every word above. A row shows the phase of the work this board ran (running, waiting for a person, pull request opened, done, failed, cancelled, claim lost, each with a glyph) and **Open on <node>**, which opens the task on the node it runs on (`#/n/<node>/t/<id>`, or the Tasks page for a task on this board). An issue by an author who is not on the allowed list carries a mark ("by <login>, who is not on the allowed list"), its **Work** is disabled and names the author, and the line under **Run** names every issue it would skip. With GitHub writes off, or with no node paired, the settings are not drawn and **Work** is a disabled button that says why. **Work on <node> passes the same hard filters as Run** (offline or stale, no `tasks` scope, repository not cloned or not reported, agent missing, logged out or unreported, back-off, window over the limit, lanes not reported, a refusal this board just had): the epic answer lists, for each open issue, the nodes that fail one (`work_refused`), and **Work** is then disabled with the board's own sentence on the row ("node-b 5-hour window is at 90 percent until 14:10 UTC"). The board checks again when you press it (`POST /api/epics/<owner>/<repo>/<n>/issues/<issue>/work {node, repo?, force?}`, then the relay row `epic_work`): a node that fails a filter is not asked and the answer is `409 node_filtered` with the filter's code and the same words. A pin never lifts a filter. A full lane count is the one thing a person may override: **Start anyway** (`force`) lifts only the free-lane count, and a lane count that was never read still refuses. **Work on <node>** stays next to **Run on...** because it also covers the issues **Run on...** refuses (a claim a node holds without a task yet, and a retry after a failed attempt).
- **The task card.** A task an epic started links the issue and its claim comment (`claim`), says "Epic work: <phase>" with a glyph, and shows a lost claim as its own state: a `⚠ lost claim` chip, with the words that the issue may go to another node and that the task is parked with its worktree kept.
- **Settings.** `CCBOARD_EPIC_WRITES` (default off) and `CCBOARD_EPIC_AUTHORS` (see the table under [Settings](../configuration.md#settings)): the second now also decides whose issues a node will run, not only whose claims count. The per-epic switches above are not environment settings.
- **Demo.** `?demo=1#/epic/example/website/147` shows **Work on node-b** on #205, **Try again on node-b** on #204, the phase of this board's work on #201 (done), #202 (pull request opened) and #203 (claim lost) with **Open on <node>**, and the settings (all off) with their paragraph. `&epic=workrun|workwait|workfail|workcancel` plays another phase on #202; `&epic=authors` marks #205 as by an author who is not allowed (Work disabled, Run names it), `&epic=epicauthor` marks the epic itself and `&epic=noauthors` says no author is known. `&work=nothere|author|epicauthor|unreadable|bypass|posture|lanes|launch|taken|lost|unknown|writesoff|closed|done|attempts|offline|scope|unconfirmed` plays each refusal of **Work** (`lanes` is refused until **Start anyway** is tapped). `?demo=1&taskepic=running|waiting|pr|failed|cancelled|lost#/tasks` lays each phase of epic work over the demo task of issue #47.
- **Known limits.** The [two-node check](https://github.com/rpandox/ccboard/issues/155) completed remote tasks and a three-issue epic with phase comments; actual `auto_pr` pushes and pull requests remain to verify. A lost claim parks the task but does not stop its session. The hub's **Work** relay targets paired nodes; the worker uses the same work logic locally. The author and full edit-history checks apply to both, but they do not make an allowed author's text safe. Two concurrent Work requests on one node return the same task.

#### Routing an epic to a node

**Run** on an epic page sends each ready issue to the node that can take it now, one at a time, and shows why. Routing only **chooses**: it calls the existing work route (`POST /api/nodes/<handle>/epics/work`, see [Working an epic issue](#working-an-epic-issue)) through the relay, which runs the author check, the guard and the claim, so no routing path starts an agent or chooses a launch option. It needs `CCBOARD_EPIC_WRITES=1` and at least one paired node; without them **Run** stays off with the reason on the page, no thread exists and nothing is stored.

- **The filters, in this order, each with its reason on the page.** A node that fails one is not a candidate for that issue: (1) online (offline, stale, unauthorized and unpaired nodes are never chosen); (2) the pair holds the `tasks` scope; (3) the repository is cloned there, as the node's last reading says (a node that has not reported its projects yet is "not known", not "no"); (4) the issue's agent (from its "Who should do it" block, Claude by default) is installed and logged in with no login problem; (5) not in a back-off for that agent; (6) the agent's rate-limit window is below the limit (`CCBOARD_EPIC_MAX_WINDOW_PCT`, 85 by default, or the epic's own limit): a percentage that is not known, or a reset that has passed, counts as **50** and the page says "window unknown"; (7) a free lane after this board's reservations (a lane cap of 0 means no cap; an unreadable lane count is "not known", never free); (8) this board's own recent experience: a node that refused or could not be reached is left alone for two poll cycles. Codex uses its weekly window.
- **The ranking of what is left.** More headroom, then more free lanes, then the lower 1-minute load per core (unknown last), then the node least recently given an issue, then the name. The result is the same for any order of the nodes.
- **Pins.** The issue's pin on the page, then a `ccboard:node:<alias>` label, then the epic's pin. A pin overrides the ranking and **never** a filter: an issue pinned to a node that fails one waits, says which, and is not sent anywhere else. A pin to a node that is not paired, to an alias that names none, or to this board waits too: routing sends work to paired nodes only.
- **One subscription, one window.** The rate-limit window belongs to the subscription, not the node. Nodes whose card shows the same subscription for the agent are counted once: the group's window is the **highest** reading of any online member (one stale low reading cannot open it), and their free lanes add up for the tie-break only. Where the card cannot tell, tick the nodes that share one on the epic page (**Nodes on one subscription**). To verify in the two-node check (#155): which stored field is a stable subscription key on real accounts; until then the manual group is the safe way.
- **Lanes are reserved.** A dispatch holds a lane of the node in this board's memory until the node's next reading shows the task or two poll cycles pass, so two ready issues go to two nodes with one lane each, and with only one lane the second waits ("no free lane"). The reservations are lost when the board restarts.
- **The loop.** A thread named `epic-run` exists only while a run is active, GitHub writes are on and a node is paired (and is resumed at start for a run that was active). A cycle reads the epic, takes each ready issue (open, claim known and none, written by an allowed author, no dependency cycle, nothing it waits for open, not sent in the last two cycles, not held) and asks routing. One work call at a time, at least one second apart, never more than the lanes free after reservations; **Pause** is read again before every call; a window that resets releases a waiting issue by itself. The outcome of a call is handled by what it means: taken or lost moves on; a node's own refusal (lanes full, writes off, not reachable) leaves that node alone for two cycles; a call whose outcome is not known keeps its reservation and is not repeated for 10 minutes; an issue the node refused for its own reasons (author, bypass, attempts used up) is held for 5 minutes and shown. The run ends when nothing is open and unclaimed (`finished`), when an agent's allowance is spent (`limit`), or when the epic is closed or gone (`closed`, `stopped`). A crash in a cycle is logged and counted and never touches the hub's poller, which is another thread.
- **Visible and audited.** Every assignment writes its `why` ("chose box: 2 free lanes, 5-hour window 31 percent") on the epic's run row and an `out` audit row (action `epic_route`) naming who started the run. The page shows a wait as "waiting: <reason> until <time>" with the nodes left out and why, never a bare spinner. Headroom is an estimate: an agent can still reach its limit.
- **The page.** **Run** is the one filled primary: on when the board can route and the epic is not paused, otherwise off with its reason (writes off, no node paired, paused, GitHub not readable). While a run goes it reads **Running** with who started it and the page asks again every 10 seconds. **Pause** and **Resume** post to the board and stop or continue new assignments at once; claims already made go on. **Run on...** on an open, unclaimed issue is a menu with **Auto** and each paired node: the same filters apply to a node you name, a node that fails one answers "waiting: <reason>", and nothing is queued. Optimistic: the row says "Choosing a node..." or "Sending to <node>..." before the board answers and goes back on a refusal. The epic settings gain **Window limit** (10 to 100, empty = the board's), **Nodes on one subscription** (two or more nodes) and **Let MCP run this epic** (off by default, with one sentence on what it allows).
- **The launcher.** A new task has an **Auto** cell after **This node**. It asks `GET /api/route/auto` for the repository the sheet was opened for and the agent chosen in the cell, shows the node and the reason in the command preview before Start ("Auto chose build-box: 2 free lanes, 5-hour window 31 percent"), and then is that node's own form. When no node can take it, it says "waiting: <reason>", lists the nodes left out and why, and offers **Check again**; nothing starts on a guess. Choosing **This node** starts exactly as before.
- **Routes.** `POST /api/epics/<owner>/<repo>/<n>/run`, `.../pause`, `.../resume`, `.../issues/<issue>/run {node}` (a node's handle or `auto`), `GET .../route[?issue=N]` (the run, and with `issue` what Auto would do now), `GET /api/route/auto?agent=&slug=` (or `project` and `repo`), and for agents `GET /api/mcp/epics/<owner>/<repo>/<n>` and `POST .../run`. A person's routes answer `403` to the hook token, a node token and a device token; the CSRF header is required as everywhere.
- **Settings.** `CCBOARD_EPIC_MAX_WINDOW_PCT` (see the table under [Settings](../configuration.md#settings)) and, per epic and kept on this board only, `max_window_pct`, `group` and `mcp_run` in `PUT /api/epics/<owner>/<repo>/<n>/settings` (a value at its default is not stored, so an old row reads as it did).
- **Two things that differ from the issue.** Routing never picks this board (`local`): the work route reaches paired nodes only, so a pin to this board waits and says so. A run an agent started reaches the person-only work row under the label `run for mcp:<token name>`, because the relay refuses an agent identity on that row; the switch a person set on the epic is what allows it. The node's own audit row therefore shows that label, while the board's `epic_run` and `epic_route` rows show exactly `mcp:<token name>`.
- **Known limits.** None of this has run on two real nodes yet (the two-node check, #155, does that): the subscription key, the real window numbers and a real GitHub are unproven. A run that is active at start with no paired node restarts on the next Run or board start. The demo: `?demo=1#/epic/example/website/147` shows **Run**; `&epic=run|runwait|runpaused|runagent|runfinished|runlimit|nonodes|paused|groups|writesoff` show a run going, a wait for a lane, a paused run, a run an agent started, the two ends of a run, no node paired, a paused epic, three nodes with a group and MCP on, and writes off; `&run=waiting|claimed|busy|notfound` plays a refusal of **Run on...**; `?demo=1#/tasks` then **New task** shows the **Auto** cell, and `&auto=wait` plays the wait.

#### When something goes wrong

Every way the fleet can go wrong ends in a plain state: what is down and for how long, what to do, and nothing that runs twice. Each row below has a test in `tests/test_nodes_failures.py` (and `tests/js/nodes-failures.test.mjs` for the words and buttons). A state is always a glyph and words, never colour alone.

| What happened | What you see | What to do |
| --- | --- | --- |
| A node is offline (asleep, off the tailnet, or a board update of about 70 seconds) | The chip says `offline since 09:14` and the node page says "<node> is offline, last seen 3 hours ago" above its last reading. Every action on it is off with that sentence and sends nothing. Nothing is queued. Routing skips it and a pin to it waits and says so. Its running tasks go on and report when it returns. | Nothing. When it is back the first reading shows it online, no refresh needed. |
| This board restarts | Nodes keep working alone and their claims renew without this board. No new assignment happens until it is back. After the restart each node shows its last reading with its true age, not a blank. | Nothing. |
| A clock is more than 5 seconds off | A `! clock off by 600 s` chip beside the node's status, a line on its page, and a `nodes-health` row in Doctor. Claim order does not change (claims use GitHub's clock; tested at 10 minutes either way). | Turn on automatic time on that device. |
| The same issue is claimed twice | One node wins, the other is told "taken". Calling the work route again for an issue a node already holds returns the same task (`already_held` on the wire; the issue's word was `already_mine`), so a repeat never starts a second one. | Nothing. |
| A write gets no answer, a server error (5xx) or a broken answer | "Outcome unknown, check <node>: it may or may not have got this. It was not retried." with a **See its tasks** link to that node's page. This board never sends it again by itself and adds no Retry button. A prompt keeps its draft in the prompt field. An epic **Claim** or **Work** button comes back, because a repeat is safe: the claim answers `already_held`. | Look at the node, then decide. |
| You removed a node here | The row and its token go at once and the other board is asked to drop its pair (best effort; the toast says when it was not told). Calls on their way end with "re-pair". Its running tasks and claims go on until released or the lease ends. | Nothing. |
| The node removed the pairing on its side | "<node> removed this pairing, pair again", chip `re-pair`, and a **Re-pair** button on the node page and the Settings row. | Make a new code on that node and press **Re-pair** (the Add node sheet opens at the saved address). |
| A token rotation | The new token works at once and the old one for 60 seconds. Using the old one after that is refused. Two rotations at once leave one valid token. If the answer is lost: "Outcome unknown, check <node>: it may have rotated the token, and this board will not ask again. Press Re-pair." The row turns amber (`re-pair needed`) and **Rotate token** is off with its reason, and only a new pairing clears it (a later good answer on the old token does not). If the node never answered the connection (asleep), nothing was sent and nothing changed: "try again later", and the pair stays healthy. **Rotate token** is also off while the node is offline or stale, with the reason, and a second press while one rotation runs is told it is busy. | Press **Re-pair**; or wait for the node to wake and rotate again. |
| Another device answers at the node's address (a re-registered or renamed device) | Chip `another device`, "This address now belongs to another device, not <node>: remove it or pair again". None of its data is shown and every action is refused. | **Remove**, or **Re-pair** if you know it is the right device. |
| The node moved to another address | After **Refresh** under Found on your tailnet, a `! address changed` line under the pair says where it answers now, that the old address was checked once more, and offers **Update address**. It names the Tailscale device when discovery has its name. Nothing changes until you press it. It is refused unless the old address is clearly not this node (connection refused, name gone, a 404, or another node's answer): if it still answers, or could not be checked (a timeout, a rate limit, a server error), the answer is "still answers or could not be checked, try again"; it is also refused if the new one answers as another node, or if you removed the node meanwhile. | Press **Update address**. |
| The node speaks another node API number | Chip `incompatible, API 2` and "<node> speaks node API 2 and this board speaks 1: update the older board". Its card is still shown; its state is not merged and every action is refused. | Update the older board. |
| GitHub is the trouble (`gh` logged out, a rate limit, an outage) | The node rests for at least 5 minutes (longer if GitHub names a longer wait) and the epic page says "<node>: GitHub is not available there (gh is logged out); trying again around 14:10". When this board's own read fails the run line says what is wrong and when it tries again. Never a tight loop. | `gh auth login` on that node, or wait. |
| A 13th node (or a 13th board that may call this one) | **Add node** is refused before anything is sent, also with both ways on (a re-pair of a board that already calls this one replaces its pair and is let in): "This board already has 12 paired nodes, the most it keeps. Remove one first." The other board's code is not spent. | **Remove** one. |
| A node sends too much, nonsense, or answers slowly | Its status shows what happened (`sent more than a reading may hold`, `sent an answer this board could not read`, `did not answer in time`) and keeps its last reading. Other nodes are not touched; the poller uses at most 4 workers. | Nothing; update or restart that node. |
| Browser gets `403` | The board has no allowed identity; pairing does not sign a browser in. | Use an allowed user-owned device and check `CCBOARD_ALLOWED_USERS`; direct localhost needs optional local sign-in. Never tag a device you browse from ([Serve identity](https://tailscale.com/docs/features/tailscale-serve)). |
| Discovery `found` | Settings > Nodes > Found on your tailnet: `ccboard answers` | Press **Pair**; discovery alone grants nothing. |
| Discovery `refuses` | `ccboard refuses us` | Something answered with 401 or 403: check the peer's grant and identity rules. |
| Discovery `no_ccboard` | `nothing listening` | Start ccboard and check its HTTPS port against `CCBOARD_NODE_PORTS`. |
| Discovery `no_tls` | `no HTTPS` | Use the correct HTTPS port and certificate name; check HTTPS setup ([Serve](https://tailscale.com/docs/features/tailscale-serve)). |
| Discovery `unreachable` | `unreachable` | Check the address, network access and whether the peer answers without a redirect. |
| Discovery `offline` | `offline` | Wake the device, reconnect it, then Refresh. |
| Discovery `invalid` | `invalid name` | The name Tailscale gave is not a tailnet name, so it was not checked; use a device of your own tailnet, not a shared-in one. |
| Discovery `unchecked` | `not checked yet` | Press Refresh. |
| Signing key changed, missing or corrupt | Settings > Nodes and Doctor name the key problem; a changed pin is refused. | For a lost or stolen key, Remove the pair and pair again. A normal rotation can be followed for 30 days; afterwards pair again. |
| A signed call is refused for its time or as a repeat (`clock`, `stale`, `replay`) | The node's status reads `clocks differ`, `signature too old` or `signature already used`; there is no automatic re-pair. | Turn on automatic time on both devices (a signature's time may be off by 120 seconds) and wait for the next check. The 5-second skew chip is an earlier hint. |

**Doctor `nodes-health`** (read only, listed on every board, skipped when no node is paired) lists each paired node that needs attention, worst first: a refused token or a lost rotation, another device at the address, another node API, offline, then a clock off by more than 5 seconds. Each line has a fix that names the button. It reads only what this board already knows and calls no node.

**Routes and words added.** `POST /api/nodes/<peer>/address {url}` (Update address: the old address is probed once more, the new one must answer with the node id this board holds; audit row `address_changed`), `GET /api/nodes/discover?refresh=1` gains `moved` (the offers), a hub record gains `peer_api`, `api` and `needs_repair`, the relay answers `identity_changed` and `incompatible` as their own refusals, an unknown outcome carries `outcome: "unknown"` and `check_url`, and a rotation whose answer was lost answers `504 outcome_unknown`. The registry holds at most 12 nodes (`registry_full`). The run view of an epic gains `error_code` and `retry_at`, and a held issue the code `github_unavailable`.

**The demo.** `?demo=1&nodestate=unauthorized|identity|repair|incompatible|skew|offline` lays one state over build-box (open `#/n/build-box` and `#/settings?sec=nodes`); `nodestate=moved` shows Update address; `nodestate=repair` also plays a rotation whose answer is lost; `nodestate=unknown` makes every start or prompt on a node end in "outcome unknown"; `?demo=1&epic=rungithub#/epic/example/website/147` shows the GitHub trouble line. The default demo already shows stale with a skew chip and offline.

**Known limits.** The [two-node check](https://github.com/rpandox/ccboard/issues/155) exercised removal, re-pairing and competing claims; a real sleep and wake, rotation race and deploy outage remain to verify. The Activity list shows the hub's receipt time next to the row time only where the board sends one (`received_at`): the rows read from a paired node carry it; this board's own rows do not. A node on an older version has no audit route, so its rows are not listed and the page says it could not be read. The turn of an epic Claim or Work button after an unknown outcome is deliberate (the repeat is idempotent); a prompt typed into a session can still be sent again by pressing Send, after you have looked.

#### The epic worker

**Setting it up from Settings.**

1. Set `CCBOARD_PAGE_WIDEN=1` in the trusted settings file once, then restart the board.
2. Open **Settings > Options > Epics & worker > Worker**. Read the safety copy: "If on, an issue's text starts an agent on that machine with nobody pressing Run. Only for repos and authors you list."
3. Fill **Repositories** (one `owner/name` per line or comma separated), **Allowed authors** (comma-separated `login` or `login:id`; an id pins the account), **Look every** (30–3600 seconds, default 90), **At most per hour** (1–60, default 6) and **At most per day** (1–500, default 30). Enable the **Epic writes** prerequisite and **Worker mode**, then **Save**.
4. Review the trusted repositories, authors and limits in the confirmation dialog. Type `ALLOW WORKER` exactly. If the same save also turns on Epic writes, Phase 4 requires the combined phrase `ALLOW GITHUB WRITES AND ALLOW WORKER`.
5. Check the board's next-start sentence and the **saved, needs restart** badges, then use **Restart board**. The prerequisite check uses only configured authors or an already cached GitHub login; it never calls GitHub. Missing repositories, an unknown author or disabled writes refuse the save while worker mode is on.

Turning off, removing repositories or authors while the prerequisites still hold, and lowering limits need no phrase. Raising a limit does. With page widening off the whole Worker form is read only and shows the file lines. **Stop worker** and **Start worker** remain live, including while the worker is running but has been saved off; saving off takes effect only at restart. A worker previously stopped by a person stays stopped until Start worker is pressed.

The form demo is `?demo=1&workersettings=off|widenoff|ready|refusing#/settings?sec=options&group=epics` (choose one state). These are simulated saved settings; `&worker=off|idle|stopped|refused` independently chooses the live worker state.

With a hub, a person presses **Run**. The **worker** is the opposite: an idle node watches the epics of the repositories you name and starts the next ready issue **by itself**, with no hub and nobody present, so an epic keeps moving while the hub is off, asleep or elsewhere. It is off by default, it is a separate switch from the hub-driven Run (which stays the default way to work), and it adds no new launch path: it calls the same local work route as **Work** and **Run**, with the same author check, no-bypass guard, redaction, fence and attempt limit.

**Read this before you switch it on.** The text of an issue starts an agent on this machine. The agent runs with `acceptEdits` in a worktree, nobody is watching, and **anyone who can create or edit issues in the listed repositories can steer it** by what they write (prompt injection through an issue body or title). The worker narrows that with allowlists and a label, but it cannot make issue text safe. So:

- **Use a private repository** that only people you trust can write to, and **a dedicated epic** for the work you want done unattended, not your busiest tracker.
- Keep `CCBOARD_EPIC_AUTHORS` short (or leave it empty so only the `gh` login of this node counts) and keep the list of repositories short.
- Permission requests still wait for a person like any session. A task that waits for one for 30 minutes is **parked** (see below), and nothing the worker starts can use `bypassPermissions` or `danger-full-access`.

- **Turning it on.** Set `CCBOARD_EPIC_WORKER=1`, `CCBOARD_EPIC_REPOS=owner/name` and `CCBOARD_EPIC_WRITES=1` in `/etc/ccboard/env` and rerun `./install.sh` (the work route needs the writes switch, and the worker says so plainly when it is off). The caps and the poll have their own keys (see the table under [Settings](../configuration.md#settings)). With the repository list empty, with no allowed author known (`CCBOARD_EPIC_AUTHORS` empty and the `gh` login not known) or with writes off, the worker **refuses to start**: no thread is made, the state says why and the Doctor row `epic-worker` **fails**. Whenever it is on the row **warns** and lists both allowlists. Off, the row is skipped.
- **What makes an issue eligible.** Every rule fails closed: anything not known is not eligible, and the first rule that fails is the reason shown. (1) The repository is listed and cloned here. (2) The issue is open and nobody holds it (a node's claim comment; a claim that cannot be read counts as held). (3) The epic's author and the issue's own author are allowed logins, read from the API as a user with a numeric id (never a name in the text, never a bot); a login whose numeric id changes is refused. (4) It carries the label `ccboard:ready`, and **the label was set by an allowed login**: the worker reads the issue's events and the newest event for that label must be `labeled` by an allowed user, so a label removed and put back by someone else, or events that cannot be read (or run past three pages of 100), make the issue not eligible. (5) The shared full edit-history check accepts every body revision and title rename of the issue and its epic; `edited`, `epic_edited` or `edit_unknown` explains a skip. An allowed edit after an outsider edit does not clear it. A permanent unknown (such as a missing editor or incomplete history) holds only that issue for an hour, and the worker checks the next candidate in the same cycle; edit checks rest the whole worker only when GitHub supplies a wait or reset time. (6) It does not wait for another issue (`depends on` outside the epic counts as open), is not in a dependency circle, is not pinned to another node and was not refused by this node in the last hour. (7) The shared routing check, against this node only: the agent is installed and logged in, the rate-limit window is below the epic's limit, no back-off, a free lane. (8) The work route then reads the text again and refuses with `changed` if it is not the text that was judged.
- **Limits.** One start per cycle at most, never more than the free lanes (a node with `CCBOARD_NODE_LANES=0` starts nothing: "no cap" is not a number of free lanes), at most `CCBOARD_EPIC_WORKER_MAX_PER_HOUR` an hour and `CCBOARD_EPIC_WORKER_MAX_PER_DAY` a day. The start is written to disk before the call, so the caps survive a restart, and a start the route refused is given back. GitHub trouble (a rate limit, `gh` logged out, an outage) rests the worker for at least five minutes, longer if GitHub names a wait. If `gh` cannot say who it is for a moment, a worker that is already running says **refused** with the reason, keeps its thread and looks again after the poll wait; only a person's Stop (or a shutdown) ends the loop. The page that shows the worker never runs `gh` itself: until the login is known it says the worker is waiting to learn it.
- **Waiting for a person.** A task the worker started that has waited for a person for 30 minutes or more is **parked**: one fixed, fenced comment on the issue, its claim released, the task and its worktree kept, the session flagged and an event raised. Nothing is deleted. The issue is then held for 24 hours and skipped for as long as its record says parked, so the next cycle does not start it again while its first session still waits; running the issue by hand replaces the record.
- **Stop worker.** A signed-in person only (the hook token, MCP and device tokens, a node token and the hub get 403, and the `X-CCBoard` header is required). It works at once, with no confirmation, because it is the safe direction: nothing new starts from that moment, a claim the worker made that has no task is released, and a start already in flight finishes first (a start that was still being read when Stop came is dropped before anything is claimed). **Start worker** wakes a stopped worker at once and does nothing to one that is running, so it cannot be used to force cycles faster than the poll. The stop is kept: a restart stays stopped until a person presses **Start worker**.
- **Every decision is recorded** (start, skip with a fixed reason word, refused, cap, rest, wait, park, stop, resume, error): the last 100 are kept, the last 20 shown, each with the time, the kind, the issue as `owner/name#number` and the reason in a plain sentence. No title, body, login or path is in a record. An epic by a login that is not allowed is one decision for the epic, not one per child, and the page shows at most 20 skipped issues.
- **A worker and a hub Run** may compete for the same issue: the claim rule makes that safe (one claim wins, the loser takes the next issue) and the hub's pick already skips an issue with a live claim. Two workers on two nodes are the same.
- **The screens.** Settings > Nodes > **Worker** (right under **This node**) shows the state in words with a glyph (`✽ Working on example/website#12`, `✻ Waiting for a window until 14:30`, `✻ Paused by the daily cap until 09:00`, `✻ Resting, GitHub is not available`, `∙ Idle`, `○ Stopped by a person`, `✕ Refused to start`, `○ Off`), the repositories and authors it may use (read only), this hour's and today's starts against their caps and when a spent cap clears, the poll interval, the last 20 decisions with their reasons and **Stop worker** (or **Start worker** after a stop). Off, it explains the risk and links to Settings > Options > Epics & worker; when page widening is off it also shows the file lines. A paired node's page shows the same state read only, with the age of the reading (the hub rebuilds it from fixed words and checked numbers, never from text the node wrote), and says to stop it on that node's own board. The routes are `GET /api/epic-worker`, `POST /api/epic-worker/stop` and `POST /api/epic-worker/start`; the state is also in `state.node.epic_worker` and the node card, **only while the worker is on**.
- **Two things that differ from the issue.** The routes are under `/api/epic-worker`, not `/api/nodes/...`, so they cannot clash with a paired node's `{handle}` routes, and there is a **Start worker** route because Stop is kept across a restart. Stop and Start control the running worker; the Options form saves its setup for the next restart.
- **Limits you should know.** The check judges who edited, never what the text says. An allowed login that is itself compromised passes. GitHub lets an editor or admin delete a revision from history; if an older revision drops out of the list, that editor is invisible to this check. A missing newest revision is refused when `lastEditedAt` is more than one second newer than all visible edits and renames. Whether creation is a revision, whether deleted revisions stay visible, whether a token without write access can read history, and whether ticking a task-list checkbox counts as an edit are **UNVERIFIED** until the real-token box check (#155). Unknown answers refuse work. Unattended runs and actual GraphQL cost remain **UNVERIFIED** too. If someone with write access renames a label that an allowed author applied to `ccboard:ready`, GitHub may show the old `labeled` event under the new name (to verify), and the worker would then take that old event as the setting of the label. The claim protocol's attempt limit still counts each refused try, so an issue that keeps asking for bypass makes at most three claims before the worker asks for a person.
- **The demo.** `?demo=1` (open `#/settings?sec=nodes`, or `#/n/build-box` for a paired node) shows the worker at work; `&worker=idle|waiting|paused|pausedday|resting|stopped|refused|refusedwrites|refusedauthors|off` shows each other state, all ten kinds of decision are in the list, and **Stop worker** and **Start worker** work for the life of the page.

#### Starting an epic from the board

Until now an epic had to be made on GitHub first. **New epic** writes one from the board, in a sheet, after a preview. It is reached from **Tasks > Epics** (the **New epic** button), from a project's **More** menu and from the command palette (`new epic`, or `epic`).

- **What you type.** A repository (one of the GitHub remotes of this board's own projects, the project you came from first), an epic title and a goal, and up to 20 issue rows. A row has a title (up to 120 characters), a short description, a **tier** (**A, B, C or Check**, a segmented control), a **size** (**S, M or L**) and, for the second row on, an optional **Depends on** that names one row above it. Rows add with **Add issue** (or Ctrl+Enter, Cmd+Enter on a Mac, in a title), move with the arrow buttons or **Alt+Up** and **Alt+Down**, and are removed with **Remove** (or Delete on it), which offers an Undo. A dependency that a move would turn upwards is cleared and the row says so. Every message about a field appears beside that field and everything you typed stays.
- **Preview, then Create.** **Preview** (secondary) writes nothing. It shows the exact titles, labels and bodies (collapsed), the number of GitHub calls, about how long they take, and whether the repository is public or private (one read of the repository; "not known" when that read fails). **Create** (the one filled primary) is enabled only after a Preview of exactly what is on screen; any change, a row added, moved or removed or another repository disables it again. Next to Create the sheet says how many issues it will write, in which repository, whether it is public, and that **the board cannot delete them**. A `depends on #[row 2]` line and the epic's list say `#[row k]` in the preview where GitHub's number for that row goes at write time; everything else is what is written, byte for byte.
- **The switch.** Create writes to GitHub, so it works only with `CCBOARD_EPIC_WRITES=1` (the same switch as claims and work; default off). With it off, Create is refused before any command exists and the sheet says why next to the button, and **Preview still works**. Only a signed-in person can use it: the hook token, MCP and device tokens, a node token and the hub get `403`, and there is no MCP tool and no node route for it. The repository must be one of this board's own projects' remotes (`404` otherwise, before anything is asked of GitHub).
- **What Create writes**, in this order and nothing else: the labels `ccboard:epic` and `ccboard:epic-child` (only if no issue carries them yet; one that exists is fine), the epic issue, each issue, each issue attached to the epic as a sub-issue, and **one edit** of the epic's body that fills in its `- [ ] #N` list. One write at a time, at least 1.1 s apart, through the same serial queue as claims (30 a minute at most), so an epic of 20 issues is 44 writes and takes about 74 s in one request; the sheet says "Writing 21 issues, about 74 s" and keeps every value if the connection breaks. It stops at the first failure and lists which issues exist. The write queue's closed list has 11 shapes now (two more than before: attach a sub-issue and edit an issue's body), each locked to this purpose and checked against a body of exactly the generated form.
- **Resume, and no duplicates.** The epic issue and each issue end with a hidden marker line (`<!-- ccboard:epic <key> -->`, `<!-- ccboard:epic-child <key>-<row> -->`, the key made from the repository, the epic title and the issue titles). **Resume** (the same request again) and a Create typed again first look for those lines in the issues with the two labels that this board's own `gh` login wrote, then write only what is missing, attach only what is not attached and fill the list only if it is not filled. A write whose outcome is unknown (a timeout, a broken connection) is never repeated blindly. The form is locked while it writes and after a stop, because a changed title is a different epic; **Edit as a new epic** unlocks it (what was written stays on GitHub). If the `gh` login cannot push to the repository, Create refuses before writing: GitHub would drop the labels and the issues could not be found again.
- **The template note.** Each issue follows the repository's issue template: Goal (your text and a `Size:` line), Why / evidence, Scope, Files, Tests and Acceptance (empty, for you to complete), **Who should do it**, Rules and References (a `depends on #N` line if asked). The "Who should do it" block comes only from a fixed table, the one in [CONTRIBUTING.md](../../CONTRIBUTING.md) (Tier A: Claude Opus high and Codex 6.1 Sol high; Tier B: Sonnet medium and 6.1 Sol medium; Tier C: Haiku low and Luna low; Check: Sonnet medium and 6.1 Sol), with the same `acceptEdits` and `workspace-write` posture on every line. It never names `bypassPermissions`, `danger-full-access` or `--yolo`, and a test parses every generated block with the same parser the board uses to read them.
- **Your text is data.** It is cleaned (control and direction-changing characters dropped, a title on one line) and put inside the template as text: a `<` is escaped, a line that starts with `#` or `depends on` gets a backslash, a code fence is broken up, so typed text can never become a heading of the template, a marker, a label, a flag or a command. Text that names a permission bypass, or holds something shaped like a secret, an email address, a personal path or a host name, is **refused beside its field and never edited**. Limits: 20 issues, titles 120 characters, each body 10,000.
- **Public repositories.** The issue text is a prompt that an agent may run later. In a public repository anyone can read it; the preview says "public: anyone can read what is written". Use a private repository for work you do not want published.
- **After Create.** The sheet closes, says "Created owner/name#12 with 3 issues. Run is on this page." and opens the epic's page (see [Epics](#epics)), where **Run** is the one filled button. The sheet does not start any work itself. Every created issue is logged (repository and number only) and left as an audit row of the `out` kind; no title or body is in either.
- **To verify.** The request that attaches a sub-issue (`sub_issue_id`, the issue's REST id), the issue-body edit, `gh` against a real three-child epic and whether GitHub's issue list returns bodies for the label reads that Resume depends on are **UNVERIFIED** until the two-node check (#155); every test uses a fake `gh`. Resume reads at most 500 issues per label.
- **The demo.** `?demo=1#/tasks?tab=epics` has the **New epic** button, and `#/tasks?tab=epics&new=1` opens the sheet at once (outside the demo too). `&newepic=writesoff` (Create refused with the reason), `fail` (stops at issue 2, lists what exists, **Resume** finishes with no duplicate), `unknown` (stops with an unknown outcome; Resume finds the issue it wrote), `private`, `norepo` and `down` play the other states; the default creates the epic and opens its page. The demo's preview is built by the page and held byte for byte to the board's by `tests/test_epic_new_demo.py`.

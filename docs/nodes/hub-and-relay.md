# The hub and the relay

For people who use one board to see and steer others.

[Back to the documentation index](../README.md)

In this page, "the box" means the machine that runs the board.

#### The hub read model

A board you look at (the hub) can show every paired board's projects, sessions, tasks and needs-you counts, with how old each reading is, without your browser ever calling another board (the page may only talk to its own origin). The hub's backend polls the nodes, keeps the last good reading of each, and serves the merged result from its own address.

**What a node offers: `GET /api/node/state`.** A small read-only answer, opened by a node token with scope `read` or by a signed-in person. It is built from the same project scan the page poll uses (the 2 second scan cache), so a hub polling every 20 seconds adds no scan. It holds: `api`, `node` (`id`, `name`, `url`, `version`, `now`), `etag_base`, `projects` (each with its repos: `name`, `slug`, `branch`, `dirty`; `slug` is `owner/name` of the repo's `origin` when that is a GitHub remote, else `null`), `sessions` (`tmux`, `project`, `repo`, `session`, `agent`, `state`, `needs_you`, `kind` = how it was started, `since`, `model`), `tasks` (`id`, `title`, `phase`, `agent`, `project`, `repo`, `branch`, `tmux`, `issue_ref`, `updated_at`, and only for a task that an epic's Work started on this node: `epic_phase` and, for a pull request, `epic_pr`), `needs_you` (`permissions`, `input`, `errors` counts), `usage` (the Claude and Codex windows, no account), `lanes`, `login_problems` (agent names) and `truncated`. It holds no prompt, reply, result, transcript, account label, e-mail address or path (project and repo names only). Task titles and session names are visible to every paired node that holds `read`: do not pair a board you do not trust with them.

Size: at most 200 sessions and 200 tasks (unfinished tasks and live sessions first), strings cut to 200 characters without control characters, the whole body at most 100 KB. If it is larger, finished tasks older than 24 hours go first, then ended sessions, then rows from the tail of the longer list; `truncated` is `true` whenever any row was left out, for the 200 cap too. The weak `ETag` (`W/"<etag_base>"`) is a hash of the body without `node.now`, so the same state keeps the same tag; `If-None-Match` that matches answers `304` with no body (and the node's time in `X-CCBoard-Now`).

**What the hub does.** Only when the registry has a row (a pair, or a `CCBOARD_NODES` entry): one scheduler thread, and a pool of at most 4 workers. Each node is polled every `CCBOARD_NODES_POLL` seconds (default 20, never below 5; a little random spread is added), with a 5 second timeout and the held `ETag`. A node that is slow holds one worker for at most its timeout and is never queued twice, so it cannot delay another node's reading. The card (`GET /api/node`) is read on the first good poll and then every 5 minutes. The hub only ever calls the addresses in its registry, with the token saved for that pair. A board with no paired node starts no thread, makes no request and stores nothing.

**The record of a node** (`GET /api/nodes/state`, `GET /api/nodes/state?handle=<handle>`, an `ETag` over everything but `age_s`): `handle`, `node_id`, `name`, `url`, `status`, `polled_at`, `last_ok_at`, `age_s`, `skew_ms`, `skew_warn`, `error_kind`, `card`, `state`, `etag`, `legacy`, `scopes`. The times are the hub's own clock. `name`, `url`, `handle` and `node_id` come from the registry, never from what the node says.

| Status | Meaning |
| --- | --- |
| `online` | The last good reading is at most two poll intervals old |
| `stale` | The last good reading is at most 10 minutes old; its card and state are still shown, with the age |
| `offline` | Older than that, or never read. A restart shows the last reading as old as it really is |
| `unauthorized` | The node answered 401 or 403: the pair was revoked or its token was replaced. The row says "re-pair" |
| `unpaired` | The node answered 404 on a node route, or it reports another node id than the registry holds (`error_kind` `identity_changed`) |

`error_kind` says why the last poll failed: `timeout`, `refused` (also a refused redirect, an address that no longer passes the address rule), `tls`, `http_5xx` (any other error status), `bad_body` (not JSON, or not the right shape), `too_large` (over 100 KB) or `identity_changed`; it is `null` after a good poll. A failed poll changes `status`, `age_s` and `error_kind` only: the previous card and state stay.

**Skew.** `skew_ms` is the node's `node.now` minus the middle of the request (the hub's send time plus half the round trip). `skew_warn` is true above 5000 ms. Ordering across nodes never uses a node's clock. To verify in the two-node check (#155): skew on real clocks and poll cost on a loaded box (the 20 second default and the 300 ms target are not measured).

**A node's answer is untrusted.** It is rebuilt field by field: unknown keys are dropped, strings cut to 200 characters without control characters, lists to their caps, numbers checked, and a node whose answer names another node id than the registry row is not merged. Nothing a node sends is written into the hub's database except the last good record, kept in kv `node_last` at most once a minute (and at shutdown) and read back at start; the pair's own registry notes (`last_seen`, `needs_repair`) are not peer data.

**Where the hub shows it.** `GET /api/nodes` lists each node with its `status`, `age_s`, `polled_at`, `last_ok_at`, `skew_ms`, `error_kind`, `scopes` and `counts` (sessions, working, needs you, open tasks). `state.nodes` keeps today's shape (`{value: [{name, url, online, ...}], at}`), now built from these records (an offline node keeps its last numbers); `state.nodes_enabled` is true when the registry is not empty. `CCBOARD_NODES` (legacy) rows are polled by the same threads the old way, `GET /api/node/summary` with the hub token, and fill only the summary fields (no card, no state).

#### The hub view

With at least one board paired, the screens you already use show the others. This section is the reading; the actions on another node are in the sections after it. Nothing changes on a board with no paired node: the page loads none of this, asks nothing at `/api/nodes*` and draws every screen as before.

- **Home > Nodes** (after the away line, before the inbox): this board first, then a cell per node: its name, a glyph and a word for its state (`online`, `stale 3 min`, `offline since 09:14`, `re-pair`), `4 live`, `2 need you`, and the 5-hour pill (`5h 42%`, `5h n/a` without a reading). A tap opens the node page; an offline cell is dim and says how long ago it was last read. The line above the cells counts what waits elsewhere (`2 need you on build-box`); the bar at the top and the app badge still count this board only.
- **Home > Other nodes** (issue #82, after the project blocks): the sessions of the paired nodes that do not need you, read only, one group per node under its name (and a link to its page) with the state glyph and word of the node. A row has the session's state and agent glyphs, name, `project/repo`, the node chip and its age; a tap on the name opens that node's session peek (`#/n/<handle>/s/<name>`). The rows are the hub's last reading of each node (the same trimmed state the cells and the node page read), so Home asks no node for them: a stale node says `last reading 3 min ago`, an offline node's last reading is dimmed with its age. Sessions that need you stay in "On other nodes" under the inbox and are not listed twice; the Home state chips narrow these rows too, a node shows ten rows and then **Show all** (its page), and the block folds like the project blocks (remembered on the device).
- **Node page** `#/n/<handle>`: the name, the state with the age of the reading, system, version, **Open board** (the node's own address in a new tab) and the sections Needs you, Sessions, Tasks, Repos (GitHub slugs) and Account windows. A row opens a read-only peek (`#/n/<handle>/s/<name>`, `#/n/<handle>/t/<id>`) with the row's fields and **Open on <node>**; there is no iframe. **New task here** and **New session here** open the launcher with that node chosen when the pair holds the scope and the node answers (see [Starting work on another node](#starting-work-on-another-node)); a backlog task's peek has **Start on <node>**; a session's peek shows its **Tail** when the pair holds `sessions` ([the stream relay](#the-stream-relay)). A session's peek also has the steer panel (a Reply box, **Ack**, **Keys**, **Kill session on <node>**) and a waiting permission request as a card, when the pair holds `sessions` and `permissions` ([Steering a session on another node](#steering-a-session-on-another-node)); without the scope the controls are shown but off, each with its reason (`needs the sessions scope on build-box`). A node that refused its token shows **Re-pair** (Settings > Nodes); an old reading says how old it is and why the last try failed.
- **Chips**: a neutral bordered chip (two letters and the node's name, a glyph when the node is not online) on the rows of other nodes; this board's rows wear a dim one once a node is paired. **Needs you** and Home list the other nodes' items under "On other nodes" (a permission request of a node whose pair holds `permissions` is a card with **Allow** and **Deny**); **Tasks** has a segmented filter (All nodes, This node, each node) and the other nodes' tasks.
- **Sidebar**: "This node" as before, then a collapsed group per node with its needs-you count and up to 20 sessions (`more` opens the node page). **Palette**: Go to a node, Open board on a node, remote sessions and tasks with their chip, `@build fix` narrows to one node (its handle, its name or a unique start of the handle; `@local` is this board). `g n` goes to the first node.
- **Settings > Nodes**: under each paired node, the hub's reading: state and age, a clock warning above 5 s, agents and accounts with their windows.
- **How it reads**: the page asks `GET /api/nodes/state` on its own address every 6 seconds while the tab is visible (`If-None-Match`; a 304 keeps what it has, a failure keeps the last reading and says how old it is). Page code never calls another board. Names and titles from another board are shown as text only, and a node's address is made a link only when it is an https tailnet name or address.
- **Screens**: Home with the strip, a node page, a peek, the sidebar groups, the palette with `@node`, Tasks with the filter and Settings > Nodes (the owner refreshes their screenshots).

To verify in the two-node check (#155): the view against two real boards and an iPad.

#### The relay

The one way a hub board may ask another board to do something: a closed table on the hub, thin wrappers on the peer that accept only a paired node's token, one guard that strips every field that would widen a permission, an audit row on both boards, and per-pair rate limits. Phase P7 shipped the table, the guard and the rows that read; phase P8 added the first rows that start work (a task, a dispatch, a session) and the stream; phase P9 adds the rows that steer a session and answer a permission request (#142). Each row of the table has a scope, a guard review, a refusal test and an audit action.

**The table.** `RELAY` in `app/nodes_relay.py` has one row per action: name, hub route, peer route, scope, body model (`extra="forbid"`), rate class and audit action. The table is data: adding a row adds a hub route, a peer wrapper and its refusal tests (`tests/test_nodes_relay.py` generates them from the table), and nothing else makes a route reachable. Importing the module puts the peer routes into `NODE_ROUTES`.

The [single scopes and routes table](../security.md#node-scopes-and-routes) lists both sides of every relay, including the stream and epic rows.

The write rows are in the write bucket (30 a minute per person on the hub, per pair on the peer), start or steer an agent (so the guard runs on both boards, for `prompt` and `keys` too) and are human-only (the two task rows are the exception named in the [MCP section](agents-and-mcp.md#using-nodes-from-an-agent)). The six rows of phase P9 also need an acting user (see below). The stream is not a row of `RELAY`: it answers an event stream, not one JSON object, and has its own module (`app/nodes_stream.py`) and tests.

**On the hub, in this order, and no request is made when one refuses.** (1) Who asks: a signed-in allowed person with `X-CCBoard: 1` (even for a GET), at most 120 reads and 30 writes a minute each (`429` with `Retry-After`). **Every row is human-only except four: the local hook token, which every agent session on the box holds, and a device token of `/mcp` get a `403` on all the others**, so an agent cannot steer other nodes through the hub. The four rows `state`, `task`, `task_create` and `task_dispatch` (lane mode only) carry `mcp` in `RELAY` (each with the narrower body an agent may send and the reduced answer it gets) and are open to an agent only while `CCBOARD_MCP_NODES` grants the row's scope (`read` for the reads, `tasks` for the writes) and only for the caller's own scope (see [Using nodes from an agent](agents-and-mcp.md#using-nodes-from-an-agent)); a row cannot say `mcp` and be a prompt, keys, a close, a permission, a screen or a stream, and a test walks the table to prove it. Nothing opens by default. A node token is a `403` (there is no chaining). The acting user sent to the peer is the authenticated login only, never a header, query or body the caller sends. (2) Which node: `local` is a `400`, an unknown handle a `404` (the target comes from the registry only, never from the request), a node with this board's own id or address a `400` (no relay to yourself), a legacy `CCBOARD_NODES` row a `409`. (3) The scope: the pair's granted scope must hold the row's scope, else `409 needs the read scope on <node>`. (4) The status: `unauthorized` or a pair marked `needs_repair` is `409 re-pair`, `unpaired` is a `409`, and a node the hub tried and could not read for 10 minutes (or never) is `503` with the reason and the age. A node the hub has not read yet (no poll has finished, for example in the first seconds after pairing) is a `409` "not read yet" and nothing is sent: a relay waits for a known `online` or `stale` reading. (5) The body, with the row's model and, for a row that starts or steers an agent, the guard: a `422` with the same sentence the peer would give. (6) The call: the address rule at the call, timeout 10 s, request body at most 256 KB, answer at most 512 KB, no redirect. The peer's `401` becomes `409` (re-pair) and the pair is marked, its `403` a `409` scope message, a `404` stays a `404`, a `429` stays a `429` with its `Retry-After`, a `5xx`, a redirect, an over-size answer or a failed connection is a `502`, and a timeout after the request was sent is a `504` "could not confirm" and is never retried. (7) The answer is `{node: <handle>, age: 0, data: <the peer's JSON>}` (`age` is how old the answer is: 0 for a live call; an offline refusal carries the age of the last good reading). The peer's JSON is rebuilt from a whitelist, as the hub read model does, and nested under `data` because the state already has a `node` key. Errors are `{error, reason, node}`: `reason` is one of `forbidden`, `csrf`, `human_only`, `mcp_off`, `mcp_level`, `mcp_scope`, `not_read_yet`, `local`, `bad_handle`, `unknown_node`, `self`, `legacy`, `scope`, `needs_repair`, `unpaired`, `offline`, `invalid`, `too_large`, `bad_address`, `unreachable`, `unconfirmed`, `redirect`, `bad_answer`, `wrong_node`, `peer_error`, `rate_limited`, `not_found`, `refused`, `repo_missing`, `stream_limit`, which the page turns into a plain sentence.

**On the peer.** The auth middleware has already checked the token, the pair's bucket for the row's rate class (reads 120 a minute, writes 30, `429` with `Retry-After`), the scope and the size. The wrapper checks the scope again, reads the query or JSON body with the row's strict model and the guard, calls an internal function (never an HTTP call to itself), stamps `origin` where a task or session is created (later rows), and writes one `in` audit row with the caller's node name, the acting user the caller reported (`for <login>`) and the action and target. The peer applies every check itself and never trusts that the hub did. A signed-in person or the hook token reaches a wrapper and is refused with `403` (they have the board's own routes). The acting user is kept as text only (printable, 64 characters at most, token-shaped words replaced) and decides nothing. The card and state routes audit a call only when it carries an acting user, so the hub's own 20-second poll writes no rows.

**The guard** (`guard_launch`, for every row that starts or steers an agent: `task_create`, `task_dispatch` and `session_open`). It refuses, each with a plain sentence that never repeats what was typed: a `permission_mode` other than `default`, `acceptEdits` or `plan`; a `mode` other than `default`, `acceptEdits`, `plan` or `read-only`; any bypass flag or acknowledgement that is set (a field named like `bypass`, `yolo`, `dangerously_*`, `skip_permissions`, `acknowledged`, and whatever the board's own task rule reads as one); `args`, `add_dirs`, `allowed_tools`, `disallowed_tools`, `append_system_prompt`, `tools`, `mcp_config`, `config` and `settings`; a Codex `sandbox` other than `read-only` or `workspace-write`; a Codex `approval` other than `on-request`; the spellings `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--dangerously-bypass-approvals-and-sandbox`, `--yolo`, `danger-full-access` and `bypassPermissions` in any string at any depth, in any case, with look-alike dashes and invisible characters taken out; an agent other than an installed adapter; and the `shell` launcher. A remote instruction is data and never consent: nothing a hub sends answers a permission request on this board.

**What the read rows show.** The task row is a fixed list of fields rebuilt on both boards: title, phase, agent, project, repo, branch, tmux name, issue, times, slug, mode, base branch, pull request number and state, and whether a result exists; never the prompt, the result, a worktree path, a session id or who started it. The agents row lists each installed agent with the launcher's controls and values a node may use (no bypass, arguments, tools, config or directories, and no `danger-full-access`, `bypassPermissions` or `shell` choice), without the account block that can hold an e-mail address. **Screen text is session content, not names and counts, so the pane row needs the `sessions` scope, not `read`.** It is the last 40 lines at most (`lines=1` to `40`, plain digits), each cut to 400 characters, with control, zero-width and bidirectional characters taken out; the login session (it shows codes) is never offered. It is cut to the last 40 lines of 528 characters first (nothing longer ever reaches a pattern; on the peer and again on the hub), then redacted before it leaves the peer and again on the hub. Key blocks of any label; the board's own node, device, hook and hub tokens (a token that tmux wrapped over several lines too); URL credentials and connection strings (`scheme://user:password@host`, `postgres://`, `mongodb+srv://`, `redis://`); `Authorization:`, `Cookie:`, `Set-Cookie:` and `X-...-Key`/`-Token` header lines; `Bearer` and `Basic` values; `sk-ant-`, `sk-` (including `sk-proj-`), `ghp_`/`gho_`/`ghs_`/`github_pat_`, `AKIA`, `AIza`, `sk_live_`/`rk_live_`/`pk_live_`, `npm_`, `glpat-`, `hf_` and Slack `xox` keys; JWT-shaped text; `--token VALUE` and `--password=VALUE` flags; the value after any name that holds password, token, secret, credential or key (`NAME=VALUE`, `export NAME=VALUE`, `NAME: VALUE`, quoted or not); and 32 or more key characters after `=` or `:` become `[redacted]`. Bare git hashes in a log stay visible. **Redaction is best effort, not a guarantee**: a secret in a shape that is not on that list goes through. That is why the row needs the `sessions` scope, why only a signed-in person can ask for it, and why `read` never shows a screen.

**Audit.** The hub writes an `out` row and the peer an `in` row for each call, and a failed or refused call writes one with its reason (`scope: needs the read scope on build-box`, `offline`, `not_found: no such task`). No row, log line or answer holds a token, a pairing code or a prompt body (the tests seed a marker string and look for it in both databases, the answers and the log). The acting user on the hub is the signed-in login or `local-token`; on the peer it is recorded as a claim (`for <login>`) and never used for any decision. A board with no registry row writes no audit row for a relay that found no node. Rows are kept 90 days.

Every text field of a peer's answer (task titles, branch names, error text) goes through the same redaction on the hub, and every size is capped before any pattern runs (the hub also refuses an answer over a row's size: 16 KB for a task, 64 KB for a card or a screen). A relay refusal text from another board is shown as capped plain text, and an audit target, user or reason is cut and cleaned before it is written. To verify in the two-node check (#155): a refusal and an audit pair seen across two real boards, the 10-second timeout over a real link, and the pane tail and its redaction against a real tmux.

#### Starting work on another node

From the board in front of you, start work on a paired node: create a task there (now, or as a card in its Backlog), hand one of its Backlog tasks to a new session, or open a plain session in one of its repos. The worktree, the branch and the tmux session are made by the node itself, with its own code; the hub never creates a worktree, clones a repo or edits the node's projects.

- **The launcher.** With the hub view on and at least one paired node online, the sheet of **+ session** and **+ task** gets a **Node** control at the top: `This node | build-box` (a native select above four options). Choosing a node swaps in a smaller form built from that node: its projects and repos (the hub's last reading), its agents, models, efforts and reasoning levels (the agents row, read once per node and kept 10 minutes), and the agent choices it has installed and logged in. A session form has the project and repo, an optional session name, the agent, the model, the effort or reasoning level and the permissions (`ask`, `accept edits`, `plan`; Codex `default` or `read-only`). A session from another node starts **without a first prompt**: open it on its own page (the toast has **Open on <node>**) to type. A task form has Run (**Now** or **Later**), a title, the prompt, an optional issue (`owner/name#123`), the agent and model options, and Close the session when it finishes. The sheet's title and Start name the node, and the command preview is labelled **Command on <node>**. **New task here** and **New session here** on the node page open the same sheet with the node chosen.
- **Hand over a Backlog task.** The peek of a task in a node's Backlog has **Start on <node>**: the launcher in dispatch mode, with the node fixed (a task id exists on one node only, so a task of this board cannot be sent to another node, and **chains stay inside one node**: a request that names `after_task_id` is refused with that sentence). **New session** starts it in a fresh lane; **Running session** pastes it into an idle session of the same repo and needs the `sessions` scope as well as `tasks`.
- **No bypass, ever.** The form offers no bypass, auto or `dontAsk` mode, no extra arguments, tools, directories or system prompt, no schedule and no `I understand` box; it says **Bypass is only available inside a devcontainer, on the node itself.** The hub runs the strict model and the guard before it calls, and the node runs both again on its own (`permission_mode` only `default`, `acceptEdits` or `plan`; Codex sandbox only `read-only` or `workspace-write` with approval `on-request`). A card saved on the node with arguments, tools, directories or a permission mode outside that set is not started from another node (`409`): start it on the node itself. **A remote launch never inherits a local default.** When the request leaves the permission out, the node writes an explicit one on the line it types: Claude `--permission-mode manual` (what `default` means; a line with no flag would leave the mode to Claude Code's own `settings.json`, which can say bypass), Codex `-s workspace-write -a on-request` (`-s read-only` for `plan` or `read-only`; a sandbox given alone still gets `-a on-request`), and no subagent-model override from `CCBOARD_SUBAGENT_MODEL`. A card keeps its own narrower choice (a card saved with `plan` stays `plan`). The options a launch ends up with go through the guard on the node as well, and the line it is about to type must say its permissions and stay inside the set, else nothing starts (`400`). **A task handed to a running session** (mode `session`) runs with that session's permissions, so the node checks the session itself: it must be one of this board's own sessions (not a tmux session the board did not start, not an internal one) in the task's repo, and the line the board recorded for it must be exactly a line the board's own adapters write (an allow list: it must tokenise and be the canonical quoting of its tokens, start with `claude` or `codex` after at most the `env` of the two subagent-model names the board sets itself, and hold only known flags with values of the shapes the board writes, each once: Claude `--session-id`, `--resume`, `--continue`, `--fork-session`, `--name`, `--model`, `--effort`, `--fallback-model`, `--worktree` and one `--permission-mode` of `manual`, `default`, `acceptEdits` or `plan`; Codex `--no-daemon`, `--no-alt-screen`, `-m`, `-c check_for_update_on_startup=false`, `-c model_reasoning_effort="…"`, one `-s read-only|workspace-write` and one `-a on-request`, and `--dangerously-bypass-hook-trust` only while `CCBOARD_CODEX_HOOK_TRUST=bypass`). Any other flag (`--add-dir`, `--mcp-config`, `--allowedTools`, `--profile`, `--search`, `-c` of another key ...), a wrapper (`sh -c`, `devcontainer exec`), an env override, chaining or a stray argument is refused, so a session started with extras is started from its own board. The same function checks the line a remote launch is about to type. A session started with `bypass`, `auto` or `dontAsk`, or with no mode on its line (Claude Code's `settings.json` decides then, which the board cannot read), is refused with `that session runs with wider permissions than another node may use, or its mode cannot be read; start it from its own board` (`409`). A mode changed inside the session after it started (Shift+Tab) is not seen. Every string a node sends has its own rule (one helper on both boards, also used for a stored card and for stream names): model, effort, agent, names, session, issue reference and the permission words are anchored patterns or enums with a length cap, and must be unchanged by Unicode normalisation (full-width look-alikes are refused). Title and prompt are free text, but a control, format or line-separator character (Ctrl-C, Escape, a lone CR, U+2028/2029, a bidi control, a zero-width character) is a `422`, because a task's prompt is typed into a terminal; a stored card that holds one is not started from another node.
- **Result.** The row shows at once (the Tasks page for a task, the node page for a session) as **Starting on <node>**, becomes started only when the node's answer carries a `ref` (`<handle>:<id>` or `<handle>/<tmux>`, built by the hub), and is taken away if the node refuses; the form keeps everything typed. The toast says **Started on <node>** with **Open on <node>** (the node's own page, a new tab; only a tailnet https address is made a link) and, when the node's Claude window is nearly full, **Started anyway: the 5h usage window is at 91%**: a hand start is never held. The task row on the node carries `origin` (the calling node and the login it reported; stored, not shown anywhere yet).
- **When it cannot.** Start is off, with the reason on the form: `build-box is offline, last seen 4 minutes ago`, `build-box no longer takes this board's token: re-pair it in Settings, Nodes`, `needs the tasks scope on build-box`, `build-box has not been read yet`. Nothing is queued for later. A repo the node does not list reads `<repo> is not on build-box. Nothing was created.` (with the clone path when the hub's own copy of the repo has a GitHub remote: only `owner/name`, never the remote's URL, a user name or a path). **A timeout, or a connection that breaks after the request was sent, is `unconfirmed: build-box did not answer in time; check its board before trying again` and is never retried**: the task may exist on the node.
- **Remembered per node.** The last agent, model, effort or reasoning level, permissions, Run and Close choice are stored per node and repo (`ccboard:launch:<handle>/<project>/<repo>:<agent>`, `ccboard:task:<handle>/<project>/<repo>`, `ccboard:agent:<handle>/<project>/<repo>`, `ccboard:nlast:<handle>`); the keys of this board's own repos are never written. A saved choice the node no longer offers is explained in the form and replaced by the node's default.
- **Audit.** Both boards write a row (`create_task`, `dispatch_task`, `open_session`) with the acting user; the target may hold the task title cut to 80 characters (secret-shaped text replaced), and the prompt is in neither row nor in any log line or answer.

To verify in the two-node check (#155): a task started on the box from the Mac with its worktree and `origin`, and the launcher at 1280, 1024 and 390 pixels.

#### Steering a session on another node

From the board in front of you, reply to a session that runs on a paired node, press a few keys in it, acknowledge it or end it, and allow or deny the permission request it is waiting on. All of it goes through six rows of [the relay](#the-relay) (`prompt`, `keys`, `ack`, `close`, `permissions`, `permission_answer`), and the scopes are opt in per pair: `sessions` for the first four, `permissions` for the last two.

**A remote answer is a person's decision.** A permission request is the agent asking its owner. The hub route takes a signed-in allowed person with `X-CCBoard: 1` and nothing else: the local hook token, a node token and any user made from a node get a `403` and an audit row. There is no "auto-allow remote" setting, no MCP tool, no scheduled job and no relay row that reaches the answer, and the tests say so in code. The peer trusts the hub to pass on a person's choice and records the name the hub reports (`for <login>`); it cannot check it. That is why `sessions` and `permissions` are off until you turn them on for that pair, and why the card says so.

**A session started with wider permissions cannot be steered from another node.** Typing into a session is launching work in it, so the peer applies the same allow list as for a task handed to a running session: the target must be one of its own agent sessions (not a shell, not one it did not start, not the login session) and the line recorded for it must be exactly a line the board writes with a Claude permission mode of `manual`, `default`, `acceptEdits` or `plan` (Codex `-s read-only|workspace-write` with `-a on-request`). A session started with bypass, `auto` or `dontAsk`, or whose mode cannot be read, is refused with `that session runs with wider permissions than another node may use, or its mode cannot be read; start it from its own board` (`409`) for the prompt and for keys. Ack and close run nothing, so they may touch such a session, but every row that names a session (prompt, keys, ack, close, a dispatch into a session, and the session of a permission request) first runs the same ownership check on the peer: a ccboard name that is not the login session, a row this board opened (not a tmux session the owner started outside the board), an agent session started by one of the board's own launchers (not a shell, not a clone), in a project and repo whose folder is on the peer (`409` otherwise). Close ends a session with a terminal attached too, exactly as the local `DELETE` does.

- **Prompt.** Up to 8192 characters (more is a `413`). A control, format or line-separator character other than tab and newline is a `422`, because the text is typed into a terminal: it is refused, never silently stripped. A remote prompt, and the first prompt of a new remote task, cannot start with `/`, `!` or `#` (after any spaces or blank lines, full-width forms included), because the terminal reads those as commands (Claude Code runs a leading `/` of a launch argument too): it is a `422` on the hub and on the node, and a stored card that starts that way is not started from another node, in a session or a new one (`409`). The text goes through the guard (the dangerous spellings are refused wherever they appear). `queue: true` is accepted for a working session as it is locally; without it a busy session is a `409` with the peer's reason (`working`, `compacting`, `permission_pending`, `permission`, `elicitation`, ...) and how many seconds to wait, or none when waiting will not help. The text is typed once and never stored: the peer's own event says only "prompt from another node (N characters)". At most 20 prompts a minute into one session, counted on the hub and again on the peer. A slash command is not relayed in this version, and the page does not send a text that starts with one.
- **Keys.** `Enter`, `Escape`, `Up`, `Down`, `Tab`, `y`, `n` and `1` to `9`. `C-c` only with `confirm: true`, which the page sets on a second tap; `confirm` with any other key is a `422`. Anything else is a `422` and reaches no terminal. **A key cannot answer a permission.** Those keys also choose an option of a permission, trust or plan dialog, so while the session is asking a question in its terminal (a permission request waiting, a session waiting on anything but its idle prompt, no state yet, a Codex update or trust dialog, or a state the peer cannot read) the peer wants the `permissions` scope for any key and for a prompt too (`403`; the hub says `needs the permissions scope on <node>: this session is asking a question in its terminal`), and even then `y`, `n`, `1` to `9` and `Enter` are refused (`409`, code `asking`: answer with Allow or Deny) and a prompt is a `409` busy; only `Escape`, `Up`, `Down`, `Tab` and a confirmed `C-c` pass. The `permissions` scope and the Allow and Deny rows are the only way to answer one.
- **Permissions.** `GET /api/nodes/{handle}/permissions` answers `{permissions: [{id, tmux, tool, summary, since}]}` for live hook requests and recognized Claude tool approval dialogs whose session still exists (terminal entries also carry `kind: terminal_prompt` and `choices`; at most 50; the summary is cut to 300 characters and redacted on the peer and again on the hub, shown to the person and stored in no audit row or hub table). `POST .../permissions/{pid}/{decision}` takes `allow` or `deny` only: no `always`, no rule, no `tui`, no body. The list shows, and the answer accepts, only a request of one of the peer's own agent sessions for an ordinary tool (Bash, Edit, MultiEdit, Write, NotebookEdit, Read, Glob, Grep, WebFetch, WebSearch, apply_patch or an MCP tool) with a summary; a plan approval, a question to the person, a mode or worktree switch and any other tool stay in the terminal (`409` `refused`, never listed). `allow` is a one-time allow: a live hook is told `behavior: allow` and nothing else (no rule, no mode). After the hook wait ends, a terminal entry has its own temporary ID; Allow and Deny send the exact one-time Yes or No number shown by the pane, checked again immediately before sending. A changed pane or an ID from before a board restart returns `409 changed` and sends nothing. Terminal answers are recorded as session events on the peer. An answered request is a `409` `answered`, an expired one (nobody waits for it any more) a `409` `expired`, a missing one a `404` `gone`; none of them decides anything. The answer is stored on the peer with the source `node <name> for <login>`.
- **Who may.** The six rows are human-only and need an acting user: a peer refuses a request that names none (`403`). A refused caller on a hub route that names a registered node leaves an `out` audit row (`local-token` or `node:<name>`); with no registry row nothing is written, so a single board is unchanged.
- **Truth.** A write that times out or breaks after it was sent is `unconfirmed` and is never retried. What the hub returns is rebuilt from a whitelist (a busy answer keeps a word list and a bounded number) and redacted again; no audit row, log line or answer holds the prompt, a key sequence beyond its name, the permission summary or a token.
- **In the page.** The remote session's peek (`#/n/<handle>/s/<tmux>`) has, when the pair holds `sessions`: a **Reply** box (Enter sends, Shift+Enter adds a line) with the session's quick replies above it, **Ack**, **Keys** (the closed list above, `C-c` after a second tap) and **Kill session on <node>** (two taps, red outlined). Each shows its state at once and a toast that names the node; a refusal shows a plain sentence in the panel and in the toast and keeps the draft; a timeout reads "Could not confirm whether build-box got this. Check the terminal before answering again." Without the scope the peek keeps the disabled controls and says which scope is missing; with the scope but an offline node they are disabled with the age. A permission request of a node whose pair holds `permissions` is a card in the **On other nodes** group (Inbox and Home), on the node page and on the peek, with the tool, the summary, **Allow** and **Deny** (Allow is filled only on the lead card), one tap from Home. It turns into "Allowing on <node>…" at once, "Allowed on <node>" appears only when the node confirmed, and a refusal puts the card back with the reason. The list is read only for a node whose reading says a request waits and only while the page is visible (every read leaves an audit row on both boards), so a quiet node costs nothing. The palette has **Reply to <session> on <node>** and **Allow** / **Deny** for the lead remote request, and its send mode takes remote sessions; on the peek `r`, `a`, `y`, `d` and `o` work as they do locally.

To verify in the two-node check (#155): a prompt, keys and a permission answer across two real boards, the acting user is a claim the peer cannot prove, and the screens at 1280, 1024 and 390 pixels.

#### The stream relay

A remote session's tail updates live on the hub's own page, and the browser never contacts the other node. The hub opens one upstream stream per request to the peer's tail route, parses and checks every event, and writes its own events to the browser.

- **Peer:** `GET /api/node/stream?names=a--b--c,...&lines=12` needs a node token with the **`sessions`** scope (`read` is not enough: a tail is session content). It is the same generator as the board's own `/api/stream`, with `names` required (1 to 20 ccboard session names, no repeated or unknown query keys) and `lines` 1 to 40; a bad name or count is a `400` before the stream starts. Every tail is cut to the line and width caps first and redacted second, exactly as the pane row does, and the tick lists only the names asked for.
- **Hub:** `GET /api/nodes/{handle}/stream?names=&lines=` for a signed-in person with `X-CCBoard: 1` only: the local hook token and a node token are `403`. It checks, in this order: who asks, the per-person read bucket, the handle, this board itself, a legacy row, the `sessions` scope (`409`), the names and lines, the node's status, the caps, then opens the upstream through the pinned HTTPS connection the relay already uses (TLS verified, the address rule at the call, no redirect). A node that is offline, needs a new pairing, is unpaired or has not been read yet is **one `gone` event with status `200`** (an `EventSource` cannot read an error body); a missing scope, a bad handle, bad names and the caps are JSON errors.
- **Events the browser gets:** `retry: 5000` first; `lines` `{name, lines}` (a name from the asked set, at most the asked count and 40 lines, each at most 400 characters, control characters out, secrets redacted again on the hub; sent when the tail changes); `tick` `{sessions}` about every 2 s; a `: ping` comment every 15 s while nothing else is sent; and at the end always `gone` `{reason, message, final, dropped}`. The reasons are `offline`, `repair`, `unpaired`, `not_read_yet`, `upstream_error`, `closed`, `idle` (no valid event for 60 s), `too_large` (a line or event over 64 KB), `revoked` (the pair was removed, or the peer answered `401`) and `shutdown`; `final: true` (`repair`, `unpaired`, `revoked`, `shutdown`) means do not reconnect. **Only `lines` and `tick` cross**: anything else, a name that was not asked for and bad JSON are dropped and counted in `dropped`; no upstream byte is copied through.
- **Limits and cleanup.** At most 2 live streams per node, 6 per signed-in person and 8 on a hub (the next is `429` with `Retry-After: 5`, and says which cap); one bounded daemon thread reads each upstream and never touches the database. The upstream is closed within about a second of the browser leaving, on `gone`, on hub shutdown, when the pair is removed and when the peer answers `401`. No new dependency: the upstream is read with `http.client` over the existing pinned connection. Audit: one `out` row on the hub and one `in` row on the peer per open (the session names, never tail text).
- **In the page.** `Live.subscribe(ref, fn)` takes a `Ref`: a remote one shares **one `EventSource` per node** at `/api/nodes/<handle>/stream`, a local one (or a bare name) keeps the page's single source at `/api/stream`, and the last unsubscribe of a node closes its source. After a `gone` the tile **keeps its last lines** and says `offline, last seen 09:14`; the page reconnects after 5, 10, 20 and at most 30 seconds (never more than one try per 5 s per node), and not at all after a final `gone`. The session peek of a node shows the **Tail** (`The last captured lines of the session, not a terminal.`) when the pair holds `sessions`, else the controls that need it keep their reason. In `?demo=1` a remote tail is read once from the demo fixture.
- **What this exposes.** A tail holds whatever the agent printed, including secrets it saw. Giving a board the `sessions` scope lets every person signed in there read the tail of every session on this board. The redaction (key blocks, this board's own tokens, URL credentials, `Authorization` and `Cookie` lines, provider keys, `NAME=VALUE` for names that hold a secret) is best effort on both boards. Only a signed-in person reads the stream; an agent session's hook token cannot.

To verify in the two-node check (#155): the stream through a real Tailscale Serve with buffering, a revoked pair ending the stream on a real link, and open sockets over a day on the box (a target, not a measurement).

#### Remote terminals and tiles

A session on a paired node is one tap from its own terminal, and the quad and the terminal dock can hold it as a live tail with a prompt box. Nothing here frames a terminal of another origin, proxies a WebSocket or changes the Content Security Policy.

- **Open terminal on <node>.** On the node page (an icon in every session row), the session's peek, the permission cards in the Inbox, a tile of the quad and in the palette (`Open terminal on <node>`, for the peek in front of you and, once you type, for any remote session). It opens `<the node's address>/term/<session>` in a new window with `window.open(url, '_blank', 'noopener')`, straight from your browser to that node: no request goes to this board or to the node's API. The link is built only when the node's saved address is an https tailnet address (`Nodes.boardUrl`) and the session name passes the name rule (no slash, dot, quote or space); otherwise the control is disabled and says why. A browser that returns no window (a blocked pop-up, and every window opened with `noopener`) leaves a link to tap in the place of the button. A node that is offline, stale or needs a new pairing says so under the control ("old-laptop is offline since 09:14. The link is still here and opens once old-laptop is back."), and the control stays.
- **The browser needs an identity on that node.** The terminal and code-server ports do not check the allowlist: the tailnet policy and the node's own access rules decide who gets a shell. Open the link from a device with a Tailscale identity (a device owned by a user); a tagged device carries none, and the node answers it with a `403` (as Tailscale documents it; not yet tried on the box). The push or ntfy **Terminal** action of a remote session already points at the node that sent it (each node notifies for itself, with its own `CCBOARD_PUBLIC_URL`), so it opens that node's own `/term/` page and needs the same identity.
- **A tile of another node (the quad).** An empty tile's pick list groups sessions by node (**This node**, then one group per paired node; an offline node shows `offline since 09:14`). A tile for a session of another node shows the node chip, the session and its state, the word **Tail**, and an **Open terminal** icon in its header, and in its body the last 12 lines from the stream relay (read only, scrolled to the bottom; every line is text), one status line and a one-line prompt field. The prompt field sends through the `prompt` relay row, so every refusal is the plain sentence of [the steer rules](#steering-a-session-on-another-node): needs the `sessions` scope, the session is asking a question, wider permissions, cannot start with `/`, `!` or `#`, busy (with **Queue it** for a working session), offline, "could not confirm". Enter sends and Shift+Enter is refused, as in the docked box of a local tile; the draft stays on any failure. The tile never creates a framed page (a test pins it), the quad's store holds `{node, tmux}` for it (a bare name is still this board's), and the tile menu says why there is no Tune or slash command. `o` on a focused remote tile opens its terminal; the key exists only on a board with paired nodes.
- **Offline and revoked.** The tile keeps the last lines, says `offline since 09:14` or `re-pair`, disables the prompt field with the reason and keeps the terminal link.
- **The dock.** From 1024 px, **Add to dock** in the tile menu shows the same tile in the terminal dock when you leave the quad (a header with the chip, the session, **Tail**, the terminal link and Close; 44 px targets on touch). It is not remembered across a reload.

To verify in the two-node check (#155): opening a remote terminal from a phone and a desktop, a tagged device's `403`, typing into a remote tile on real nodes, and the screens at 1280, 1024 and 390 pixels.

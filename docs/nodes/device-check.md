# Devices without a board and the device check

For people who add devices without ccboard and who turn on the device check.

[Back to the documentation index](../README.md)

#### Devices without a board

A device without a board is a machine on your tailnet that has no ccboard on it. It is not a node: no pair, no token, no relay, no tasks, no worktrees or clones, no worker. The board you are using starts agent sessions (Claude, Codex or a plain shell) in `tmux` on that machine over Tailscale SSH and reads them back. For devices that do run a board, see [Several devices](platforms.md#several-devices-issue-154-phase-p6).

**What it can and cannot do.**

| | On a device without a board |
| --- | --- |
| Can | Start, list and stop sessions; open the normal terminal page for a session; show its state in the sidebar; show a Claude or Codex permission menu in **Needs you** with one-time **Allow** and **Deny**; paste a **Reply** into an idle prompt. |
| Cannot | Hooks (unless you install the optional state log), local notifications on the device, a worker, tasks, chains, worktrees, clones, previews, cost or transcripts. State is read from the screen, so it shows less than a board with hooks. |
| Notifications | The device sends none. The board sends its usual notice for a terminal prompt, because the board read the prompt. |
| Stored | No password and no private key. Agent sign-ins stay on the device; sign in there through the attached terminal. |

**The tailnet rule.** Enable Tailscale SSH on the device. The list offers only your own devices: online ones on your account and tagged ones, never a device shared in from someone else. Grant the board access to the dedicated user only, with an SSH ACL rule: `check` (12-hour check period) when the board host is untagged, `accept` when it is tagged. Never put root in the rule's users. A check prompt shows only a Tailscale login link and **Retry**. The board pins the first host key in its data directory under `bare-ssh`; a changed key is refused until you verify it and press **Forget host key**.

**The dedicated user.** In **Settings > Nodes > Devices without a board**, choose a non-root account (default `ccagent`) and a projects folder relative to its home (default `projects`). The board refuses an account in `sudo`, `wheel` or `admin`, never goes on past an unreadable identity or groups check, and checks the user ID and groups again before every start. **Add and check** tests SSH, the numeric user ID, groups, system (Linux or macOS), tmux, Claude and Codex on PATH (sign-in is not checked) and the repositories below the projects folder. Each row has a pass or fail mark, a plain sentence and a fix. A device with a missing tool can be saved; fix it and press **Check again**. A Mac needs open-source `tailscaled` with Tailscale SSH on.

**Starting.** The launcher's **Node** picker offers each checked device as **<device> (no board)**, even with no paired node. Choose one of its repositories, an agent and an optional model and effort. There are no extra arguments, first prompt or worktree controls. Claude always gets `--permission-mode default|manual|acceptEdits|plan` (Ask is `manual`); Codex gets `-s workspace-write|read-only -a on-request -c check_for_update_on_startup=false`; with no choice the board picks `default` or `workspace-write`. A line with no mode is refused. A shell gets no agent flags. At most 20 sessions are open per device. Every part of a command is validated and quoted in `app/bare.py`, and prompt text goes over stdin, never on a command line.

**Watching.** Each board uses its own tmux socket, `ccboard-bare-<8 hex>` from its node ID, and keeps device sessions in the `bare_sessions` table. The sidebar groups them under the device with a **no board** badge. While this board has open rows on a device, a server worker reads the device every 10 seconds in one SSH call (session list, foreground command, visible screen and up to 40 lines of history per pane). No open rows means no polling and no contact; an offline, unchecked, removed or no-longer-yours device is not contacted either. A failed read keeps the rows and backs off from 10 seconds to 5 minutes without filling Activity. The ordinary board refresh reads only cached rows; **Read** (the refresh icon) reconciles the list with tmux. Before it sends **Allow** or **Deny** the board recaptures the screen and compares the prompt; a changed or vanished menu sends nothing. **Reply** works only at an idle input prompt; for any other dialog use the terminal.

**Terminal.** **Open terminal** on a row gets a private ticket (mode 0600, ten minutes, reconnects allowed until then) for a signed-in person with `X-CCBoard`. The terminal page passes a random ID to `bin/ccboard-attach`, which hands device tickets to `bin/ccboard-attach-bare`; the URL never holds a host. An attached terminal keeps running after the ticket expires; reopen from the sidebar for a fresh one. On a Mac, rerun `./install.sh` once after updating so ttyd knows the data directory.

**Stopping.** **Stop**, then **Confirm** (**Cancel**, or five seconds, disarms) sends `/exit` to Claude, `/quit` to Codex or `exit` to a shell. After ten seconds the board reads the session list once and kills that exact session only if it is still there. A start whose acknowledgement is lost is **unconfirmed** and is never retried; press **Read** to see whether it runs.

**The state log (optional, v0.5.88, #277).** A checked device has **Install state log** and **Remove state log** buttons (each a second tap; nothing is installed until **Confirm**). Install puts one shell script at `~/.ccboard-bare/hook` and merges four hook entries (SessionStart, UserPromptSubmit, Stop, PermissionRequest) into `~/.claude/settings.json` and `~/.codex/hooks.json`, for the agents the check found. The script appends `{"state":"working","session":"bare-<32 hex>","time":<epoch seconds>}` lines to `~/.ccboard-bare/state.log`, only for sessions on a `ccboard-bare-*` socket. It never reads the hook's input, so no prompt text, tool input or path is written. The log is capped at 64 KB (past that it moves to `state.log.1` and the newest 50 lines carry over). The board reads `tail -c 16384` of it in the same 10-second call and prefers a new line to the screen read; the screen read stays the fallback. A visible dialog always wins, a log line about a dialog never overrides a screen without one, a line older than an hour is ignored, and a missing or odd log means the screen alone. Reply and Allow or Deny still use a fresh screen read only. The merge happens on the board: it refuses a settings file that is not a JSON object or is a link (nothing is written), keeps all your other entries, adds ours once, makes one backup (`settings.json.ccboard-bak`) and writes through an atomic rename only if the file's checksum is unchanged and the whole byte count arrived. Codex asks you to review new hooks once: run `/hooks` in a Codex session on the device. Re-adding a device with a different user drops the saved state log, as the hooks sit in the first user's home.

**Removal.**
- **Remove state log** takes out only our entries and deletes the script and logs. Do this first: **Remove device** never contacts the device, so it leaves the hooks (they only write the local log). By hand: `rm -r ~/.ccboard-bare` and delete the entries whose command contains `.ccboard-bare/hook`.
- **Remove device** forgets the saved record, even while the device is offline, if it has no open sessions. With open sessions, stop them, or press **Forget its sessions here** then **Confirm** (it disarms after five seconds): the rows end locally with reason `device_removed` and the sessions keep running on the device.
- The dedicated user, the ACL rule and the tag are yours to remove, in the tailnet policy and on the device.

**Audit.** `bare_check`, `bare_add`, `bare_remove`, `bare_forget_host_key`, `bare_forget`, `bare_start`, `bare_list`, `bare_stop`, `bare_kill`, `bare_attach`, `bare_answer`, `bare_hook_install` and `bare_hook_remove` record the person, device, session and outcome, never prompt or reply text, screen text, command output, file contents or the ticket. Previous images leave device rows alone on rollback.

**When something goes wrong.** Text in backticks in the first two columns below is the board's own wording; `tests/test_bare_docs.py` fails if it drifts from `app/bare.py`, `app/main.py` or the page scripts (`<device>`, `<user>` and `<agent>` stand for the names the board fills in).

| Scenario | What you see | What to do |
| --- | --- | --- |
| Device asleep or offline | `<device> is offline` followed by `Nothing was started.` On a start: `This device is offline. Wake it and try again.` | `Wake it and try again.` No SSH is tried while Tailscale says offline. |
| Tailscale check prompt | `<device> asks for a Tailscale check.` with a login.tailscale.com link and **Retry**. | `Open the link, sign in, press Retry.` |
| Tailnet rule denies the user | `The tailnet rule denied SSH access to <device> as <user>.` | Add the SSH ACL rule from above: `use an SSH ACL check rule (12-hour check period)` for an untagged board, accept for a tagged one. |
| Connection hangs | `The SSH connection timed out for <device>; it was stopped.` | `Wake the device and check its Tailscale connection, then Check again.` |
| Host key changed | `The host key has changed for <device>. SSH was stopped.` | `Verify the device's new host key, then use Forget host key and Check again.` |
| Account in sudo, wheel or admin | `<user> is refused on <device>: groups are unreadable or include sudo, wheel or admin.` | `Use an account outside sudo, wheel and admin, then Check again.` |
| tmux missing | `tmux is not installed for <user> on <device>.` Start is off. | `Install it, then Check again.` |
| Claude or Codex missing | `<agent> is not on <user>'s PATH on <device>.` | `Install <agent> for <user>, then Check again.` Sign-in is not checked; sign in through the terminal. |
| Reading fails mid-session | `The device could not be read; its sessions may still run.` The rows stay as they were; they are not marked ended. | Wait (it retries, then backs off) or press **Read**. |
| Stop not confirmed | `Stop was not confirmed; read the device before trying again.` | Press **Read**. |
| Start not confirmed | The row shows **unconfirmed**. | Press **Read**; a start is never retried for you. |
| Reply with no input prompt | `The session is not at its input prompt. Open the terminal; nothing was sent.` | Answer in the terminal. |
| Answer not confirmed | `The answer is unconfirmed. Open the terminal before trying again.` | Check the terminal before sending it again. |
| Twenty sessions open | `This device already has 20 open sessions; stop some first.` | Stop some. |
| Remove with sessions open | `Stop its sessions first, or refresh the list, or remove it and forget its sessions here (they keep running on the device).` | Stop them, or forget them here. |
| Terminal ticket old | `Terminal ticket expired. Open the terminal again from the board.` | Open the terminal from the sidebar again. |
| `tailscaled` restarts or the device sleeps | The next read either still lists the session or the row ends. | Not yet run on real hardware; see below. |

**Demo.** `?demo=1#/settings?sec=nodes` shows lab-pi with a session in each state the sidebar can show: working, waiting, needs you (a dialog, also in **Needs you**), unconfirmed and stopping. Only open sessions are listed, so a finished one has no row. Everything stays in page memory; no device is contacted.

**Not yet run on real hardware** (the owner's device checks): the real Tailscale check-prompt text, a tmux session surviving a `tailscaled` restart, sleep and wake, a Mac as a target, and the state log hooks firing in real Claude and Codex.

#### The device check (issue #136)

An optional layer on top of the pair token and node signature. Keys prove the node; this check also proves the device. With the device check on, the receiving board also asks Tailscale who is really calling (`tailscale whois`) and, if you want, requires a permission written in your tailnet policy. A copied token then stops working anywhere but on the paired device. **It is off by default**: `CCBOARD_NODE_AUTH=token` (or nothing set) behaves exactly as before, with no Tailscale call, no extra header read, no new column value and no new audit row, and node signing keys continue to apply independently.

| `CCBOARD_NODE_AUTH` | A call from a paired node must carry |
|---|---|
| `token` (default) | the pair token |
| `whois` | the pair token, from the device that paired (its Tailscale StableNodeID, saved in the pair row when the pair was made) |
| `whois+cap` | the same, and the tailnet policy must grant `CCBOARD_NODE_CAP` with the operation of the route's scope (`node.read`, `node.tasks`, `node.sessions` or `node.permissions`) |

The mode is set in the settings file (`/etc/ccboard/env`, or by rerunning `./install.sh` with the value) and needs a restart. Nothing on a page switches it. A node paired before the mode was on has no saved device: it is refused with `not_bound` until it is paired again. Settings > Nodes > **Device check** shows the active mode in words, a banner when the mode is stronger than this host can do now (with the reason), what the host reads (the board's address, the Tailscale version against 1.92, whether Tailscale answers, whether Serve passes the capability on), the last refusal, the grant and the serve command to copy, and how to switch. Each pair that calls this board shows its bound device (the first and last four characters of the StableNodeID, never the whole one) and its tags. `?demo=1` shows every state (below).

- **Where the caller is.** `tailscale serve` ends TLS and proxies to the board on loopback, and puts the caller's tailnet address in `X-Forwarded-For` (it replaces any copy the client sent). uvicorn's proxy headers are on by default and believe that header only from `127.0.0.1` and `::1`, so behind Serve the peer the board sees is already the caller's address, not the proxy (uvicorn takes the rightmost hop that is not loopback; Serve sends exactly one). From any other peer uvicorn keeps the real peer. The board therefore asks three things: the connection arrived on a loopback address of the board (the local end, which nothing rewrites), the request carried `X-Forwarded-For` at all (one without it reached the board directly), and the caller is a tailnet address. Under `uvicorn --no-proxy-headers` the peer stays loopback and the board takes the last `X-Forwarded-For` hop instead. Put nothing between Serve and the board.
- **The board-bind precondition.** Those headers can be forged by anyone who reaches the board directly, so in the two device modes the connection must have arrived on loopback **before** `X-Forwarded-For`, `Tailscale-User-Login` or `Tailscale-App-Capabilities` is read (a test proves no code path reads them otherwise), and the modes **refuse to switch on** while the board listens beyond loopback: every node call is then a `503 board_bind` and Settings and the Doctor (`board-bind`) say why. They also refuse (`503 proxy_trust`) while `FORWARDED_ALLOW_IPS` or `--forwarded-allow-ips` names anything but a loopback address, because uvicorn would then believe a forged header from that wider peer.
- **What it does not protect against: a hostile local user.** Any process on the board's own machine can connect to `127.0.0.1` and send a forged `X-Forwarded-For` and a forged capability header, exactly as it can forge the sign-in header (see [Security model](../security.md#security-model)). The device check narrows who on the tailnet may use a token; it is no defence against someone who can already run programs on the board's machine. The bind is read from the `--host` of the uvicorn process and, on Linux, from the socket table (`/proc/net/tcp`; `psutil` elsewhere). A bind that cannot be read is shown as **unknown (to verify)**, allowed with a warning, and never as healthy; only a confirmed wider listener refuses. In `token` mode a wider bind is only a Doctor warning.
- **Binding at pairing.** In a device mode, after the code matches and before it is spent, the board asks Tailscale who the pairing device is and stores its StableNodeID and tags (`peer_ts_id`, `peer_tags`, added by a forward-only migration; older rows and token-mode pairs stay empty). If Tailscale cannot answer, nothing is paired and the code stays usable. A tag from `CCBOARD_NODE_TAGS` is required when the calling device is tagged or this board's own device is tagged (`none` refuses every tagged caller); when this board cannot read its own Tailscale status, an untagged caller is refused (`503`, the code stays). Pairing **both ways**: the board that starts it binds the reverse pair to the device the other board calls back from to confirm the pairing; if that call never comes, or Tailscale cannot place it, the reverse pair stays unbound and its calls are refused (`not_bound`).
- **On every call**, after the token and its scope pass: the forwarded address is looked up, and its StableNodeID must equal the saved one (`403 device_mismatch`). **Fail closed**: Tailscale that cannot answer is `503 tailscale_unavailable`, never a quiet fall back to the token alone; more than 20 uncached lookups in a minute for the whole board is `429 whois_rate_limited`. Answers are cached 60 seconds per address (an unavailable answer is never cached). Every refusal writes an audit row whose action is the reason, and the answer is `{"error", "reason"}` so the calling board can say which. A pair with tags also needs an allowed tag still on the device.
- **Capabilities** (`whois+cap`). The header Serve adds is JSON, possibly RFC 2047 encoded; the board cuts it at 16 KB before decoding and again before parsing, decodes it with the standard library, merges the `ops` of every object under `CCBOARD_NODE_CAP`, and requires the operation of the route's scope. A missing header, a value that cannot be read or a missing operation is a `403` with its reason (`cap_missing`, `cap_invalid`, `cap_op_missing`). The capability only narrows what the token's scopes allow; it never widens them. Rotate and unpair, the routes any pair may use on itself, need the capability to be granted but no particular operation.
- **Only reads.** The board runs `tailscale whois`, `version`, `status` and `serve status --json`, never a command that changes state: it does not run `serve`, does not touch the tailnet policy and never resets anything. The grant and the Serve command are text for you.
- **The grant** (user-owned devices; the tag variant has `src` and `dst` both `tag:ccboard`). `ip` gives the network access: a grant with only `app` gives none. Use a domain you control; `tailscale.com` is reserved. `<owner login>` and `example.com` are placeholders:

```json
{ "grants": [ { "src": ["<owner login>"], "dst": ["autogroup:self"], "ip": ["tcp:<board port>"],
    "app": { "example.com/cap/ccboard": [ { "ops": ["node.read", "node.tasks", "node.sessions", "node.permissions"] } ] } } ] }
```

Then, once, on the device that serves the board (Tailscale 1.92 or newer, check with `tailscale version`): `tailscale serve --bg --https=<board port> --accept-app-caps=example.com/cap/ccboard http://127.0.0.1:<CCBOARD_PORT>`. Settings shows both texts with your real ports.
- **Doctor (read only).** `board-bind` (pass: loopback only; a wider bind is a fail in a device mode and a warning in `token` mode; unknown is a skip in `token` mode and a warning otherwise) and `node-auth` (a skip in `token` mode that asks Tailscale nothing; otherwise the mode, the Tailscale version, whether Serve passes the capability, whether whois answers and the last refusal).
- **Browser sign-in is not touched.** The `Tailscale-User-Login` check that signs a person in, and the legacy hub-token route `GET /api/node/summary`, work as before.

**The four runtimes** (issue #136). The check needs the board to listen on loopback and to run the Tailscale command. What is known, and what is not:

| Runtime | Board bind | whois through | Measured 2026-10-16 |
|---|---|---|---|
| systemd (Linux box) | `uvicorn --host 127.0.0.1` in `systemd/ccboard.service.in` | the `tailscale` command | Not measured on a systemd install: to verify. |
| Container | `--host 127.0.0.1` in the entrypoint, on the host network | the same command, through the mounted `tailscaled` socket | The board was found bound to `127.0.0.1:8000` only, Tailscale 1.104.1, and it reads a `ts:` node id through the socket. `whois` itself inside the container: to verify. |
| launchd (Mac) | `--host 127.0.0.1` in the plist | the Tailscale app binary run with `TAILSCALE_BE_CLI=1` | The board was found bound to `127.0.0.1:8000` only, Tailscale 1.104.1, and the board runs that command successfully. `whois` on a Mac and the `psutil` bind reading (`psutil` is not installed by default, so the reading relies on the plist's `--host`): to verify. |
| WSL2 | `--host 127.0.0.1` in the unit | the distro's `tailscale`, or the Windows host's through interop (to verify) | Not run on a real Windows machine: to verify. With Tailscale on the Windows host, whether the board then sees a loopback peer is to verify. |

**To verify on the two real boards** (issue #155), until it is proven there: that `AcceptAppCaps` is the key `serve status --json` uses; the exact text the command prints for an unknown address (the board matches "peer not found", "not found" or "no match"); the real header Serve sends (plain JSON for ASCII, RFC 2047 for anything else); what the user profile holds for a tagged peer; `whois` inside the container and on WSL2; and that a copied token used from a third device is refused.

**Demo.** `?demo=1#/settings?sec=nodes` shows the Device check in `token` mode; `?demo=1&authstate=<name>#/settings?sec=nodes` shows the others, with `<name>` one of `whois`, `whois-cap`, `tagged` (more than one allowed tag), `bind` (the board listens wider), `old` (Tailscale 1.88.2), `noserve` (Serve without the capability flag), `down` (whois does not answer), `nocap` (`whois+cap` without a capability name), `badmode` (an unknown value) or `unknown` (nothing could be read). **Check** on the token state plays the host reading.

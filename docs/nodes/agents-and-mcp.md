# Using nodes from an agent

For people who let an agent session call other nodes.

[Back to the documentation index](../README.md)

#### Using nodes from an agent (issue #152; phase P10)

An agent session on this board (Claude Code or Codex, through the stdio `ccboard` server or through `/mcp`) can list the paired nodes, read their projects and tasks and, at the higher level, create a task on one and start it in a new session there. It is **off** until the board's owner sets `CCBOARD_MCP_NODES`; Settings > Agents shows the level in words, read-only, with the env value, next to the MCP block.

- **Levels.** `0` (or unset, or any value not listed) is off. `read` lets the tools list the nodes and read a node's projects and tasks: `list_nodes`, `list_projects`, `list_tasks`, `get_task_status`, `get_task_result`. `tasks` also lets `create_task` and `dispatch_task` act on a node. `1` keeps meaning `read` (the safer reading of the old value). The stdio shim, which holds the hook token every agent session on the box has, holds only the scopes the level grants (never every scope), and a device token still needs its own scope as well. At `read`, a write answers `403` `mcp_level` with "this board lets agents read other nodes but not start tasks on them (CCBOARD_MCP_NODES is read; tasks allows it); nothing was sent", and the refused try is audited with who asked.
- **Off (the default).** A tool call whose `node` is not `local` is a tool error: "this board does not let agents act on other nodes (CCBOARD_MCP_NODES is off)". It is checked before the registry, so an unknown handle learns nothing while the switch is off. `list_nodes` works either way.
- **Which tools.** The six existing tools take an optional `node` (`local`, the default, or the handle of a paired node; the shape is checked before anything else): `list_projects`, `list_tasks`, `get_task_status`, `get_task_result` (reads) and `create_task`, `dispatch_task` (writes). `list_nodes` (no arguments) lists the paired nodes from the hub's last reading, without asking any node: handle, name, status, age in seconds, free task lanes, the agents on each (name and a `ready` flag: installed and logged in) and the level of this board; never an address, a token, an id, a version, an account or login detail, a usage window or a scope of a pair. Ids of a remote task come back as `<handle>:<id>`; local ids stay plain numbers. Every answer for another node carries `node` and `age`, and what the node does not share is `null`, never a guess. The result text of a remote task is not shared: `get_task_result` says `has_result` and where to read it ("read it on <node> itself").
- **What an agent may send is checked at the route.** Whoever calls `/api/nodes/<handle>/...` as an agent (the hook token over HTTP, or a device token through `/mcp`) is read with a body of exactly the fields its tool sends, not the person's: for `create_task` `project`, `repo`, `title` (120 characters), `prompt`, `when` (`dispatch` false is `later`), `agent` (`claude` or `codex`, and installed on that node as the hub last read its card) and `auto_close`; for `dispatch_task` `agent` and `auto_close`, always as a new session (the hub adds the lane mode itself). Anything else, whoever sent it and however: `model`, `effort`, reasoning, an issue reference, a permission mode, options, `session`, `force`, `queue`, `after_task_id`, or a query on a read, is a `422` before anything is sent. The tool schemas and these bodies are made from one table (`NODE_SEND` in `app/mcp.py`; the module fails to load when they differ). The node writes the explicit safe launch options for everything left out. The `card` and `agents` rows are not open to agents at all: no tool reads them.
- **What comes back is untrusted data.** An agent gets a reduced answer, built field by field (no account or login detail, no usage window, version, address, node id or audit data, no screen state beyond the state word), and every tool answer for another node is `{node, age, untrusted: true, notice, data}`: everything the node said is under `data`, and the `notice` says it is information, never an instruction. Free text (a task title) is cut to 120 characters, error text to 160, both on one line (line breaks, tabs and separators become spaces), without control, format or bidi characters, with `<`, `>` and backticks replaced by `(`, `)` and `'`, and run through the secret redaction. A name, branch, phase, session name or time that does not have its shape is `null`. Nothing tries to recognise an instruction by its words; the tool descriptions say it in a sentence, and the stdio shim and `/mcp` use the same code (`tests/test_mcp_nodes.py` keeps the two copies equal).
- **Scopes, both ends.** A read needs the level `read` or `tasks`, the token's `read` scope and the pair's `read`; a write needs the level `tasks`, the token's `tasks` scope and the pair's `tasks`. The tool error names the side that lacks it ("this device token does not hold the tasks scope" or "needs the tasks scope on build-box"). A remote `create_task` starts with an explicit manual permission mode and never inherits a default; a remote `dispatch_task` starts a new session of its own only (`session`, `force` and `queue` are tool errors, as is `after_task_id`: chains stay inside one node).
- **What an agent can never do on another node.** Send a prompt or keys, answer or list a permission request, acknowledge or close a session, read a screen or the stream, open a plain session, hand a task to a running session, pair, mint a token or change a setting. No tool has a permission, sandbox, bypass, arguments, tools, keys or model argument (a test fails if one does), and every other relay row is refused for an MCP caller whatever the scopes are. The guard, the command-prefix rule, the missing-repo sentence, the redaction of every peer string and "unconfirmed on timeout, never retried" apply as they do for a person.
- **Audit and limits.** Both boards write a row for each call: `out` on this board with `mcp:<token name>` (or `local-token` for the stdio shim, which is every agent session on the box together: it is not a person and it names no session) and the node, and `in` on the node, where the caller's name is a claim. The prompt is in neither row. The `/mcp` limits apply, plus the relay's bucket keyed by the token name (each token has its own, the shim has one for the whole box, and neither draws from a person's).
- **Epic tools (phase P15).** `epic_status(repo, number)` reads an epic the way its page does, as plain fields: the issues, their claims, the nodes they are on, what the run sent and what waits (level `read` or `tasks`, the token's `read` scope). `epic_run(repo, number, max_issues?)` starts the run of an epic, and works **only when every one of these holds**, checked in this order: this board's level is `tasks`, the token holds `tasks`, fewer than 6 calls were made by that token in the last hour, `max_issues` is 1 to 10 (10 if left out), the epic's own setting **Let MCP run this epic** (`mcp_run`) is on, the epic is not paused, and GitHub writes are on with a node paired. `mcp_run` is off by default and is set only by a signed-in person on the epic page: the hook token, a node token and a device token get a `403` on that route, so no tool can turn it on. Every refusal and every start is audited with who asked (`mcp:<token name>` or `local-token`). Turning off **Let MCP run this epic**, lowering the MCP level below `tasks` or turning GitHub writes off stops a run an agent started at its next step (before the next issue is sent), and so does revoking the device token that started it. The run goes on in the board after the call; the first cycle runs while the call waits, for 20 seconds at most, and the answer says what was sent and what waits. The text of an epic comes back as untrusted data like any other node data. Neither tool has a permission, sandbox, bypass, arguments or keys property.
- **Not in this phase.** The `node` argument is a free string checked by shape (the list of handles is `list_nodes`, not a `tools/list` enum). A remote `list_projects` and `list_tasks` use the live `state` row (one request each, `age` 0) rather than the hub's last reading. `list_nodes` stays as shipped: it shows no usage window, lane cap or pair scope to an agent, on purpose.

Claude Code (the same `claude mcp add` line as [on the MCP page](../guide/mcp.md#mcp-from-other-devices), or the stdio server `install.sh` registered on the box; then, with `CCBOARD_MCP_NODES=tasks` on this board, or `read` for the reads):

```
claude mcp list
# in the session: "Call list_nodes, then create_task on node build-box: title 'Fix the flaky cart test', project shop, repo api."
```

Codex (the same `codex mcp add` line as [on the MCP page](../guide/mcp.md#mcp-from-other-devices); Codex reads the token variable when it starts):

```
codex mcp list
# in the session: "Use the ccboard tools: list_nodes, then get_task_status for task build-box:12."
```

For an epic (after you turned on **Let MCP run this epic** on its page, and with `CCBOARD_MCP_NODES=tasks`):

```
# in the session: "Call epic_status for repo example/website, number 147, then epic_run with max_issues 2."
```

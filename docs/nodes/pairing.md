# Pairing two boards

For people pairing two boards.

[Back to the documentation index](../README.md)

#### Pairing two boards

Pairing connects two boards with a one-time code that you read on one and type on the other. From then on the second board can call the first with its own token, limited to what you chose. A token belongs to one pair, shows once, and can be rotated or cut at any time. The token and, for keyed pairs, a pinned signature open only the [scoped node routes](../security.md#node-scopes-and-routes).

**The steps (Settings > Nodes).**

1. On the board that will be controlled (call it B) press **Create pairing code**, tick what the other board may do, and read the code (`XXXXX-XXXXX`, valid for 10 minutes by default, 1 to 30). It is shown once. **Cancel code** ends it early; making a new one replaces the old one.
2. On the board that will do the controlling (A) press **Add node**, type B's address (`https://<node>.<tailnet>.ts.net`, or the one under "Found on your tailnet" with Pair) and the code. Tick "also let that node control this one" to give B a token for A as well (scopes `read` and `tasks`).
3. A is "Paired" once it has read B's card. B lists A under **Who can control this node** with when it was last used. **Rotate token** (on A) and **Remove** (on A) or **Revoke** (on B) are two taps.

**Scopes.** The accepting board chooses them: `read` and `tasks` default on; `sessions` and `permissions` default off. The [security table](../security.md#node-scopes-and-routes) lists every route and scope. `read` exposes task titles and session names, and the newest audit rows that name the calling pair (no other pair's rows), but no prompts, results or screen text. `sessions` exposes tails to everyone signed in on the calling board; those can contain secrets and redaction is best effort. Permission summaries can contain commands and paths, so they have a separate scope. An answer must come from a signed-in person through the hub.

**The code.** 10 characters of Crockford base32 (50 bits), single use. The board keeps only its SHA-256 hash, expiry, scopes and attempt counter. Five wrong tries burn it; a source gets 20 tries a minute. The pair endpoint needs `X-CCBoard: 1`, refuses Origin and disallowed identity headers, caps the body at 16 KB and accepts only `code`, `node`, `reverse` and `confirm`. The node claim accepts an optional public key. It checks the shape before spending the code. A's Add node holds a random confirm nonce for this call. B calls A with the code-keyed HMAC bound to the nonce, caller id, both addresses and, for keyed pairs, the public key. The signed answer must match that key and id. A keyed callback that cannot be verified refuses the pair; it cannot fall back to an unsigned pair. See [Node signing keys](#node-signing-keys) for the wire format and the older-board retry.

For unkeyed pairing, a missing or unreachable callback keeps the **callback not verified** flag after acknowledgement: B keeps no reverse token and does not replace a verified pair. Removal, unpair and replacement still check the address as well as the id. A newer verified pair at another address marks an older pair `superseded_by`; the person decides which to revoke through `remove-preview`. The confirm route needs `X-CCBoard: 1`, refuses Origin, reads at most 1 KB and allows 30 calls a minute per source.

**The token.** `ccbnode_` and 43 URL-safe characters (256 bits), made by the board that accepts the pair and returned once, in the pair answer or the rotate answer. The accepting board keeps its SHA-256 hash in the `node_pairs` table (compared in constant time against every pair); the calling board keeps the token itself in `<data dir>/node-tokens.json` (0600, written whole and atomically, an earlier file stays if a write fails; only the outgoing client reads it). Plaintext tokens and codes never appear in the database, logs, audit rows or later answers; the database does hold their verification hashes. `GET /api/nodes` and `/api/nodes/pairs` list pairs without either.

**What a token opens.** A pair credential needs `X-CCBoard: 1`, no `Origin`, and no hook or hub credential alongside it. The [security table](../security.md#node-scopes-and-routes) is the complete allowlist, including pair acknowledgement and self-management. Pending pairs can only acknowledge; keyed pairs also need the pinned signature.

**The allowlist rule.** After signature verification, every other `/api/*` route is a `403` for a node token (the table is closed; `tests/test_nodes_auth.py` walks every route of the running app, so a route added without a row fails that test by default), a listed path with another method is a `405` with `Allow`, and `/mcp`, `/api/hook`, `/api/permission` and `/api/deploy/gate` are among them. The hook token and the hub token are never node credentials, and a node token is none of theirs. A pair has its own bucket (120 reads and 30 writes a minute, then `429` with `Retry-After`) and a request body over 256 KB is a `413`. The caller may send `X-CCBoard-Node` and `X-CCBoard-Acting-User` (at most 64 characters, control characters dropped); both are bound by the signature. The node id must match the pin; the acting user is still the paired board's claim, not proof of a person.

**Rotate and remove.** *Rotate token* (A) asks B for a new token with the current one; B answers it once and keeps the old one valid for 60 seconds, so running work is not cut. *Remove* (A) tells B to unpair as a best effort, then deletes the row and the token whatever B answers: removing never fails because the other board is off (it says so, and you press Revoke on B). Removing a both-ways pair also revokes its confirmed incoming pair at the same node id and address: the Remove sheet warns that the other direction goes too, then names what went, and the answer lists it under `auto_revoked: [{peer_id, name}]` (`[]` for a one-way pair), while `also_revoked` still lists only extra pairs requested. *Revoke* (B) cuts a pair at once: its next request is a `401`.

**Routes.** All need the login and `X-CCBoard` for a change, and the hook token, the hub token and a node token are refused on them (a person manages pairs): `POST /api/nodes/pair-code {scopes, minutes}`, `DELETE /api/nodes/pair-code`, `POST /api/nodes {url, code, handle?, both_ways?}`, `GET /api/nodes` (the nodes this board calls, plus the pairs that call it), `GET /api/nodes/pairs`, `GET /api/nodes/audit?limit=100` (1 to 500; optional filters `direction=in|out`, `node=<name or peer id>`, `action=<one action>`, `failures=1`, all together), `POST /api/nodes/{peer}/rotate`, `POST /api/nodes/{peer}/remove-preview` (which other pairs use the same node id; changes nothing), `DELETE /api/nodes/{peer}` (optional body `{also_revoke: [peer_id, ...]}`: each must be an active pair with the removed node's node id, else 400 and nothing happens). `{peer}` is the `peer_id` (`p_` and 16 hex characters) or a registry handle. The address of the other board follows the same rule as discovery, when it is saved and at every call, and a redirect is never followed. `POST /api/nodes/pair` is the one route that answers with no login (above).

**Audit.** `node_audit` holds one row per pair event (code created, cancelled and burned, a pair made, refused and revoked, rotated, removed), per refused node call and, from the relay, per relayed call on both boards, with the time, direction (`in` or `out`), the other board's name, the acting user, the action, the target (`task 42`), the status (`ok`, `failed`, `refused`) and a short detail. Settings > Nodes > Activity lists the rows newest first and filters them by direction (Sent or Received), node, action and Failed. Rows are kept 90 days. It also lists the rows each paired node keeps **about this board**, next to this board's own, marked with the node's chip ("on build-box"), the direction as that node saw it ("it received", "it sent") and the time this board received them next to the row's own time: `GET /api/nodes/<handle>/audit?limit=25` (the relay row `audit`, a signed-in person's read; the node's side is `GET /api/node/audit`, scope `read`) answers the newest rows whose pair is the caller's, at most 50, with no other pair's rows, no prompt text and no token (every field is rebuilt on the hub and cleaned again), and leaves out its own reads of this list. The page reads them when the tab opens and when **Reload** is pressed, one call per node you call that holds `read`, at most 12, never from a poll or a filter; a node that cannot be read keeps its last rows and the page says why under the list. The filters apply to those rows too. A row may show a short public key id, but never a token, a code, a full digest, a seed, a signature or a prompt: anything shaped like one is replaced before it is written.

**`CCBOARD_NODES` and the hub token (deprecated).** Each entry is read into the registry at start as a **legacy** row ("read only, pair to enable actions"). The hub polls it with `CCBOARD_HUB_TOKEN` on `GET /api/node/summary`, exactly as before (since v0.5.36 by the hub read model's threads, [below](hub-and-relay.md#the-hub-read-model)); the hub token is accepted on that one route and nowhere else. Pairing the same address replaces the legacy row and the hub stops asking it with the hub token. A board with no `CCBOARD_NODES` and no pair starts no thread, makes no request, and adds no key to `/api/state`.

**Doctor row (group Box, read only).** `nodes-pairs` warns for a pair that nobody has used for 90 days, a token made or rotated more than 180 days ago (judged for a pair that calls this board; a node this board calls does not record its rotations yet, so its token's age is not judged), and a pair marked `needs_repair` (the other board stopped taking the saved token); each fix names the button (Remove then Add node, Rotate token, Revoke).

`?demo=1` reads `app/static/demo/nodes.json` for the paired list, who can control this node and the activity. To verify in the two-node check (#155): the whole handshake across two real boards through `tailscale serve`, the 60-second rotation window against a real clock, the callback check from a tagged board, and that a user-owned board's server process (which arrives with the owner's login) is told apart by its token and signature.

#### Node signing keys

Every board makes an Ed25519 key on first use. `<data dir>/node-key` contains `ed25519:` and the base64url 32-byte seed, with mode 0600. Only `app/node_keys.py` reads it. It is not backed up on purpose, like `node-id` and `node-tokens.json`. The SQLite snapshot contains only public pins. Restoring without the key makes a new identity key: every peer refuses it until the pair is removed and made again. A corrupt file is kept once as `node-key.bad`, also 0600; Doctor says every pair must be made again, then to delete `node-key.bad` in the data directory and restart to clear the warning. An unwritable directory gives a key for this run only and a Doctor failure.

Settings > Nodes shows the algorithm, created date and key id in four groups, with Copy. Pairing pins both public keys with source `pairing`; the pair sheet says **Check that this matches on the other board**. The id is the first 16 hex characters of SHA-256 of the raw public key. A different key at any address cannot take over an already pinned node id. Remove the old pair before pairing a replacement key.

`CCBOARD_NODE_KEYS=prefer` is the default for this release. Old unkeyed pairs work and Doctor names them with **pair again**. Their first signed request carries `X-CCBoard-Pubkey`; the receiver verifies and pins it with source `upgrade`. The sender pins the other board's public key on its next card read. This is weaker than a code-bound pairing: whoever holds a stolen token could win that first use. Settings says **keyed (upgrade)** and offers Pair again. `require` refuses unkeyed calls with `signature_required` or `key_required` and refuses an unkeyed pairing before the acceptor spends the code or issues a token. Both boards need the key update and signing enabled, or use `prefer`. An invalid `CCBOARD_NODE_KEYS` value fails closed as `require`; Doctor names the invalid value. `off` makes and sends no key and does not upgrade unkeyed pairs; Doctor warns. **An existing pin always requires a valid signature, even in off.** The owner decides whether to make `require` the default two releases after this one.

The pairing proof is HMAC-SHA256, keyed with the code, over compact JSON `["ccboard-pair-confirm/3", nonce, caller_id, caller_address, target_address, caller_pubkey]`. The confirm answer is `{node_id, pubkey, sig}`; the signed bytes are newline-joined `ccboard-pair-confirm-answer/1`, the proof and the node id. With no public key on either side the proof stays `/2` and the pair is unkeyed. In prefer mode, a previous board's strict 400 `bad_request` triggers one retry without `pubkey`, before it spends the code; require never retries unkeyed. `hello` remains exactly three fields.

The keyed pair answer also carries `sig`: the acceptor signs newline-joined `ccboard-pair-answer/1`, the code-bound proof, SHA-256 of the issued token (hex, never the token itself), caller node id and acceptor node id. The caller verifies this against the answer's public key before saving the token or pins. Updated callers send `X-CCBoard-Pair-Ack: 1` when pairing and send a signed `POST /api/node/pair/ack` with the token when the answer says `pending: true`. Until that acknowledgement, the acceptor keeps only a pending row: the token cannot make normal calls, the key is provisional and cannot block a new pairing, and older pairs remain active. Reverse pairing is saved only on acknowledgement. A re-pair keeps its existing local row and token until the ack answers `active: true`; a refused or unanswered ack discards only the staged token. If the acceptor activated the pair but its ack answer was lost, pair again with a new code. Without the request header, the acceptor activates the pair and reverse pair immediately; an answer without `pending: true` is already active and needs no ack. Existing pairs remain active on upgrade, and a new pairing between an updated and an older board still works. Unrevoked pending rows are deleted after ten minutes with a `pair_expired` audit entry, on the scheduler tick or the next pairing or token lookup; this also works after a restart. Revoked rows keep their revocation history. Settings > Nodes lists “Pairing with <name> not finished, expires in N min” with Remove for a signed-in person. Pending rows count toward the incoming pair limit only up to three. A pending token gets 401 `pairing_not_acknowledged`; the caller shows “the other board has not confirmed this pairing yet; pair again if it does not finish” without marking the pair as needing repair. A missing or invalid signature refuses the pair. Unkeyed answers still work in prefer and are refused in require. A keyed callback timeout refuses without pinning; the code has already been spent, so the message asks for a new one. A pin conflict says to remove that node's existing pair on the board holding the conflicting pin first.

Every keyed request, including streams and unpair, carries `X-CCBoard-Signature: v1.<key id>.<unix seconds>.<nonce>.<signature>`. The nonce is 16 random bytes in unpadded base64url; the signature is 64 bytes in unpadded base64url. The signed bytes are these UTF-8 lines joined by a newline, without a final newline except the empty acting-user line:

```text
ccboard-node-req/1
METHOD
/path?query=exactly-as-sent
SHA256(body bytes) in hex
unix seconds
nonce
recipient node id
sender node id
SHA256(pair token) in hex
acting user, or empty
```

After the token and rate checks, the receiver caps and hashes the body and verifies the signature before granting a route. Refusals are 401 JSON with fixed reasons: `signature_required`, `key_required`, `key_changed`, `bad_signature`, `clock`, `replay`, `stale`. Clocks must be within 120 seconds; a clock refusal says to fix the time. The board atomically records each accepted sender node id and nonce in SQLite until the request timestamp plus 120 seconds, refusing repeats as replay even after a restart. Expired records are pruned in bounded batches; unexpired records are never evicted. The start floor is process start minus 120 seconds, allowing a slightly slow peer after restart. Requests below the start floor are stale. Stale, replay and clock refusals name the check in the hub and Doctor without asking to re-pair. Audit records a reason, key id and `verified` on verified calls, never a seed, signature, token or body.

**Rotate key** in Settings > Nodes > This node takes two taps. The new key is saved atomically. The old key signs newline-joined `ccboard-key-rotate/1`, old public key, new public key and Unix time, then is discarded. Public proofs live in `node-key-rotation.json`; `X-CCBoard-Key-Rotation` is base64url JSON of an `{old,new,at,sig}` statement (a list of up to 16 statements for consecutive rotations). A peer follows only a valid chain from its pinned key, within 30 days, and verifies the request with the new key before replacing the pin with source `rotation`. The sender stops attaching proofs to that pair after `X-CCBoard-Key-Seen: <new key id>`. The public card carries the same proof so a polling peer can catch up. An offline peer catches up on its next contact within 30 days; later, pair again. Rotation protects an ageing key, not a stolen one: whoever has the old key can rotate it. A stolen or lost key means **Remove** the pair and pair again with a new code. There is no accept-new-key button.

Assumed: boards reach each other over a tailnet (encrypted by Tailscale, and by the HTTPS certificate of `tailscale serve`). Other devices on the tailnet may be hostile or compromised, and some boards a person pairs with may not be under their control.

What the key stops:
- A stolen token. Reading `node-tokens.json`, a backup of it, or a request log line gives an attacker the bearer secret but not the private key, so the peer answers `signature_required` or `bad_signature`.
- Another board taking over a paired node's identity. Once a node id has a pinned key, a board that claims the id with another key is refused (`key_changed`), at the same address or another.
- Replay and redirection of a captured request. The signature covers method, target, body hash, time, nonce, the recipient's id and the pair's token hash, and the receiving board persists sender/nonce records across restarts and refuses timestamps outside the clock window or below its start-minus-120-second floor.
- A hostile board vouching for a key it does not hold. Both the confirm answer and pair answer are signed, so neither side can copy another node's public card and be pinned without proving possession of its key.

What the key does not do:
- It does not prove who the person at the other board is. The root of trust at the first pairing stays the pairing code and the address the person typed (trust on first use, with the code binding the key). A hostile board can still pair with its own fresh key under any node id that has no pin yet. The fingerprint comparison on the pair screen is the answer to that, and it is up to the person. Deriving the node id from the key (a self-certifying id) would close it and is a separate decision, not part of this issue.
- It does not protect a node whose private key file is readable by an attacker (same user, root, a backup that included it). It does not protect against an allowed, correctly paired peer misusing the scopes it was given.
- It signs the pairing and confirm answers, but does not sign ordinary API responses or encrypt them. A paired peer that lies in its answers is a trust decision the scopes limit; transport integrity comes from the tailnet and HTTPS.
- It does not replace the optional device check (`CCBOARD_NODE_AUTH`) or the scopes; it adds a layer under them.

This closes #135's unsigned-confirm hole for keyed pairs: both boards must prove possession of the private halves of their code-bound public keys. It does not authenticate a person's identity or make unpinned node ids self-certifying.
